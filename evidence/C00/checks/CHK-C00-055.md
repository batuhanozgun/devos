**F1: Lease expiry is treated as a stop**
- **Plan place:** K-7 item 6; Appendix B 3.5; Appendix G G5 item 2; 6.3 "Session lifetime"; 6.8 item 4; Appendix A DR06-Y acceptance ("no ghost workers").
- **Sources:** C:.../2026-09-08-devos02/REVIEW.md §5; C:.../2026-09-06-stage-1a/REVIEW.md §4; S:hermes-agent/.../LEASE-RECOVERY-COVERAGE-2026-09-11.md (ownership row); S:hermes-agent/inventory/CONTINUITY-COVERAGE-2026-09-11.md (ownership/delegation row).
- **What they show:** An expired lease stops the old holder only on paths that consult the lease. On any other path the old writer may still be running. So a takeover needs either evidence that the old writer stopped, or a fence on every effect path. The hermes coverage found claim, refresh, expiry and reclaim, but left process cancellation and an effect fence open.
- **What it means for the plan:**
  - The database side is fenced (B 3.12 re-check; F08 (c)).
  - Section 6.3 says a paused cloud session can come back. If such a session's claim expired and its work was reassigned, it still has the machine account's git path: it can push and open a PR.
  - K-7 item 3 gives "a branch per writer" but does not tie the branch to the claim generation.
  - 6.8 item 4 re-reads "authority and epoch". An expired claim in the same epoch passes that check unless the generation on the PR's Operation is also checked.
  - N21 tests a second claim, not a resumed expired one.
- **Type:** factual or technical defect. Condition 1.

**F2: The plan does not keep schedule, due occurrence and attempt apart**
- **Plan place:** 6.4; Appendix B §5, §6 (independent monitoring), 3.21, 3.24; Appendix G G7 routine and Actions rows; C11 task 2 and its acceptance; K-7 item 9.
- **Sources:** S:hermes-agent/synthesis/04 §1, §2, §3, §5; S:hermes-agent/synthesis/03 §1; S:hermes-agent/inventory/CRON-COVERAGE-2026-09-11.md (job/trigger row).
- **What they show:**
  - A reusable job, one due fire, one execution attempt and one consumed run right each have their own identity.
  - Success at one link proves nothing about the next.
  - A stored record does not show that the automation still fires.
  - Tick counts, model-run counts and report counts differ.
  - Deduplication per occurrence was lost where the key narrowed to the job alone, or where a live claim stood in for it.
- **What it means for the plan:** The plan has the schedule (the routine) and the attempt (SessionRecord), but no record of the due occurrence. Inside the plan's own text this gives four gaps:
  - (a) G7 models one routine stopping while the others continue. But the monitor checks one "last session record" time, which the other routines keep fresh. A stopped audit routine, meaning no binding verdicts, would go unseen.
  - (b) The B §5 database jobs (purpose audit, sampling, deadlock scan, capability-gap scan, assumption testing) have no outside check. Yet C11's acceptance requires that a faltering job "was noticed and recorded".
  - (c) A fire that dies before `register_session` is invisible to the routine-run count.
  - (d) LaunchRecord has no work-item or cause field. A cause that stays true until the started session claims the work (for example, Batu's answer has arrived) can trigger again and use up the reserve budget. N24 covers only a lost response.
- **Type:** factual or technical defect. Condition 2.

**F3: The export mark can be set before the backup is delivered**
- **Plan place:** 5.7 items 2–3; Appendix B §2 (`devos_backup`), 3.13 `exported_at`, §4 `mark_exported`, §6 monitor; C09; N26.
- **Sources:** S:hermes-agent/synthesis/04 §4, §5; S:hermes-agent/synthesis/03 §5.
- **What they show:** A progress checkpoint recorded before the downstream step succeeds changes meaning once it is used as "processed". Writing an output and delivering it are separate states. A counter can advance while the saved copy stays stale after a failed save.
- **What it means for the plan:**
  - The plan never fixes the order of `mark_exported` and the push to `devos-backup`.
  - If the mark comes first and the push fails, those events are never exported again. The loss is silent and has no limit, not one hour.
  - A monitor that reads the mark would still report a fresh backup.
- **Type:** factual or technical defect. Condition 3.

**F4: The restore closes and reconnects a hand-written list, not the inventoried scope**
- **Plan place:** K-8 item 5 (a), (d); Appendix G G6 items 1 and 3; Section 12 item 4 and the key inventory; 6.7; 6.2 (migration job and outbound trigger); 6.9 (intake); Appendix C F03.
- **Sources:** F:05_relation-control-composition/transition-effect-feedback/synthesis/TRANSITION-EFFECT-FEEDBACK-SYNTHESIS.md (cloud-IAM propagation part); F:05_relation-control-composition/transition-effect-feedback/transition-propagation/synthesis/TRANSITION-PROPAGATION-SYNTHESIS.md §6, §11, §15.
- **What they show:**
  - A revocation committed centrally is not yet in effect at every point, and old sessions can stay usable.
  - Running a reconciliation does not mean things are reconciled.
  - Updating every known target does not show that every applicable target is known. A completeness claim therefore needs scope discovery, or it stays "unknown".
- **What it means for the plan:**
  - G6 item 3 reconnects environments, routines, CI and the backup job; K-8 (d) and Section 12 item 4 are similar.
  - Paths the plan itself defines are missing from these lists:
    - the migration job (credential per project, 6.2);
    - ingestion;
    - the independent monitor;
    - the decision-channel intake (6.9). If it is missed, Batu's answers go to the dead project;
    - the second-model gateway and its key;
    - the routine API trigger key in the old project's secrets. With it, the old database can still start routines once they are re-enabled.
  - F03 (f) tests an old routine against the new project, not the reverse.
  - Minor, same place: `Recovery.pending_effects_reconciled` reads like a flag. Following §11, it should link to an Observation for each open Operation.
- **Type:** factual or technical defect. Condition 4.

**F5: `informed_of` cannot hold what the plan says it records**
- **Plan place:** Appendix B 3.4, 3.16; 6.10; C06 (criterion 14); Appendix E §8.
- **Sources:** F:05_relation-control-composition/relational-binding/synthesis/RELATIONAL-BINDING-SYNTHESIS.md (n-ary qualifier part; represented versus actual); F:05 TEF synthesis (feedback part); F:05/.../feedback-adaptation/synthesis/FEEDBACK-ADAPTATION-SYNTHESIS.md §3; S:hermes-agent/synthesis/02 §6.
- **What they show:** Qualifiers such as time belong to one instance of a relation, and they are lost when the relation is reduced to two endpoints. A signal being available is not the same as it being taken in. Starting a computation and delivering its notice are separate events.
- **What it means for the plan:**
  - 3.4 says `informed_of` carries when and through which channel. The Relation fields have no place for either.
  - The event's `created_at` is the time the record was made, not the time Batu was told.
  - So the user model cannot tell "issue opened" from "Batu opened it". That is exactly the distinction the 24-hour repeat rule in Appendix E depends on.
- **Type:** factual or technical defect (internal inconsistency). Condition 5.

**F6 (non-blocking): The accepted whole and the released whole are one state in the plan**
- **Plan place:** K-5 item 1; Appendix B 3.10 `delivery_baseline`; Appendix G G4 item 1; C08 (install from `soul-system`).
- **Sources:** C:current/DEVELOPMENT-OS-BOOTSTRAP.md (repository-authority part); F:03_ground-deepening/grounds/environment/synthesis/ENVIRONMENT-GROUND-SYNTHESIS.md §4; F:05 transition-propagation synthesis §6.
- **What they show:** The candidate, the accepted main or release, and the running product are separate. Finishing work in a repository does not mean the target changed.
- **What it means for the plan:** The plan uses "delivered" and "accepted" for one state. The release itself is tracked as an Operation and Observation, so no information is lost. But the Assembly cannot say which accepted whole was actually released, and the C08 install test needs that.
- **Recommendation:** in C08, either rename the field to an accepted baseline, or add a released baseline linked to the release Observation.
- **Type:** difference of preference, bordering on a defect.

**F7 (non-blocking): Verdict values cannot express "undecidable"**

- **Source:** F:05_relation-control-composition/composite-standing/synthesis/COMPOSITE-STANDING-SYNTHESIS.md (false/unknown/stale non-collapse part; the section from line 151 at 941f027, which separates a standard from the rule for applying it).
