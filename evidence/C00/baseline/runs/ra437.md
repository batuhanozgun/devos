# BR-212 · Run store retention job: design

**Summary.** A daily systemd timer on `disp-1` deletes every run record whose date directory is older than the last 14 UTC days. Nothing in Brindle reads a record after its 7th day. Keeping 14 days gives twice that margin and holds the store at about 200–225 GiB, which is 20–22% of 1,024 GiB and far below the 70% line of 716.8 GiB. The 7 newest directories (today and the six before it) are protected in code. No setting or mode of the job can delete them.

**Deadline.** On 2026-09-30 the volume had 133 GiB free and was growing by 14–15 GiB a day, so it fills around **2026-10-08/09**. The required dry-run day has to fit before that.

## 1. What is deleted, what is kept, and why

These are all the readers of run records named in the materials:

| Reader | What it needs from run records | Source |
|---|---|---|
| The running session | Its own record while it appends to it (at most 6 h) | overview, run_records |
| Dispatcher (billing) | The end line, read once as soon as it is written. The counts then live in the usage DB, or in `dispatcher.db` until the copy succeeds | operations |
| On-call | `failed`/`killed` records in today's UTC date directory and the six before it | operations |
| Reviewers / `replay promote` | Any record until 48 h after the session ended. Sessions last at most 6 h, so that is at most 54 h after start (start day + 3) | replay_suite |
| Replay suite | Nothing. It reads only the fixtures committed in the repository | replay_suite |
| Periodic triggers / `periodic retry` | Nothing. The `periodic_runs` table decides whether a period is done, and `retry` needs only the trigger key | scheduler |
| Invoices, cost report | Nothing. They use the usage DB only and are never rebuilt from records | operations |
| Audit, legal, security | Nothing (counsel, 2026-06-03) | policy_notes |

What follows from this:

- **No special cases.** Golden sessions, periodic sessions (including the quarterly `access-review` and `licence-scan`) and records from the current billing month need no extra retention.
  - Deleting a golden session's record does not affect the suite.
  - Deleting a periodic record does not make its trigger run again.
- **Seven directories meet every need.** Age is measured by the date directory's name (session start date, UTC), not by file mtime or end time. That is how the on-call rule counts, and a session that ran past midnight stays with its start day.
- **Status does not matter.** Seven days of all records is about 105 GiB, so there is no reason to treat `done` records differently.

**Rule.** Keep the directories for today (UTC) and the 13 days before it (`keep_days = 14`). Delete records in older directories. Never delete anything in today's directory or the six before it (`PROTECTED_DAYS = 7`, a constant, not a setting). Going from 7 to 14 days costs about 100 GiB and protects against date bugs and clock errors. It still leaves about 500 GiB of room below 70%, which is more than a month of normal intake.

**Burst step-down.** If projected usage after the age pass is still ≥ 70%, the plan adds the next-oldest directories one at a time. It stops when projected usage is below 65% or when the next directory is protected. If the protected seven alone are ≥ 70% (about 7× normal intake), the job deletes nothing more and pages on-call.

## 2. When and how it runs

**Units.** `run-retention.service` and `run-retention.timer` on `disp-1`. They run as the user `brindle` and log to the journal, like the other maintenance jobs.
- Schedule: `OnCalendar=*-*-* 01:15:00 UTC`, `Persistent=true` (a missed run catches up).
- 01:15 is after the UTC date changes and away from `queue-vacuum` (02:30) and `cert-check` (07:00).
- Once a day is enough, because a day adds only about 1.5%.

**Command line.** `run-retention --dry-run | --delete [--max-dirs N]`.
- Exactly one of `--dry-run` and `--delete` is required; a call with neither exits with an error.
- There are no flags to change the root directory or the clock.

**Config.** Add this section to `/etc/brindle/brindle.toml`. The root comes from `[paths] run_store`.

```toml
[retention]
keep_days = 14            # job refuses a value below 7
target_percent = 70
stepdown_to_percent = 65
warn_percent = 60
max_dirs_per_run = 3
```

**One run, step by step:**

1. **Lock.** Take a non-blocking `flock` on `/run/lock/run-retention.lock`. If another run holds it, exit.
2. **Pre-flight.** Run the checks in §3. If any fails, exit non-zero, warn on-call and delete nothing.
3. **Plan.**
   - Set `today = datetime.now(timezone.utc).date()`.
   - The eligible directories are those dated ≤ `today − keep_days`.
   - Go through them oldest first. For each record, run the checks in §3, then add `(path, st_blocks×512)` to the plan or the path to the skip list.
   - Projected usage = `statvfs` used bytes minus the planned bytes. Apply the step-down if it is still ≥ 70%.
4. **Act.**
   - With `--dry-run`, print `WOULD DELETE <path> <bytes>` for each planned file.
   - With `--delete`, first check again that the directory date is ≤ `today − 7`, then `unlink` the file and print `DELETED <path> <bytes>`.
   - When a directory's planned files are done, `rmdir` it if it is empty. Never delete recursively.
   - Any I/O error other than "file already gone" stops the run.
5. **Summary and alerts.** Log directories, files, GiB freed (or that would be freed), usage before and after, and the skip list.
   - Warn on-call, through the same channel `cert-check` uses, if anything was skipped or usage is ≥ 60%.
   - Page on-call if usage is ≥ 70%.

Dry run and real run use the same planning code; only step 4 is different.

## 3. How it avoids deleting the wrong thing

The run store has **no backup**, so every deletion is final.

1. **Right place.**
   - Resolve the root with `realpath`. It must equal `/srv/brindle/runs` and be a mount point.
   - Look only at direct children named `YYYY-MM-DD` that parse as dates and are real directories (`lstat`; never follow symlinks).
   - Inside those, look only at regular files named `s-<hex>.jsonl`.
   - Leave and report everything else (`lost+found`, temp files, symlinks, subdirectories). The store is documented to hold only run records, so anything else is a surprise.
2. **Right age.**
   - Use only UTC directory names.
   - The protected seven are checked twice: at planning and again just before each unlink.
   - Refuse `keep_days < 7`.
3. **Sane clock.**
   - The newest date directory must fall between `today − 3` and `today`; otherwise refuse. At about 400 sessions a day, a directory should always be that recent.
   - This catches a clock that has jumped ahead. A jump of up to 3 days still keeps at least 11 days, well outside the protected seven.
4. **Finished sessions only.**
   - Read the file's tail; records can be up to 2 GiB, so never read the whole file.
   - The last line must be JSON with `ended_at` and a `status` of `done`, `failed` or `killed`.
   - Otherwise skip the file and report it: the session may still be running, or the dispatcher may not yet have written its end line (and therefore not yet copied its billing counts).
5. **Limited deletion per run.**
   - Normally a run deletes one directory, or two after a missed day.
   - If more than `max_dirs_per_run` (3) directories are eligible, refuse unless a person passed `--max-dirs N` on the command line. The timer never passes it.
   - Step-down can add at most the 7 directories between the protected seven and `keep_days`.
6. **Least privilege.** Run as `brindle`, not root. The job needs no access to `dispatcher.db` or the usage DB.

## 4. Testing before it is enabled

**a. Unit tests.** Test the planning function directly, passing it the root, `today` and the config.
- **Cutoffs:** with today 2026-10-08, it deletes `2026-09-24` and older and keeps `2026-09-25` onward. Also cover month and year boundaries (2026-12-31 → 2027-01-01), and check that `keep_days = 6` is refused.
- **UTC:** run under `TZ=Pacific/Kiritimati` and `TZ=Pacific/Pago_Pago`, at hours where the local date differs from the UTC date. The plan must be the same.
- **Names:** `lost+found`, `2026-13-01`, `2026-9-1`, a symlinked directory, a symlinked file, `s-….jsonl.tmp` and a nested directory. None may be planned for deletion, and all must be reported.
- **End lines:** missing, truncated, not JSON, unknown status, and a 2 GiB sparse file (check that only the tail is read).
- **Guards:** clock sanity (newest directory in the future, or 4 days old), the per-run cap and its `--max-dirs` override, and lock contention.
- **Step-down:** with synthetic sizes, it stops at 65% and never enters the protected seven. If the protected seven alone are ≥ 70%, it deletes nothing more and pages.
- **Dry run:** the directory listing is identical before and after, and the printed plan matches exactly what `--delete` does on an identical copy.

**b. Integration test.** Use a throwaway VM or container with its own `brindle.toml` and a small loop-mounted volume at `/srv/brindle/runs`, filled with sparse records in every date directory from 2026-03-02 on. Set the clock with `faketime`. Run the real command in both modes over several simulated days, including a two-day gap (it should catch up) and a forward clock jump (it should refuse).

**c. Dry run on `disp-1`.** Policy 2026-04-14 requires at least one day. Install the timer with `--dry-run`, run it once by hand, then review at least one scheduled 01:15 run. A second platform engineer checks the output:
- no path in today … today−6;
- the oldest kept directory is today−13;
- every path matches the expected pattern;
- bytes per directory roughly match `du -s`;
- projected usage is about 20–22%;
- every skipped file is explained and dealt with by hand.

**d. Enabling.** Do this attended, during working hours.
1. Run `run-retention --delete --max-dirs 1`. This deletes only `2026-03-02`, which is tiny. Check the result.
2. Clear the backlog with `--delete --max-dirs 300`. That is about 200 directories and about 750–800 GiB.
3. Verify:
   - `df` shows about 20–22%;
   - the 85% disk alert clears;
   - `brindle replay run` passes;
   - on-call can open a recent `failed` record.
4. Change the timer's `ExecStart` to `--delete`.
5. For the first week, check that each run deletes exactly one directory and that usage stays flat.
