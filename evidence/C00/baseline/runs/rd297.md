# BR-212 · Run store retention job: design

**Summary.** `run-retention` is a daily systemd job on `disp-1`. It deletes run records whose date directory is older than the 14 newest dates (today in UTC and the 13 days before). It never deletes a periodic record whose period is still running, and it never deletes a record it cannot classify with certainty. At about 15 GiB a day, the store then stays near 210 GiB, which is about 21% of the 1,024 GiB volume and far below the 70% limit of 717 GiB.

**This is urgent.** On 2026-09-30 the volume had 133 GiB free. At 14 to 15 GiB a day that runs out around 2026-10-08. Check `df` before you start. The policy of 2026-04-14 still requires at least one day of dry run before the first deletion, so install the dry-run timer as soon as the tests pass. Do not delete records by hand in the meantime. If the volume will fill before the first real run, take it to the platform team.

## 1. What the job deletes and keeps, and why

### Who reads run records

| Reader | What it reads | How long it needs records |
|---|---|---|
| On-call (`operations.md`) | Whole records of `failed` and `killed` sessions | The last 7 date directories (today in UTC plus 6). The guide says explicitly that nothing older is needed. |
| Reviewers using `brindle replay promote` | A session's record, within 48 h of its end | At most 54 h after the session starts, so at most the last 4 date directories |
| Dispatcher, for billing | The end line, once, as soon as it is written | Nothing after that. Invoices and reports use only the usage database and are never rebuilt from records. |
| **Dispatcher, trigger check (`scheduler.md`)** | **The header of every record, however old, every 15 minutes** | **A periodic record for as long as its `period` is the trigger's current period** |

These do not read the run store:
- `brindle replay run` reads only the fixtures committed to the repository, so golden sessions need no protection.
- Agent sessions only append to their own record.
- Backups: the databases are never rebuilt from records.
- Audit, legal and security: nothing requires keeping records (policy decision of 2026-06-03).

### Why periodic records need their own rule

The dispatcher decides whether a period's work is done only by looking for a header with that `trigger` and `period` in the run store. Suppose the job deletes the `access-review` record for `2026-Q4` (started 2026-10-01):
- The next trigger check finds no such header and starts a new `access-review`, which sends every team lead their access list again.
- The new record is deleted 14 days later, so this repeats all quarter.

The same thing would happen with `licence-scan` (duplicate issues), `dep-update` (duplicate pull requests), `cost-report` (a duplicate email to the budget owner) and the weekly triggers. So deleting by age alone is wrong.

### The rule

The job **keeps** a record if any of these is true:
1. **It is inside the window.** Its date directory is one of the 14 newest dates (`date >= today_utc − 13 days`) or later. On-call needs 7 of these days. The other 7 are a margin against off-by-one and clock errors and cost about 105 GiB.
2. **It is a periodic record whose period is current.** Its header has a non-empty `trigger`, and its `period` ended less than 24 h ago or has not ended. A period ends at:
   - the next ISO Monday 00:00 UTC for `YYYY-Www`;
   - the 1st of the next month for `YYYY-MM`;
   - the 1st of the next quarter for `YYYY-Qn`.
3. **It is not certain.** Any check in section 3 fails.

The job **deletes** every other record: work records outside the window, and periodic records outside the window whose period ended at least 24 h ago. Status (`failed` or `killed`), golden status, size and team make no difference.

**Expected effect.**
- **First real run:** deletes roughly 750 to 800 GiB, which is everything from March to mid or late September.
- **Steady state:** about 14 × 15 = 210 GiB, plus a handful of current periodic records, so about 21%. Each daily run deletes about one date directory (about 15 GiB).
- **There is no "delete more when the disk is full" mode.** The job will not run with fewer than 7 days. If usage is still at or above 70% after a run, it warns on-call instead of deleting more.

## 2. When and how it runs

- **Unit.** `run-retention.service` and `run-retention.timer` on `disp-1`, run as user `brindle`, logging to the systemd journal like `queue-vacuum` and `cert-check`. Add the job to the maintenance-jobs table in `operations.md`.
- **Schedule.** Daily at 03:30 UTC: `OnCalendar=*-*-* 03:30:00 UTC` with `Persistent=true`, so a missed run happens at boot. Daily is enough, because one day adds about 15 GiB against about 500 GiB of headroom below 70%.
- **Command.** `run-retention [--dry-run] [--keep-days N] [--max-delete-gib G]`, with defaults `--keep-days 14` and `--max-delete-gib 50`.
- **Path.** The job reads the run store path from `[paths] run_store` in `/etc/brindle/brindle.toml`. Update the comment there, which says only the dispatcher and `promote` use it.
- **Time.** All dates and times are UTC, whatever the host's time zone.

**What one run does:**
1. Refuse `--keep-days` below 7. Compute `now` in UTC and `cutoff = today − (keep_days − 1)`.
2. **Check the clock.** The newest date directory in the store must be today or yesterday; otherwise abort, because a wrong clock would move the window.
3. Go through the date directories older than `cutoff`, oldest first. Mark every entry DELETE or KEEP(reason) using the checks in section 3.
4. **Check the invariant.** Collect the `(trigger, period)` pairs whose period has not ended, across all headers in the store. The set must be the same with and without the DELETE records. If not, abort and delete nothing.
5. **Apply the cap.** If the DELETE records total more than `--max-delete-gib`, abort, delete nothing and print the totals. After an outage of more than about 3 days, review a dry run and then run it by hand with a higher cap.
6. Unless `--dry-run` is set, unlink each DELETE file. Then `rmdir` each examined date directory that is now empty. Never delete a directory recursively.
7. **Log.** Write one line per examined file (`DELETE|KEEP path bytes kind trigger period reason`). Then write a summary: files and GiB deleted per date directory, KEEP counts by reason, and usage before and after (projected, in a dry run).
8. **Warn on-call** (the same way `cert-check` does) and exit non-zero if any of these happened:
   - the run aborted;
   - a record was kept as `no-end-line` or `recently-modified`;
   - kept records that could not be classified total more than 5 GiB;
   - usage after the run is at or above 70%.

## 3. How it avoids deleting the wrong thing

A file outside the window is DELETE only if **all** of the following hold. Otherwise it is KEEP, with the reason in brackets.
- **Name and place.** The directory name is a valid `YYYY-MM-DD` date. The entry is a regular file (not a symlink or a directory), its real path is under the run store, and its name matches `s-[0-9a-f]+\.jsonl`. Anything else is skipped and reported (`unexpected-entry`).
- **Header.** Line 1 (read up to 1 MiB) parses as JSON and its `session_id` equals the file name (`bad-header`). The dispatcher treats an unreadable header as no header. But the job's parser could disagree with the dispatcher's, so the job keeps these records.
- **Kind.** The header is one of two things:
  - `kind = "work"` with empty `trigger` and `period`;
  - `kind = "periodic"` with a non-empty `trigger` and a `period` that matches `^\d{4}-W\d{2}$`, `^\d{4}-\d{2}$` or `^\d{4}-Q[1-4]$` and ended at least 24 h ago.

  Anything else is `unknown-kind` or `current-period`.
- **End line.** The last line, read by seeking back from the end of the file (records reach 2 GiB), parses and contains `ended_at` and `status` (`no-end-line`). This shows the session has ended and its token counts were already copied.
- **Not modified.** The file's mtime is more than 24 h old, because an ended record never changes (`recently-modified`).

Further safeguards:
- the run steps above: the minimum of 7 days, the clock check, the invariant and the cap;
- deletion one file at a time, never a whole directory;
- no command-line option to override the date (tests inject the clock in code);
- no writes to `dispatcher.db`, the usage database or any repository.

**The run store is not backed up. A deleted record cannot be restored, so reviewing the dry run is the real safety gate.**

## 4. Testing before it is enabled

1. **Unit tests** (with an injected clock), at least these cases:
   - **Window edge.** With today = 2026-10-20, directory `2026-10-07` is kept and `2026-10-06` is deleted. A session that started at 23:50 on 10-06 and ran past midnight counts by 10-06.
   - **Periods.**
     - An `access-review 2026-Q4` record in `2026-10-01` is kept on 2026-11-30 and 2026-12-31, and deleted on 2027-01-02.
     - A `dep-update 2026-10` record is kept until 2026-11-02 00:00.
     - A `weekly-digest 2026-W53` record has a period end of 2027-01-04 00:00 (2026 has 53 ISO weeks).
   - **Kept odd cases:**
     - a bad header, an empty file, and a file holding only an end line;
     - no end line, a recent mtime, and a session ID that does not match the file name;
     - a symlink, a stray file, an unknown period format, and a directory dated in the future.
   - **Guards.**
     - `--keep-days 6` is refused.
     - The clock check aborts when the newest directory is 3 days old or dated in the future.
     - The cap aborts with nothing deleted.
     - The invariant aborts when a deliberate bug is planted.
2. **Integration test on a synthetic store** in a temporary directory. The store contains:
   - 60 date directories of work records (`done`, `failed`, `killed`);
   - periodic records for all six triggers over several periods, retries included;
   - the odd entries above.

   Run in real mode at 2026-10-20, 2026-12-31 23:00 and 2027-01-02, and assert the exact list of surviving files. **Scheduler check:** before and after each run, for every trigger and its current period, the answer to "is there a header with this trigger and period?" must be the same. Use the dispatcher's own check function on the test directory if it can be called; otherwise use an equivalent scan.
3. **Dry run on the real store.** Install the timer in `--dry-run` mode for at least one day, as the policy requires; two scheduled runs is better. Check that:
   - no file from the last 14 date directories is listed for deletion;
   - every current periodic record is KEEP `current-period`: Q4 `access-review` and `licence-scan`, October `dep-update` and `cost-report`, and this week's `weekly-digest` and `stale-branches`;
   - the GiB to be deleted per month match `storage_report.md` (March to August, 471 GiB, all deleted);
   - projected usage after the run is about 20 to 25%;
   - every KEEP reason other than `current-period` has been explained.
4. **First real run.** After the review, run the job once by hand as `brindle` with `--max-delete-gib 900`. Then confirm that:
   - usage is below 70% (about 21% expected) and the disk alert clears;
   - over the next day, the `sessions` table shows no periodic sessions starting other than those actually due;
   - on-call can still open a recent failed record.

   Then switch the timer to real mode with the default cap.
