# BR-212 · Run store retention job (`run-retention`): design

**Summary.** Every day just after midnight UTC, the job deletes the date directories in `/srv/brindle/runs` that are older than the seven most recent days, which are today (UTC) and the six days before it. The first run frees about 790 GiB. After that the store stays at about 10–12% of the volume, well below the 70% limit.

## 1. What the job deletes and what it keeps

**Rule.** Let `T` be today's UTC date when the job runs. The job keeps every directory `/srv/brindle/runs/<D>/` where `D ≥ T−6`. In each directory where `D ≤ T−7`, it deletes the records and then removes the empty directory. The rule is the same for every record: `work` or `periodic`; `done`, `failed` or `killed`; golden or not.

**Why seven days is enough.** These are all the readers of run records named in the materials:

| Reader | What it needs | Source |
|---|---|---|
| The session itself | Appends to its own record. A session runs for at most 6 h. | overview |
| Dispatcher | Reads the end line once, as soon as it is written. If the usage DB is down, it keeps the counts in `dispatcher.db`. After a restart it writes any missing end lines straight away. | operations, run_records |
| Reviewers and `brindle replay promote` | Within 48 h of the session's end, so at most 54 h after its start. `promote` refuses anything later. | replay_suite |
| On-call | Records of failed and killed sessions. **The on-call guide requires today's date directory and the six before it.** Anything needed for longer goes into the incident notes. This is the rule that sets the limit. | operations |

Some records look as if they must be kept longer, but they do not need to be:

- **Golden sessions.** `promote` copies the record into the Brindle repository as a fixture. `brindle replay run` reads only the fixtures, and a broken fixture is never copied again from the run store.
- **Periodic triggers.** The dispatcher decides whether a period's work is done from the `periodic_runs` table in `dispatcher.db`, not from run records. `brindle periodic retry` needs only the trigger key. So deleting the record of a quarterly `access-review` session will not make that session run again.
- **Billing and the cost report.** Both are built only from the usage database. Usage data is never rebuilt from run records, and neither database is restored from them.
- **Audit, legal, customers, security.** None of these needs run records (policy decision of 2026-06-03).

I considered deleting `done` records sooner, since nothing needs them after about 54 h. It is not needed to reach the target, and one rule based only on the date is easier to check.

**Capacity.** 70% of 1,024 GiB is 717 GiB.
- **First run:** it deletes everything from 2026-03-02 to `T−7`, about 780–790 GiB, which leaves about 100 GiB (about 10%).
- **Steady state:** at the planned 15 GiB a day, the store holds at most about 8 directories, roughly 120 GiB (about 12%), just before each run.
- **When the job cannot help:** the 7-day window alone would only exceed 70% at about 100 GiB a day for a whole week, which is about 360 records at the 2 GiB maximum size. The job cannot fix that without breaking the on-call rule, so it warns on-call instead (step 7 in section 2).

## 2. When and how it runs

**Form.** It is a new maintenance job, set up like `queue-vacuum` and `cert-check`:
- a oneshot service `run-retention.service` and a timer `run-retention.timer` on `disp-1`;
- it runs as the user `brindle` and logs to the systemd journal;
- add it to the maintenance-jobs table in `operations.md`.

**Schedule.**
- It runs daily at 01:00 UTC (`OnCalendar=*-*-* 01:00:00 UTC`).
- Set `Persistent=true`, so a run missed while the host was down happens after the next boot.
- 01:00 is after midnight, when `T−7` has just become deletable, and before `queue-vacuum` at 02:30.
- Set `Nice=10` and `IOSchedulingClass=idle`.

**Interface.**
`run-retention [--dry-run] [--keep-days N] [--max-dirs M] [--run-store PATH]`
- The defaults are `--keep-days 7`, `--max-dirs 3` and `--run-store /srv/brindle/runs`.
- The job refuses `--keep-days` below 7.
- There is no option to set "today". Tests inject the clock in the code instead.

**Steps of each run.**
1. Take an exclusive `flock` on `/run/brindle/run-retention.lock`. If the lock is already held, exit.
2. Run the pre-checks in section 3. If any of them fails, stop and exit with a non-zero code.
3. Find the candidates: top-level directories whose name matches `^\d{4}-\d{2}-\d{2}$`, parses as a real date, and is `≤ T − keep_days`. Sort them oldest first.
4. In each candidate directory, delete an entry only if it passes every per-file check in section 3. Otherwise leave it and record it as an anomaly. Delete with `unlinkat` relative to the open directory descriptor. Never use `rm -rf` and never follow links.
5. Remove the directory with `rmdir` if it is now empty.
6. Measure the volume with `statvfs`. Write one summary line to the journal: directories, files and bytes deleted, anomalies, and usage % before and after.
7. Warn on-call, through the same channel `cert-check` uses, in any of these cases: there are anomalies, the run stopped, or usage is still at or above 70% after the run. Also send an early warning at 60%.

**`--dry-run`** runs steps 1–3 and every check in step 4, but deletes nothing. It prints one line per file it would delete (path, size, and status from the end line), then the summary and the expected usage after deletion.

## 3. How it avoids deleting the wrong thing

**Pre-checks.** If any of these fails, the whole run stops and nothing is deleted.
- **Right path:** `--run-store` resolves to `/srv/brindle/runs` and is a mount point (on a different device from its parent). A missing mount or a wrong path therefore deletes nothing.
- **Clock check:**
  - The system clock is NTP-synchronised (`timedatectl show -p NTPSynchronized --value` returns `yes`).
  - No date directory is later than `T`.
  - The newest date directory is no older than `T−3`. About 400 sessions start each day, so three empty days most likely mean a bad clock.
- **Cap:** if more than `--max-dirs` directories are candidates, stop. Normally one directory is a candidate, or two after a missed run. The cap stops a date bug or a jumped clock from deleting many days.

**Per-file checks.** A file that fails any check is left in place and reported as an anomaly.
- It is a regular file (not a link or a sub-directory), on the run store's device, and its name matches `^s-[0-9a-f]+\.jsonl$`.
- Its last non-empty line is valid JSON with `ended_at` and a `status` of `done`, `failed` or `killed`. Read this line by seeking from the end of the file, because records reach 2 GiB. A record without an end line means the dispatcher never wrote one, so its token counts may never have reached billing, and on-call must look at it.
- It was last modified more than 3 days ago. A record in directory `T−7` stopped changing by 06:00 on `T−6` at the latest, so a newer change means something unexpected is happening.

**What is never at risk.**
- The directories `T−6` to `T` are never candidates, whatever they contain.
- Unknown entries at the top level of the store are left alone and reported.
- The job never opens `dispatcher.db`, the usage database or the Brindle repository and its fixtures.

## 4. Testing before it is enabled

1. **Unit tests.**
   - The keep/delete set for a given `T`, including across month and year ends. For example, `T = 2027-01-03` keeps `2026-12-28` to `2027-01-03`.
   - `--keep-days 6` is refused.
   - Names that do not parse as dates (`2026-02-30`, `tmp`) are left alone.
   - The end-line parser handles: a valid end line, no final newline, a truncated last line, an empty file, a file with only the header, and a 2 GiB sparse file. The 2 GiB file must take milliseconds, not a full read.
2. **Integration test on a throwaway loopback volume** mounted as a fake run store. Fill it with 40 date directories around an injected `T`, plus:
   - a directory dated in the future;
   - a link to a file outside the store;
   - a sub-directory and a stray file that is not a record;
   - a record without an end line;
   - a recently modified record in an old directory.

   Check that:
   - exactly the expected files are deleted;
   - the anomalies are reported and their directories remain;
   - the cap, clock and mount checks stop the run without deleting anything, including when the volume is unmounted;
   - a second run deletes nothing.
3. **Dry run on `disp-1`.** Policy (2026-04-14) requires at least one day; run it for three days to see the day-to-day change. Use the timer with `--dry-run --max-dirs 300`, since about 220 directories exist. Check each day that:
   - the list is exactly the directories `≤ T−7`;
   - its byte total matches `du` on those directories;
   - the expected usage is below 70%;
   - every anomaly is explained;
   - the list moves on by exactly one directory a day.
4. **Announce it.** Tell on-call and the reviewers in the four teams that records older than seven days will be deleted. Anything they want from them goes into the incident notes now.
5. **Backlog run.** On the morning after the last dry run, run the job once by hand without `--dry-run` and with `--max-dirs 300`. Compare its journal output with that dry run's list. Confirm with `df` that usage is about 10% and that the 85% disk alert has cleared.
6. **Enable the timer** without `--dry-run`, with the default `--max-dirs 3`. For one week, check the daily summary: one directory deleted per day, and usage around 10–12%. Run `brindle replay run` once to confirm it still passes. It does not read the run store, so this only confirms that nothing else was touched.
