# BR-212: Retention job for the run store (design)

**Summary.** Every night the job deletes the records of *work* sessions whose date directory falls outside the on-call window. That window is today (UTC) and the six days before it. The job never deletes the record of a *periodic* session. Once the backlog is gone, the store holds about 7 × 15 GiB ≈ 105 GiB, roughly 11% of the 1,024 GiB volume and far below the 70% limit (716.8 GiB).

**Urgency.** The storage report shows 891 GiB used on 2026-09-30, growing by about 15 GiB a day, so the volume is full around 2026-10-09. Check `df` before you start. The rollout in section 4 needs at least two days, because the policy requires one day of dry run.

## Who reads run records (the basis for every rule)

| Reader | What it needs | Source |
|---|---|---|
| On-call engineer | every record in today's date directory and the six before it (UTC, by start day) | operations.md |
| Reviewers and `brindle replay promote` | a record for up to 48 h after its session ends | replay_suite.md |
| Dispatcher, for billing | the end line, read once when it is written | operations.md |
| Dispatcher, for periodic triggers | the header of each trigger's current-period record, in every directory however old. If that header is missing, the trigger starts the session again. | scheduler.md |

Nothing else reads run records:
- The replay suite reads only the fixtures in the repository.
- Usage data and the dispatcher database are never rebuilt from records.
- Sessions read nothing from the run store.
- No audit, legal or security rule requires keeping them (policy, 2026-06-03).

The run store has no backup, so every deletion is permanent.

## 1. What the job deletes and what it keeps

A record is **deleted only if all four of these hold**:

1. Its path is `<run_store>/<YYYY-MM-DD>/s-<8 hex>.jsonl` and it is a regular file, not a symlink.
2. Its directory date is before *today − 6* (UTC), and the directory is not one of the 7 newest date directories in the store.
3. Line 1 reads as a header in which:
   - `session_id` matches the file name,
   - `kind` is `work`,
   - `trigger` and `period` are empty,
   - the date of `started_at` (UTC) matches the directory.
4. The last line reads as an end line with `status` set to `done`, `failed` or `killed`, and its `ended_at` is more than 48 h ago.

**Everything else is kept:**

- **All periodic records, permanently.** A record counts as periodic if `kind` is `periodic`, or if `trigger` or `period` is not empty.
  - The dispatcher uses these headers as its only proof that a period's work is done. If the current period's record is deleted, the trigger starts again within 15 minutes:
    - account lists are sent to every team lead again,
    - dependency PRs are duplicated,
    - a second cost report email goes out,
    - licence issues are opened twice,
    - the digest is posted twice.
  - Example: the 2026-Q4 `access-review` and the 2026-10 `dep-update` records are due on 2026-10-01 and so sit in `2026-10-01/`. A plain 7-day rule would delete them on 2026-10-08, and both tasks would run again.
  - Deleting only records of past periods would be safe in principle. It would mean copying the dispatcher's week, month and quarter arithmetic (2026 has an ISO week 53), and one bug there would rerun these tasks.
  - Keeping every periodic record costs about a dozen records a month, roughly 0.5 GiB.
- **The window:** today's directory and the six before it, as the on-call rule requires. Sessions last at most 6 h, so the window also covers the 48 h in which a record can be reviewed or promoted.
- **Anything the job cannot classify.** This covers:
  - an unreadable or non-JSON header,
  - a missing end line (billing may not have copied that session's token counts yet),
  - a header that does not match its path,
  - unexpected files or directories.

  The job keeps these and lists them in its report for a person to look at.

**Why 7 days.** It is less than that would break the on-call rule. Nothing documented needs more, and anything that has to last longer goes into incident notes.

**Retention is by age, not by disk usage.** Deleting "until usage is below 70%" could eventually reach into the window.

**Expected effect.** The first run frees about 780 GiB, plus whatever has been added since 2026-09-30. After that, each run deletes about one directory, roughly 15 GiB.

## 2. When and how it runs

- **Form:** a new maintenance job called `run-retention`. It is a systemd service and timer on `disp-1`, runs as the user `brindle` and logs to the journal, like `queue-vacuum` and `cert-check`.
- **Schedule:**
  - Daily at 01:15 UTC (`OnCalendar=*-*-* 01:15:00 UTC`), with `Persistent=true` so a missed run happens at boot.
  - At that time it is already the new day in UTC, and the run avoids `queue-vacuum` (02:30) and every trigger's due time.
  - Set `Nice=19` and `IOSchedulingClass=idle`.
- **Configuration:** read `paths.run_store` from `/etc/brindle/brindle.toml` and add:
  ```toml
  [retention]
  keep_days = 7         # the code refuses any value below 7
  max_delete_gib = 50   # per run, about 3 days of records
  warn_percent = 60
  ```
  Update the comment on `run_store`, which says only the dispatcher and `promote` use it.
- **Command line:** `run-retention [--dry-run] [--max-delete-gib N]`.
- **Steps:**
  1. **Preflight checks.** If any of these fails, the job stops and deletes nothing:
     - the run store exists and is a mount point,
     - the configuration is valid,
     - the clock looks right: the newest date directory is today or yesterday.
  2. **List the date directories** and mark the kept ones (the window and the 7 newest).
  3. **Classify each file in older directories.** Read only its first line (up to 1 MiB) and its last line (from the last 64 KiB). Never read whole records; some reach 2 GiB.
  4. **Build the plan,** oldest first.
  5. **Delete each planned record:**
     - Run `lstat` on it again and skip it if its size or mtime has changed.
     - Delete it with `unlink`.
     - Stop when the cap is reached.

     Never truncate, rewrite, move or compress a record: the dispatcher treats a half-written header as missing. Never delete recursively.
  6. **Remove empty directories.** Run `rmdir` on a date directory only once it is empty.
- **Report in the journal:**
  - one line per deleted record: path, bytes, status, `started_at`, `ended_at`;
  - one warning line per anomaly kept, with the reason;
  - a summary: records and GiB deleted, kept counts by reason (window, periodic, anomaly), total size of periodic records, and volume use before and after.
- **Exit status and alerts.** The job exits non-zero and warns on-call (by the same route `cert-check` uses) when:
  - a preflight check fails,
  - the cap is reached,
  - usage after the run is at or above `warn_percent`. The job cannot delete inside the window, so above that level a person has to act before usage reaches 70%.

## 3. How it avoids deleting the wrong thing

- **Delete only what is fully known.** A record is deleted only when every condition in section 1 is confirmed. Any doubt means it is kept.
- **Age is checked three ways:** the directory name, the header's `started_at` and the end line's `ended_at`. The "7 newest directories" rule protects recent records even if the clock is wrong.
- **Periodic records are recognised from three header fields,** so one with a wrong `kind` is still kept.
- **Records without an end line are never touched.** That covers sessions still running and sessions billing has not processed.
- **Only regular files inside the run store are touched.** They must match the name pattern and be on the run store's volume, and symlinks are never followed.
- **The cap limits the damage of any bug** to about 3 days of records. The one-off backlog run raises it by hand.
- **The dispatcher may list a record just before the job deletes it.** That can only happen to a work record, which the dispatcher already treats as "no periodic work done", so the race is harmless.
- **`--dry-run` shows exactly what a real run would do** (policy, 2026-04-14). It runs the same code up to the `unlink` call and prints the plan.

## 4. Testing before the job is enabled

**A. Automated tests.** Build a temporary run store with a fixed "now":

| Case | Expected result |
|---|---|
| Work record that is done, failed or killed, in *today − 7* | deleted |
| Work record in *today − 6*; also a session that started at 23:59 and ended the next day | kept |
| Periodic records in old directories, for current and past periods of each format (`2026-W41`, `2026-10`, `2026-Q4`) | kept |
| `kind` = `work` with a non-empty `trigger` | kept, reported as an anomaly |
| No end line; empty file; non-JSON header; header id not equal to the file name; `started_at` not on the directory's date | kept, reported as an anomaly |
| Symlink, subdirectory, `notes.txt`, a directory named `2026-13-40/` | not touched |
| Sparse 2 GiB record | classified by reading only its first and last lines |
| Plan bigger than the cap | oldest deleted up to the cap, exit with a warning |
| Clock 30 days ahead; run store not a mount point | job stops, nothing deleted |
| `--dry-run` | file tree unchanged (checksums before and after), and the printed plan matches what a real run deletes |
| Directory left with only a periodic record | directory not removed |

**B. Dry run on `disp-1`, for at least one day (policy).** Install the timer with `--dry-run` and also run it once by hand. In the output, check that:
- no planned path is in the 7 newest directories;
- the plan contains no periodic records;
- the number of periodic records kept matches a separate count of periodic headers (made by a short script that reads line 1 of every file);
- the current-period records of all six triggers are listed as kept;
- the planned GiB roughly equals store size minus window minus periodic records;
- every anomaly has an explanation.

**C. First real run, by hand and supervised.**
- **When:** at least 24 h after the first dry run, on a working day. Avoid Monday morning and the 1st or 2nd of the month.
- **Command:** `run-retention --max-delete-gib 1000`.
- **Afterwards, check:**
  - `df` shows about 10–12% used;
  - over the next hour (four trigger checks), no new periodic session appears in the run store or in the `sessions` table;
  - on-call can still open a failed record from six days ago.

**D. Switch the timer to real runs.** For the first week, check each day that the run deleted about one directory, raised no warnings and did not cause any extra periodic sessions.

Finally, update `run_records.md` and the storage report, which both say that no record has ever been deleted.
