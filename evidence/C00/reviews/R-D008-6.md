**B-1 (blocking): a write whose guarded path comes from data, not from the command line.** B5 inspects only the paths the command names. Several writers take a directory that is an *ancestor* of a guarded location, and the guarded path inside it comes from the source's contents. All of the following were **allowed** with ROOT as the live tree:
- a recursive copy of a directory named `.claude` or `.git` into the tree root
- `cp -a src/. <root>`
- archive extraction with `-C <root>`, or with cwd at the root (`tar`, `cpio`, `unzip -d <root>`)
- `patch -d <root>`, or `patch -p1 < file` with cwd at the root
- `git apply --unsafe-paths --directory=<root>` run from another directory

Reproduced end to end in a disposable copy of the clone. The guard returned `allow`, and the one command then ran. It replaced `.claude/hooks/tool_allowlist.py` with a two-line no-op and planted an executable `.git/hooks/post-checkout`. The archive route did the same. Minimal example: `cp -r /scratch/x/.claude /home/user/devos/`.

`mv` of the same source is denied, but only incidentally: `mv` is checked as a removal, so the ancestor test fires. `cp`, `tar`, `unzip`, `patch` and `cpio` get no ancestor test.

This is plain shell, and it is plausible as an honest mistake: "sync the reviewed `.claude/` from my scratch clone" is exactly the shortcut a builder might take. It is also plausible as an injected instruction. So it lies inside the §9 threat model, not in its residual.

**B-2 (blocking): the merge gate's code is unguarded.** `merge_checks` runs `ROOT/tools/check_records.py`. The `Write` tool on that live file is allowed (rule T1, "outside the guarded paths"), and so is `sed -i` on it. An edit there, accidental or injected, silently changes what M7 checks for every later merge from this session. §9 presents M7 as the replacement for the classifier's "merge without review" rule, and that claim rests on a file any tool may change. Suggested fix (cheap, not lexical): have the gate run the checker from `git show origin/main:tools/check_records.py` (or HEAD's blob), not from the working-tree file. Alternatively, add the gate's files to the guarded roots.

## Assessment of the lexical approach

B5 now keys on a fixed set of locations, which is the right inversion for *named* targets. B-1 shows that the set of writers that *derive* their targets from data is open again: copy trees, archivers, patchers, `git apply`.

One cheap partial hardening is available: deny a non-reader that names an *ancestor* of a guarded location, as `mv` already is. It would not close the cwd-relative forms (`patch -p1 < f` or `tar xf a.tar` run from the root). Closing those lexically means denying every non-reader whose cwd is the live root, which over-blocks normal work there.

So the barrier cannot be made sufficient by more lexical rules, even for the accident and injection threat model. That finding is blocking. I recommend the posture already accepted in D-003 and §9: the guard is best-effort, and the environment plus git history are the barrier. State that plainly in §9 for live-guard writes, with B-1's category named. Add the ancestor test as cheap hardening. Fix B-2 structurally, as above, so that M7 does not depend on an unprotected file.

One more structural option, at the producer's discretion: a drift check that fails closed whenever the live `.claude/` or `.git/hooks` differs from `HEAD`. It is not lexical, so it also catches interpreter writes. It cannot protect against a replacement of the hook file itself.
