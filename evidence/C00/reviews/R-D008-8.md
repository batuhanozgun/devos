**B8-1 (blocking): `tools/` is guarded only by the writer lists, not by the catch-all.**
- **Location:** `.claude/hooks/tool_allowlist.py`, `write_guarded` and its callers.
- **Problem:** The docstring says the "non-reader names a guarded path" check deliberately uses `guarded_zone`, so that the gate stays runnable. As a result, a write to `tools/` is denied only when the program is in a known write-destination list. For `.claude/`, the catch-all denies every one of the programs below. For `tools/`, all of these are allowed:
  - download-to-file and decode-to-file options;
  - `patch` with a named target;
  - archive extraction with `-C tools`, and `cpio -D tools`;
  - in-place compressors;
  - `unlink`, `shred` and `ed`;
  - `sort -o`, `uniq`, `split` and `mktemp` on a path under `tools/`;
  - a glob on the directory component itself (`sed -i … too*/r*.py`; the same shape on `.cl*/` is denied).
- **Example:** fetching a file to `tools/yaml.py` with a download tool's output option is allowed. That recreates the import-shadow route that B7-1 named.
- **Effect:** L-104 says the guard covers "the whole live `tools/` directory (glob, ancestor and new files such as `tools/yaml.py` included)". §9 says the directory "can be run but not written". Both over-claim.
- **Fix (either is enough):**
  - (a) Use `write_guarded` in the catch-all, and exempt only an interpreter or `bash` whose script argument is under `tools/`, plus the existing readers.
  - (b) The structural fix R-D008-7 offered: `merge_checks` runs the gate from a fresh export of `origin/main` with `python3 -B -P`.
  - Add planted cases for a download tool, archive extraction into `tools/`, and the `too*/` glob.

**Not blocking (stated residual):** `perl -pi` and `python3 -m py_compile` on `tools/` are allowed. They are interpreters, which §9 names. `py_compile` rewrites the bytecode from the same source, which the gate's own run does anyway.

**B8-2 (blocking, new named-target route): a git output-file option writes into the live `.claude/` and `.git/hooks/`.**
- **Location:** the git handling in `command_checks`. B4 covers live-tree-changing subcommands; the B5 path check does not see git's output-file options.
- **Problem:** Read-type git subcommands that accept an output-file option are allowed, with the destination in a guarded zone or in `tools/`. Those subcommands are `show`, `log` and `diff` (`--output=`), and `archive` and `format-patch` (`-o`). I reproduced it in a disposable repository: the `show` form writes the exact committed content of a named blob to the named file.
- **Example:** `git show <rev>:<path> --output=.claude/hooks/<file>` is allowed. It replaces a live guard file with any committed content. The same holds for a file under `.git/hooks/`.
- **Why blocking:** This is a named target on the command line and a plain git command. It is not data-derived and not an interpreter, and an injected instruction could plausibly use it. It predates this fix; no earlier round reported it.
- **Fix:** Treat git's `--output[=]` and the `-o`/`--output-directory` of `archive`, `format-patch` and `bundle` as write destinations, checked with `write_guarded`. Add planted cases, including the `-C <scratch>` form with an absolute live destination.
