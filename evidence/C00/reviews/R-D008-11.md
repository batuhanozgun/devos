All three fixes are small.

## Findings

**B11-1 (blocking; criterion 2): a command substitution becomes a plain placeholder word, so an unresolvable path looks resolved.**
- **Location:** `.claude/hooks/tool_allowlist.py`, `substitutions()`, which writes `out.append("_sub_")` for `$(…)`, `` `…` ``, `<(…)` and `>(…)`. The result is consumed by `resolve_dir`/`target_path`, and so by `git_checks` (`base`, `out_guarded`) and every other write check.
- **Problem:** `resolve_dir` and `target_path` return `None` (unresolvable) only for text that contains `$` or a backtick. After the substitution pass, the text holds the literal `_sub_`, so `-C $(pwd)/tools` resolves to `<root>/_sub_/tools`. That path is in no guarded zone, so the call is allowed. The `-C`/cwd test of the new coarse rule ("a -C directory the guard cannot resolve is denied") never fires for this spelling.
- **Allowed, all confirmed in this review:**
  - `git -C $(pwd)/tools init`, `` git -C `pwd`/tools init ``, `git -C "$(pwd)/tools" clone <src>`, `git -C $(pwd)/.claude clone <src>`;
  - `cd $(pwd)/tools && git init`, `cd $(git rev-parse --show-toplevel)/tools && git init x`;
  - `git clone <src> $(pwd)/tools/x`, `git worktree add $(pwd)/tools/wt`;
  - `git archive -o $(pwd)/tools/x.tar HEAD` and `-o$(pwd)/…`, `git format-patch --output-directory=$(pwd)/tools`.
- **Most realistic case:** `git -C "$(git rev-parse --show-toplevel)" clone <src> tools/x`. Here `-C` is the live root, and the relative destination is resolved against the fake `<root>/_sub_`. Run from inside the tree, this is an ordinary, honest way to write a git command.
- **Confirmed in a disposable repository:** `git -C $(pwd)/tools init` creates `tools/.git`.
- **Pre-existing, but criterion 2 requires it:** the same placeholder also lets redirections and copies through (`echo x > $(pwd)/.claude/settings.json`, `cp <f> $(pwd)/tools/check_records.py`). That predates this round. Criterion 2 explicitly requires the unresolvable-directory denial.
- **Fix:**
  - Make the placeholder unresolvable, for example `$_sub_` or any token containing `$`, so that `resolve_dir`/`target_path` return `None`. The tree-writers' `e is None` denial then applies.
  - Check that nothing relies on `_sub_` being a plain word. The G0 command-name check would also start firing on `$(…)` used as a command name, which is consistent with §9.
  - Add planted cases: `git -C $(pwd)/tools init`, `` git -C `pwd`/.claude clone <src> ``, `git -C "$(git rev-parse --show-toplevel)" clone <src> tools/x`, and `cd $(pwd)/tools && git init`. Add allowed near misses: `git -C $(mktemp -d) init` is currently allowed and would become denied, so decide and record that over-denial.

**B11-2 (blocking under criterion 4, honesty; pre-existing, not introduced by `1bc2d81`): a write target that starts with a variable passes every write check.**
- **Location:** every write call site follows the pattern `p = target_path(d, x); z = p and write_guarded(p)`: redirections in `shell_checks`, `written` in `command_checks`, the catch-all, and `out_guarded` in `git_checks`. `target_path` returns `None` for a `$`, and `None` is treated as "not guarded".
- **Problem:** a variable-prefixed path that names a guarded location is allowed. Allowed examples:
  - `echo x > "$PWD/.claude/settings.json"` and `echo x > $PWD/tools/x`;
  - `cp /tmp/a "$PWD/tools/check_records.py"`;
  - `git clone <src> "$PWD/tools/x"`;
  - `git archive -o "$PWD/tools/x.tar" HEAD`.

  The path is on the command line, so this is neither data-derived nor an interpreter's own language. `"$PWD/…"` and `"$HOME/…"` are common honest spellings, and injected text can use them just as easily. Only a tree-writer's `-C` treats a variable as unresolvable (`git -C "$PWD/tools" init` is denied). That makes the gap inconsistent as well as open.
- **Why it blocks here:** criterion 4 asks that L-107 and §9 claim no more than the code checks. L-107 says a guarded path that appears as a positional, `--opt=value` or `-o<path>` token is denied. §9 says the guard "blocks every write that names a guarded location (by redirection or by a non-reader naming it)". Both are false for these spellings. Earlier rounds did not raise this. I did not re-open the accepted residual; this is not in it.
- **Fix (either):**
  - **(a) Code.** When a write target cannot be resolved, deny it if its literal text after the unresolvable prefix contains a guarded component: `.claude`, `.git`, `tools` as a path component, `.config/git`, or a protected file name. Alternatively, resolve `$PWD`, `$HOME` and `$(pwd)` and deny the remaining unresolvable writes that carry such a component. Add planted cases.
  - **(b) Wording.** State in §9 and L-107 that a write target written with a variable or substitution is not checked, and list it as a residual. Option (a) is cheap and fits the honest-mistake threat model better.

**B11-3 (blocking, small; criterion 3 intent and honesty): the shared `SAFE_INTERP_OPTS` treats `-s` as harmless for shells, where it makes standard input the program.**
- **Location:** `SAFE_INTERP_OPTS` (it includes `-s`) and the `exempt` loop in `command_checks`. `INTERPRETERS` includes `bash`, `sh`, `zsh`, `dash` and `ksh`. Only `-c` routes shells into the `SHELLS` branch.
- **Problem:**
  - For python, `-s` means no user site-packages. For bash/sh/zsh/dash/ksh, `-s` means "read the commands from standard input", and the next words become `$1…`. So in `bash -s tools/check_records.py < payload` (or `<<<`, or a pipe), the "script" the guard exempts is really an argument handed to a stdin program. That program can write it, for example with `cp … "$1"`.
  - This is exactly the bare-`-` case that criterion 3 names as ending the exemption (`python3 - tools/x` is denied), in shell spelling.
  - **Confirmed in a disposable directory:** `echo 'echo pwned > "$1"' | bash -s tools/f` writes `tools/f`. The guard allows `bash -s tools/check_records.py < /tmp/payload.sh`, `echo "cp /tmp/x \"\$1\"" | bash -s tools/check_records.py` and `sh -s tools/check_records.py <<< …`.
  - The comment above `SAFE_INTERP_OPTS` and L-107 say a generous list "can never open a hole". That is false, because one list is applied across interpreters whose flags mean different things.
  - Other listed flags were checked per interpreter, and I found no further write route:
    - `-E` (perl: inline code) and `-I` (perl/ruby: include directory) only over-deny or exempt a non-written include path;
    - `perl -x`/`-s`/`-n`/`-d` and `bash -x`/`-v` still run the named file as the program.
- **Fix:** make the allow list per interpreter: python flags for `python*`, and for the shells only `-x`, `-v`, `-e`, `-u`, `-E` and similar, never `-s` or `-i`. Or, minimally, drop `-s` for `SHELLS`/`ksh`. Correct the comment and L-107. Add planted cases `bash -s tools/<f>` and `sh -s tools/<f>`, both deny.

**Minor (not blocking):**
- **m-1 · Over-denials from the coarse rule.** `git archive -o /tmp/x.tar HEAD tools/` and `git format-patch HEAD~1 -- tools/` in the live tree are denied, because a pathspec is checked as a destination. So is a branch or remote named like a guarded path (`git worktree add -b tools/x /tmp/wt`, `git clone -b tools …`), and so is `format-patch -O<orderfile>`. L-107 discloses the branch and pathspec cases. Archiving `tools/` from the live tree to `/tmp` could plausibly be wanted. A scratch clone is the workaround.
- **m-2 · Interpreter over-denials.** `bash -e tools/x.sh`, a cluster such as `python3 -Bu …`, and `python3 -- tools/…` are denied. These are safe failures. Cluster support or `--` could be added if they are ever needed.
- **m-3 · The test count depends on checkout state.** 539 holds on a pushed-branch checkout. A detached checkout prints 536 with an info line. This is not a defect, but L-107 could say which state the count was taken in.

## Conditions to pass

1. **B11-1:** an unresolvable substitution in a tree-writer's `-C`/`cd` directory or path is denied. Make the placeholder carry `$`, and add planted cases.
2. **B11-2:** variable- or substitution-prefixed write targets that name a guarded component are denied. If they are left open, §9 and L-107 must state them as a residual and drop the "any command-line token" claim.
3. **B11-3:** `-s` (and `-i`) no longer keep the exemption for shells. Correct the "can never open a hole" wording, and add planted cases.

A re-review can be scoped to these three items and their planted cases.
