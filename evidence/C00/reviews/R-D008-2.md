## Blocking findings

### N-1 · A git alias bypasses the push check (B3) and the live-tree revision ban (B4)

- **Location:** `.claude/hooks/tool_allowlist.py`. `GIT_RISKY_KEYS` (no `alias.`). `git_checks()` decides by the literal subcommand name (`sub == "push"`, `sub in LIVE_BANNED_GIT`). `config_checks()` lets `alias.*` writes through outside the live tree.
- **Problem:** git expands `alias.<name>` before it runs the subcommand, and the guard does not. With `alias.p=push`, the subcommand the guard sees is `p`. `push_checks()` never runs, so B1, B2 and B3 are all skipped. An alias that starts with `!` runs any shell command, and the guard never sees that command. L-095 says B11 denies "keys that reroute or run programs", but `alias.` is not in the list.
- **Reproduced:**
  - Through the guard, each of these gets `allow` (B0): `git -c alias.p=push p <other repository> claude/x`; `git config alias.p push` in a scratch clone, then `git p <other repository> HEAD:claude/x`; `git -c alias.st=!sh st`.
  - With real git, `git -c alias.p=push p <bare repo> claude/x` delivered `claude/x` to the other repository.
  - In the live tree, the guard allows `git -c alias.co=checkout co origin/claude/w12-6-guard -- .claude/hooks/tool_allowlist.py`. The unaliased form of the same command is denied by B4. Real git: `git -c alias.co=checkout co HEAD~1` moved `HEAD`.
  - In any tree, the guard allows `printf '[alias]\n\tco = checkout\n' >> ~/.config/git/config`, and after it, `git co …`. `~/.config/git/config` is not a protected name.
- **Why it blocks:** one ordinary git invocation sends a branch to a host other than `devos` (B3, D-008 cost 1). The same kind of invocation swaps the hook in the live tree, which is what B4 and the working-tree rule exist to prevent. R-D008-1 B-1 treated `git -c` as outside the "lexical analysis" residual risk, and this is the same route. The §9 residual list mentions "aliases", but L-095 presents B11 as covering settings that run programs, and §9 still presents B3 and B4 as enforced.
- **Suggested fix:**
  - Deny `alias.` keys in `git -c` and in `git config` writes, as part of `GIT_RISKY_KEYS`.
  - Better, also resolve the subcommand: when `sub` is not a known git subcommand, run `git -C <e> config --get alias.<sub>` in the hook. Deny if the alias exists, or else deny unknown subcommands.
  - Add `~/.config/git/config` (and `$XDG_CONFIG_HOME/git/config`) to the protected paths, for shell writes too.
  - Planted cases: `-c alias.p=push p`; a configured alias; `-c alias.co=checkout co` in the live tree. Near miss: `git -c alias.st=status st`, which may stay allowed only if alias resolution is in place.

### N-2 · Push rerouting through config sources the address check does not see (B3/B11)

- **Location:** `push_checks()` and `strip_wrappers()`/`GIT_ENV_OVERRIDE`.
- **Problem:** `git remote get-url --push --all` runs in the hook's own environment and only for a remote **name**. Three routes escape it:
  1. **Environment the hook does not share.** `XDG_CONFIG_HOME=<dir> git push origin claude/x`. Git reads `<dir>/git/config`, which can hold `url.<other>.pushInsteadOf`, and the hook resolves the URL without it. `XDG_CONFIG_HOME` and `HOME` are not in `GIT_ENV_OVERRIDE`. Writing `<dir>/git/config` is not guarded, because only the basename `.gitconfig` is protected.
  2. **Literal URL plus `pushInsteadOf`.** When the remote contains `://` or `/`, the guard checks the literal text, but git still applies `pushInsteadOf` to it. Writing the rewrite into a scratch clone's `.git/config` with a shell redirection is allowed (see N-4), and so is writing it into `~/.config/git/config`. Then `git push https://github.com/batuhanozgun/devos claude/x` is allowed. In that case `git push origin claude/x` is correctly denied, which shows the gap is the literal-URL branch only.
  3. **`--git-dir` to a bare repository.** `git --git-dir=evil2.git push origin claude/x` sets `e` to `dirname(evil2.git)`, the current clone, because the code assumes the directory is named `.git`. The guard therefore checks the current clone's `origin` (`devos`), while git uses `evil2.git`'s `origin`. `git clone --bare . evil2.git` and a redirection appending a `[remote "origin"]` section to `evil2.git/config` are both allowed.
- **Reproduced with real git:** route 1 delivered `claude/x` to the other repository, route 2 delivered `claude/x`, and route 3 delivered `claude/y`. The guard allowed each of the three push commands on a clean test repository.
- **Severity:** blocking (criterion (d): "a push … to a remote other than `devos`").
- **Suggested fix:**
  - Run the address check as git will run it. Pass the command's own leading assignments into the hook's `git` call, or deny `HOME=`, `XDG_CONFIG_HOME=` and `GIT_*` assignments on any git command.
  - For a literal URL, resolve the rewrite with `git -C <e> ls-remote --get-url <url>`, which applies `insteadOf`. For push, also apply `pushInsteadOf`, or simply deny a literal-URL push and require a named remote.
  - Set `e` to the `--git-dir` path itself and resolve with `git --git-dir=<path>`, or deny `--git-dir` on push.
  - Add a planted case for each route.

### N-3 · B8 still misses close variants of the dumps it names

- **Location:** `command_checks()` (B8 additions) and `shell_checks()`.
- **Problem:** L-095 says B8 now denies "`export` without names or with `-p`", "`compgen -v`, `-e` and `-A`", "`declare` … with `-p`" and BSD `ps e`. Each of these variants is allowed by the guard (B0), and each printed a planted `FAKE_TOKEN` value when run under bash in a clean environment:
  - `export -n` (no names) and `export -pn`. The check tests `"-p" in rest` literally.
  - `declare -px GH_TOKEN` and `typeset -px GH_TOKEN`. Combined flags have a name, so `not names` is false, and `-px` ≠ `-p`. This prints a credential **by name**, which (d) bans as "any use of the session's credential variables".
  - `compgen -Avariable`, with the argument attached.
  - `find . -maxdepth 0 -exec env \;` and `-exec printenv GH_TOKEN \;`. `find -exec` is not unwrapped the way `xargs` is.
  - `cat /proc/self/env?ron`. The check looks for the literal word `environ`, so a glob gets past it.
  - `git -c 'alias.e=!env' e` (see N-1).
  - `ps -p <pid> e`. Only the first argument is checked for BSD `e`.
  - `s=set; $s`, and `v=GH_; eval "echo \$${v}TOKEN"`.
- **Severity:** blocking together with N-1/N-2 for the same reason as R-D008-1 B-2: §9 says "environment dumps" are denied. The first five are plain commands of the kinds the fix itself names. The last two use indirection and could fairly be placed under the lexical residual risk, if §9 said so.
- **Suggested fix:**
  - Parse combined short flags: treat `-px` as `-p` plus `-x`. Deny `declare`/`typeset` with `-p` in any combined form. Deny any `export` whose flags include `p` or `n` and that has no names.
  - Match `compgen -A*`.
  - Unwrap `find … -exec/-execdir/-ok` the way `xargs` is unwrapped.
  - Match `/proc/…/env` followed by any glob character.
  - Check every BSD-style `ps` argument.
  - Treat a command name that is a variable expansion as unknown, and deny it.
  - Name the indirect cases in §9.

### N-5 · The decision log's protection and the hash chain are overstated

- **Writes the guard still allows** (rule B0) under the default `/tmp/devos-guard`: `rm -rf /tmp/devos-*`, `rm -r /tmp/devos-gu?rd`, `find /tmp/devos-guard -delete` and `find /tmp/devos-guard -name '*.jsonl' -exec truncate -s0 {} +`. None of these is an interpreter. L-095 states that only "an interpreter can still rewrite the whole file", which understates the residue.
- **Tail truncation:** §9 and `guard_report.py` say an "edited or truncated log shows as a broken chain". A log cut at a record boundary from the end leaves a valid chain. The guard then continues numbering from the shortened file, so the cut cannot be detected. A deleted log reads as "no decision log".
- **Fix:**
  - Treat glob and `find` targets under `LOG_DIR` as guarded.
  - Reword: "edits inside the log break the chain; removing records from its end or deleting it does not show".
  - Optionally report the last `n` in the session's own log entry, so a later report can compare against it.

### N-6 · `Workflow` dynamic keys: the claim is broader than the check

- Allowed (reproduced): `const k="iso"+"lation"; const o={}; o[k]="work"+"tree"; agent("x",o)`, and `Object.fromEntries([["iso"+"lation", …]])`.
- A workflow script is a program, so this belongs with the stated lexical residual risk, and it is not a plain-command route. The wording should still say so, or the check should deny scripts that assign by `[`expression`]` or use `Object.fromEntries`/`Object.assign` on `agent` options.
- The other m-2 fixes hold, reproduced: `name` alone is denied, `resumeFromRunId` without a script is denied, a quoted `worktree`/`remote` is denied, and an unresolvable `scriptPath` is denied.
