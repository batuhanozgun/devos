**Shared facts the rows refer to** (stated once so that the rows stay short):

- **F1, cloud loading (N-005):** a probe observed that ECC, loaded as a marketplace skill or account plugin, does not reach cloud sessions (plan 5.9 leaves this to C01). Only what is copied into `devos` at a fixed version can load there. Two kinds of file are observed to load from the repository: `.claude/agents/*.md` (the installation roles run that way) and the hooks in `.claude/settings.json` (the guard runs that way). Plain files under `methods/` are read like any other file. Whether repository `.claude/skills/` load has not been verified (C01). Node 22 is present in this container.
- **F2, model pinning:** ECC agents pin `model:` to sonnet, haiku or opus. DevOS runs every session on Opus 5.5 with `model: inherit` (D-008). Adaptation would remove the pin.
- **F3, prompt-defense block:** every ECC agent carries a "Prompt Defense Baseline". Among other things, it bars outputting code, scripts or URLs unless they are validated. DevOS handles untrusted content through `CLAUDE.md` (read-only sources are data) and K-9 item 8, and the block would get in the way of producer work.
- **F4, guard and account rules:** under the guard (working order section 10), the only MCP tools allowed are GitHub, the session tools and read-only Supabase (M1–M7). The guard also denies: `gh`, `gcloud` and `claude` command lines; worktree switching; writes into Claude Code's own configuration (`~/.claude`) and into the live `.claude/`; uploads and raw network tools (T, F and B rules). `CLAUDE.md` bans connectors and any paid feature.
- **F5, Batu gives no technical approval** (K-11 item 7, PC-05, `CLAUDE.md`). Where ECC says "escalate to a human", "the human flips the done switch" or "wait for user confirmation", DevOS uses the independent verdict: a fresh-context Checker until C03, the audit environment after. Only Batu's own decisions go to him, in the Appendix E format.
- **F6, independence** (D4 item 2, Ek A 5.6, plan 8.7, K-4 item 4): two same-model subagents in one session count only as declared "same session, fresh-context subagent" independence, and the guard notes that subagents run in-process without isolation. A second reviewer with the same model, frame and rubric does not add independence. Ek A DR13-G: "Several reviewers repeating the same mistake do not automatically increase confidence."
- **F7, single live state:** DevOS's live state is only in Supabase (plan 6.6; D7 item 2, no two authoritative copies), and files count only on `main`. ECC's memory and session files under `~/.claude` would be a second copy, and a route by which old authority could come back (criterion 10).

**How a component installs.** In `scripts/lib/install-manifests.js` (`expandComponentIdsToModuleIds`), a component installs every path of its modules plus their dependencies. Nothing filters by skill. So `skill:tdd-workflow` would install all 47 items of the `workflow-quality` module, and `lang:python` would install all 70 items of `framework-language` plus `rules-core`, `agents-core`, `commands-core` and `platform-configs`. DevOS never runs the installer: N-005 says to copy at a fixed version, and the task bans running it. Here "adopt" means copying the named file or idea into `devos`, so each row judges the item the component names. For a language or framework component, the row judges the module items specific to that stack.
- Some items of `workflow-quality`, `security`, `research-apis`, `machine-learning` and `rules-core` (all of `rules/`) are named by no component in this scope. They are judged under `baseline:*` and `capability:*` in the other parts of W-C00-07.
- Some items of `framework-language` are named by no component. They can only be reached through this scope's components, so they get the "module items" rows at the end.

**Short forms used in the rows**
- **FL**: the `framework-language` module (70 skills; the manifest lists 70 paths, CHK-C00-021 F2).
- **Copy loads**: an ECC install (plugin, marketplace or `~/.claude/...`) does not reach a cloud session (N-005). The file would load once copied into `devos` at this commit, and it needs no extra runtime.
- **Model-gap test** (plan 6.12 item 4): every DevOS mechanism must say what it makes up for that the model cannot do alone. General idioms of a stack the model already writes make up for no gap that has been observed. Loading them costs context (Appendix D section 1, "Length and effect").
- **Fresh-source rule** (K-2 items 2 and 3, criterion 17): version-specific facts enter DevOS only from a dated primary source. A frozen third-party skill is a secondary source that goes stale.
- **SOUL-stack rule** (the task's instruction): guidance for a stack DevOS itself does not use can only help later SOUL product work, and SOUL's stack has not been chosen (DR02 design, stage B). The decision is "undecided" and is made when a SOUL work item chooses that stack, using the model-gap test and the fresh-source rule. It is not loaded until then.
