2. **The count of calls, and whether 20 is sound (not blocking).**

Only `printenv` is B8 (`:1054-1055`). So rule 1.2's fallback, which costs one denial plus one `tools/guard_report.py` call, happens only when a run uses `printenv`, as R1a did (#8).
   - **Chained minimum: 7 to 9 calls.**
     1. Read CONTROL.md.
     2. One Bash call: `date`, `echo` of the ID, the shallow test and `git remote get-url`.
     3. The clone, listing the probe branches and reading the CLOSING Result lines.
     4. `git fetch --unshallow` (a call of its own).
     5. `checkout -b`.
     6. Write IDLE.md.
     7. add and commit.
     8. push (a call of its own).
   - **Literal case, one command per call, R1a-style: 18 calls.**
     - Read; `date`; `printenv`, denied by B8; guard_report.

     - Shallow test; unshallow fetch; `checkout -b`; Write; add; commit; push.

   - **R1a as evidence.**
     - "15 calls before its first push" is #16's record number. `log_decision` numbers PermissionRequest records as well as PreToolUse ones (`tool_allowlist.py:2014-2024`, `2063`), so 15 is an upper bound on calls.
     - R1a's 15 also included working-run items that an idle run does not need. For example, it read the boot ID at 08:09:27Z, before its push at about 08:10Z (OPENING part A item 6).
     - The annotation's "R1a had two before it" (`ROUTINE_DESIGN.md:83`; also in L-199) is slightly off. #16 was the first push itself: one denial (#8) came before the first push attempt, and two came before the first accepted push. This is a precision slip, not a defect of the bound.

3. **There is no instruction for reaching the bound before the push (condition C2).**
   - Rule 2.4 gives a cap, "at most 20 tool calls", and an order, "push, and end" (`CONTROL.md:22`). Rule 1.8 says to push "so that what is done is on the branch if the session stops" (`CONTROL.md:14`).
   - A run at call 20 with no push yet has to choose between the cap and its only record, and no human is present.
   - Under the strict reading, the record is lost. The executor then cannot tell that run apart from no run, and the day's count for row 5 is lost (CHK-C01-038 finding 10's note at line 135).
   - Finding 2 shows this edge can be reached by a literal run. One sentence closes it, and it makes the exact number less critical.

4. **Rule 1.2 and rule 1.5 still assume a stamp or closing record that an idle run does not write (condition C1).**
   - Rule 1.2 still says "say so in the stamp" (`CONTROL.md:8`).
   - Rule 1.5's "record the denial (number and rule…)" (`CONTROL.md:11`) has no place in an idle run. Denials go to CLOSING.md item 8 (`CONTROL.md:61`), which an idle run does not write, and IDLE.md's list at `CONTROL.md:22` includes neither.
   - This is the same kind of gap as N-143's note A, closed here for rule 1.9 only (D6: "can the same failure class still arise by another route?").
   - The B8 denial on rule 1.2's path is the one denial an idle run is likely to meet.
   - The impact is low: information is lost, and no ban is broken. A general sentence in rule 2.4 (IDLE.md stands in for the stamp and the closing record) would close it.

5. **The new wording is clear for an unattended run (not blocking).**

   - The version line is accurate. Each run reads it as the file's version.
