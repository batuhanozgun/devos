4. **The wrapper, read as the shell runs it (item 2). Not blocking.**
   - After JSON-unescaping, settings.json:31 is `out=$(python3 "$CLAUDE_PROJECT_DIR/.claude/hooks/tool_allowlist.py" PermissionRequest); rc=$?; case "$rc:$out" in '0:') ;; '0:{"hookSpecificOutput": {"hookEventName": "PermissionRequest", "decision": {"behavior": "'*'}}}') printf '%s\n' "$out" ;; *) printf '%s\n' '<fixed deny>' ;; esac`.
   - `sh -n` and `bash -n` both pass. The only unquoted pattern character is the `*`. The fixed deny is valid JSON, contains no single quote, and is printed by the `printf` builtin, so it works even when PATH has no python3.
   - I ran it with fake guards under dash and bash; the two shells agreed in every case:

     | What the fake guard did | What the wrapper gave |
     |---|---|
     | PermissionRequest allow, with a trailing newline, without one, or with three | passed through, exit 0 |
     | Allow plus 1 MB on stderr | passed through (stderr is not captured) |
     | PermissionRequest deny, including a 5 MB message | passed through (0.22 s in sh, 0.58 s in bash) |
     | No output, or only a newline | pass (no output) |
     | Allow with exit 1, exit 2, or killed by SIGTERM | fixed deny |
     | A junk line or a space before the allow | fixed deny |
     | CRLF line ending | fixed deny |
     | Compact JSON, without spaces | fixed deny |
     | An allow in the PreToolUse form | fixed deny |
     | No output with exit 1 or exit 2 | fixed deny |
     | Only a space | fixed deny |

   - No input can turn a guard deny into an allow, or a guard allow into a deny:
     - the guard's allow output is constant and does not depend on the input, so it always matches;
     - its deny output either passes through verbatim or becomes the fixed deny;
     - the wrapper never writes an allow of its own.
   - Edge case: two lines, the first in the PermissionRequest form and the last ending in `}}}`, pass through verbatim (`*` spans newlines). By the hooks page ("Anything else that starts with `{` and ends with `}` but isn't valid JSON: a parse failure"), that is invalid output, which onFailure then denies. The guard prints exactly one line (tool_allowlist.py:2089-2091; its subprocesses capture their own output), so this cannot happen today.
   - Coupling: the pattern copies json.dumps' default key order and separators. A future change to the guard's output format would turn every PermissionRequest answer into the fixed deny. That fails closed, and the positive controls catch it (finding 7, break b4).
