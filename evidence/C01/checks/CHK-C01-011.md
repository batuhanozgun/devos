2. **P3 tables: met.**

3. **P3 functions: met, apart from finding 4.**
   - All seven functions are SECURITY DEFINER with `search_path = ''` and fully qualified names; pgcrypto is called as `extensions.*`.
   - There is no dynamic SQL, so there is no injection path.
   - No function returns or logs a token or a hash, except `issue_token`, which returns the new token once to the SQL editor caller.
   - `issue_token` (106) and `revoke_tokens` (137) are revoked from public, anon and authenticated, so neither can be called through the API.
   - With the header absent, the role is NULL: `whoami` returns 'unknown', and `next_item` and `complete_item` raise an error (206-208, 233-235). If `request.headers` were '' outside PostgREST, the cast would raise an error, which fails closed.
   - A caller holding only the publishable key gets 'unknown', its own header names, and errors. Nothing else.
   - Syntax, checked by reading: I expect no statement to fail. PostgreSQL's grammar accepts `FOR UPDATE SKIP LOCKED` before `LIMIT`; `RETURNING q.* INTO` a rowtype variable is valid; the alias of `json_object_keys` resolves to its column.
   Not blocking.

4. **`role_from_request` is callable by anon** (P3_probe_schema.sql:147-161, 249; EV-C01-002:133-134). Neither file revokes it. PostgreSQL grants EXECUTE to PUBLIC on creation, and Supabase's default privileges in public grant it to anon and authenticated, so `/rest/v1/rpc/probe_c01_role_from_request` is reachable. The impact is nil, since it returns only the caller's own class, as `whoami` does. But the stated property is false. Blocking (condition 1).

   Blocking (condition 2).

    Not blocking.
