2. **End status of an Agent-tool subagent (not blocking).** The code is at tools/subagent_audit.py:232-280. It reads three kinds of record from the session's transcript:
   - a user event whose `origin.kind` is task-notification;
   - a `queued_command` attachment whose `commandMode` is task-notification;
   - the meta toolUseId's own tool result, provided its status is not `async_launched`.

   The last of these decides, and only an exact `completed` counts. I checked the real session transcript by structure only:
   - It holds 60 notifications (44 user events, 16 attachments). All 60 start with `<task-notification>`, and all have status completed.
   - The tag order is task-id, tool-use-id, output-file, status, summary, result, usage. The head the tool reads (everything before summary or result) therefore holds only fields the platform sets.
   - Typed messages carry `origin.kind` "human" (13), and a message typed while the session was busy is a `queued_command` with mode "prompt" (1). Neither matches.
   - All 45 Agent calls were background calls, and every launch result was `async_launched`, which the tool excludes.
   - The program lists the statuses as `completed|failed|killed|blocked`.

   An unknown or missing status gives exit 3. A false "finished" would therefore need a record written by the platform, which PC-24 defines as the end. The `queue-operation` enqueue records are ignored, which at worst delays the read.

7. **Hand-back forms (not blocking; the open points feed C1).** The code is at subagent_audit.py:289-310. The order of preference is:
   - the first SubagentHandback call with a non-blank `message` whose result is not `success: false`;
   - else the last StructuredOutput call: its `text` if that is a non-empty string, otherwise the input as JSON;
   - else the last text.

   I read the installed program's code (/opt/claude-code/bin/claude):
   - SubagentHandback's input is `message`, and a blank message is rejected by validation.
   - Every refusal returns `{success:false, …}`: not active, already delivered, the main conversation did not accept the message, the spawning agent is no longer running.
   - The platform's own StructuredOutput reader takes `input.text` when it is a non-empty string, the same rule as the tool's.

   If both forms appear, the hand-back wins; no test covers that. If neither appears, the last text is used (case 46). What reading the code leaves unproven:
   - (a) No transcript in this session contains either call (0 of 107 agents, and 0 in the session's transcript). That a refusal is stored as `toolUseResult.success == false` is inferred from the code, not observed.
   - (b) The caller receives a sanitized text, with a backslash inserted before anything that imitates harness markup. A "flagged" hand-back is delivered under a SECURITY WARNING. `last` prints the raw input, without the warning.
   - (c) For a "withheld" hand-back, nothing is delivered, but `last` would still print its message.
   - (d) An errored call is taken as the report: an `is_error` result whose `toolUseResult` is not a dict with `success: false` (for example a hook denial). The guard allows both tools (.claude/hooks/tool_allowlist.py:97, 101), so this is unlikely here.
   - (e) A failed StructuredOutput call is not excluded.
