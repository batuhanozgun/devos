### What the documentation does not state that a design would need
1. Any setting that limits, per environment, which tools or MCP servers its sessions get. The only routes are repository files (rows 7 to 12) or managed settings, which Max does not have.
2. Whether a `~/.claude/settings.json` written by a setup script is read in an Anthropic-hosted session.
3. Whether Anthropic-hosted sessions get permission rules from the control plane. P8 says so for self-hosted sessions only; a deny still wins either way.
4. The full tool list of the session-tools server, and whether its tools stop at an environment boundary (EV-3 §2 item 1). Its reach over other sessions' transcripts is not documented; DevOS's own ledger records its use to read session events.
5. Whether a repository-file `deniedMcpServers` reaches the connectors a cloud host passes in.
6. Whether a session's git credential, as distinct from API requests, is limited to its attached repositories.
7. Whether a running session can change its own environment, or a routine's environment (EV-3 §2 item 6).
8. Whether deny rules hold in routine runs specifically. Their mode is not stated (EV-3).

## Counter-evidence and alternatives
- Rows 7 to 13 are the only documented way, on Max, to stop a session acting on the account's other sessions and routines. They load only in sessions with one repository, and a session that can write the file can change them, with edits reloading mid-session. They are the same kind of control as the guard, not separation by account.
- P8's deny rule appears on a self-hosted page, and that page names server-managed settings or the runner's user file as its place, not a repository file. The repository route is my inference.
- Alternative frame: keep what must not be read out of every repository the account can reach. Exam answers and audit authority would sit on the database side behind each environment's network secret (rows 3 and 19). That relies on per-environment settings Batu holds, not on files a session can change.

## For the decision
On Max, the per-environment settings that Batu holds outside the session are four: network level and allowlist, variables, network secrets and setup script, plus the choice of environment for each session, routine and project. They limit what an environment's sessions can reach outward. They do not limit what one session can do to the account's other sessions or routines.

That second need can only be met by a few documented deny and stricter-setting entries in each DevOS repository's `.claude/settings.json` (rows 8 to 10), with one repository per session. This is configuration of existing parts, not a new guard rule family (I). It remains the residual Batu accepted with D-020, not separation.

GitHub reach, connectors, account skills, routines and usage are account-wide.
