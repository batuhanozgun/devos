## Findings

**1. The fix**

1.1 (not blocking; holds) **Revoke by hash, hash computed outside psql.**
- Step `tokens` has a `revoke()` helper, `.github/workflows/migrate.yml:798-803`. Step `tokens_revoke` repeats the same fragment at `:922-932`.
- Both compute `hashlib.sha256(token.encode("utf-8")).hexdigest()` in Python. They pass it to psql only as the environment variable `W03_TOKEN_HASH`, read with `\getenv h`.
- They call `devos_private.revoke_env_token(t.id)` on the row `where t.token_hash = :'h'`. No revoke call's arguments or standard input held a token. In every run, the counts for token values and format strings were (0,0) in the revoke calls' args, stdin, stdout and stderr (`raw/all.txt`).

1.2 (not blocking; holds) **Python's hash equals `devos_private.token_hash`.**
- The migration computes `encode(sha256(convert_to(token,'UTF8')),'hex')` (`20261017230001_w09_identity_chain_first_part.sql:30`).
- Every token is ASCII: a marker built from two pieces plus base64url text. 32 bytes give 44 base64 characters, under PostgreSQL's 76-character line wrap, and `rtrim` and `translate` are applied (`:189-190`). Every PostgreSQL server encoding is a superset of ASCII, so `convert_to` gives the same bytes as Python's UTF-8 encoding.
- Shown by runs: 7 of 7 tokens were found and revoked with status ok on a UTF8 cluster (`head_ok`) and on a LATIN1 cluster (`headl1_ok`, `raw/latin1.txt`). After each run, 0 rows were live.

1.3 (not blocking; holds) **One call per row.**
- `token_hash` is `unique` (`20261014170201_w08_role_classes_epoch_tokens.sql:32`), so the scalar subquery returns at most one row.
- `pg_stat_user_functions.calls` for `revoke_env_token`:
  - `head_ok`: 0 → 1 after step `tokens`, → 7 after `tokens_revoke`, for 7 tokens.
  - `head_delete_row`: 6 calls for 7 statements. The `no_row` statement does not call the function, and `coalesce` gives `no_row`.

1.4 (not blocking; holds) **"Revoked" only on ok; repeats.**
- `done = r.returncode == 0 and status == "ok"` (`:803`, `:929`).
- A repeat returns `status ok, repeat true` (migration `:226-228`) and counts as revoked. That is right: the row's `revoked_at` is set. In the `head_repeat` run, an owner revoked one token first. `tokens_revoke` then exited 0 and printed "revoked" for all, and the epoch moved 2 → 8: one owner revocation plus five new ones, none from the repeat.
- `refused`, `no_row` and psql errors all count as not revoked. The L-352 note on the D6 second cause (exit 0 with a non-ok status) is right: `head_delete_row` printed "NOT revoked (psql exit 0, status no_row)".

1.5 (not blocking; holds) **A failure keeps the file, fails the step, and gives go=no.**

1.6 (not blocking; holds) **Nothing prints a token, hash or key.**

**3. Residuals**

3.1 (not blocking) **Tokens stay live after a failed revocation.**
- The premise is right. GitHub documents that `RUNNER_TEMP` is emptied at the start and end of each job. The job runs on hosted `ubuntu-24.04` (`migrate.yml:77`), a fresh VM per job. So a kept file cannot be retried by a later run.
- The residual is stated honestly, and the in-file comment (`:935-937`) says the same.
- Observed: in `head_raise_epoch`, 6 rows stayed live after the epoch row was restored.
- The annotation does not state a mitigating fact: when the job ends, each token's value exists nowhere, so a leftover live row authenticates nobody unless the value leaked. Nothing to change.
- The annotation names no owner or deadline for revoking such rows by hand. EV-C02-016 section 4 item 1 leaves it as "the executor's decision". The failing run is the signal, and that is acceptable.

3.2 (condition C1) **The hash in the log is acceptable, but the residual is incomplete.**
- Acceptable:
  - EV-C02-003 section 14's first bullet covers "this record, PC-43, the step text or the key inventory", not a database log.
  - B 3.27 and section 14's second bullet keep the token itself out of tables, records and logs, and keep the hash of a presented, unknown value out of RejectedAttempt. Neither is breached by the job's own SQL naming the hash of a synthetic token it issued in `devos-test`.
  - `env_tokens` already stores that hash, and a hash does not authenticate (migration `:133`).
- Incomplete: the annotation says the hash is logged "with statement logging on".
  - With `log_statement=none` and the default `log_min_error_statement=error`, run `headdef_raise_epoch` put 6 hashes into the server log, one per failed statement's STATEMENT line. `headdef_ok` put 0.
  - The planned check ("devos-test's logging settings were not read ... checked when the first .py program runs") would miss this if it reads only `log_statement`.
  - Failure runs are exactly when someone reads the logs, and the long_hex hits will show up there.
- Condition C1 corrects the wording. The design needs no change, since the hash is acceptable either way.
- A further option, not required: psql 16's `\bind` with the default `log_parameter_max_length_on_error=0` would keep the hash out of error logging.
