## 1. The common interface (every `devos_api` function)

Kept from README 8.1 (R:374-447) unless a line here says otherwise.

1. **Answer** (R:396-400). One `jsonb` object, returned, never raised: `{"status": "ok", ...}`; `{"status": "refused", "reason_code": ..., "reason": ...}`; could not check is `refused` with `reason_code` `could_not_check`. Over the Data API every answer is HTTP 200 (T-W07-IDC:46). The two owner-only functions are not `devos_api` functions and are refused by privileges, SQLSTATE 42501 (T-W07-IDC:34).
2. **Parameters** (R:402-419). Named. A record writer takes `p jsonb`; a function acting under a claim takes `claim_token text` first; a state change of one record takes `<record>_id uuid` and its new values. Identifiers are `uuid`, except an Event's id, which is `bigint` (M2: `event.id`).
3. **References in a payload (chosen; D-1 in section 5).** A reference to a record is the field's Appendix B name holding the record's `uuid`, and, where Appendix B gives the reference "+revision", a second key `<name without _ref>_revision` holding an integer: `mission_ref` + `mission_revision` (B 3.3), `work_ref` + `work_revision` (B 3.5, 3.15), `from_ref` + `from_revision`, `to_ref` + `to_revision` (B 3.4), `target_ref` + `target_revision` (B 3.11), `owner_authority` + `owner_authority_revision` (the Decision's answered revision). EffortPolicy's `work_ref` has no revision (B 3.18; M3 `effort_policy.work_ref`). A function that changes a revisioned record names it by `id` and `base_revision` in `p` (as `revise_work` and `revise_mission` are already called, `job/w07_f06_state_change_event.sql:362`, `:392`). Reason: README 8.1's own rule, "a record's own field keeps Appendix B section 3's name" (R:407), and the columns W-C02-08 built (`assignment.work_revision`, `relation.from_revision`, `eval_run.work_revision`); README 8.1 already writes `record_eval_run`'s `work_ref` "with `work_revision`" (R:425).
4. **Keys a function does not read are ignored (chosen).** A payload may carry a declared role name, an `origin` or any other key; the function reads none of them, and they change nothing in the outcome (B principle 8, B:22; W9 point 3's fifth bullet, W9:32). Refusing unknown keys would make a declared role name change the outcome, which point 3 forbids. A required key that is absent is refused (`missing_field`).
5. **Declared fields.** `declared_session_id` (text, optional) is accepted in every `p` and in `claim`'s second parameter; it is written to the event's `declared_session_id` and, where the family has the field, to the record, and nothing reads it for authority (B:22).
6. **Order of checks** (W9 point 3, W9:31; B:46-48; EV3 §1.6, EV3:158). (a) The derivation `devos_private.caller_role_class(<function name>)`: a token that is not verified is refused with its token reason code before any other check, counted (section 1 item 9). (b) The function's own role list, a literal in its own text (B:48; section 10, "Forms the merged break patches read"): a class not on it is refused `role_class_not_permitted`, per call. (c) Input form (`missing_field`, `invalid_field`, `could_not_check` for unreadable input, W9 point 7). (d) Ownership (EV8 1.7.1 Rule O) and another class's claim (Rule C). (e) The claim (section 2.4), for a function that takes a claim token. (f) The family's rules. (g) The writes and their events. The only function with a branch before (a) is `deployment_drift`, which first admits the migration job's direct login (B:46; EV4 Y-02).
7. **The inner blocks and the refusal (CHK-C02-075 finding 2 (d) (a); B 3.13, B:270).** Every `devos_api` function returns a refusal and never raises one. *[R1-1, CHK-C02-076 C1. The first version ran steps (b) to (g) in one block whose handler gave every caught error but a decided refusal `write_failed`, so a failed read of a check's input could not be told from a failed write.]* **Two blocks, in this order.** Steps (b) to (f) run inside a **read block**, and step (g) inside a **write block**: two PL/pgSQL `begin … exception … end` blocks, one after the other in the function's body, each with its own handler. The read block writes nothing (its row locks, `for update` and `for share`, and the transaction-level advisory lock are taken in it, and stay with the transaction when it ends normally); every input a check of steps (b) to (f) needs is read in it, the lock re-checks of F08 and the claim check at an effect included; the write block reads only what it writes back (the ids it creates, the next revision). The build tells the two kinds of error apart **by the block the error occurs in**, never by the SQLSTATE of an unexpected error:
   - **(i) A refusal decided by a check** (read block): the check sets the function's local variables `v_code` (a code of item 14) and `v_reason` (fixed text), then raises the private SQLSTATE `P0D01`; the handler keeps them. PL/pgSQL variables are not undone with the block, so they reach the code after it.
   - **(ii) Missing or partial input, decided by the check itself** (read block): a check that reads no row where its input requires one (the epoch's row, the work item's Mission, a relation's creation event, a referenced record or revision, a read-set element), or a NULL where it requires a value (the epoch's value, a lease, a generation, a claim's `role_class`, an event's `event_type`, a reference's revision), decides `could_not_check` as in (i), with `v_reason` naming the input and "missing" or "partial". It never reads a NULL as false, as zero or as "not transferred".
   - **(iii) Any other error in the read block** (the handler's `others`): `could_not_check`, never `write_failed`. Among them: a missing or renamed table (42P01), a renamed column (42703), privileges revoked from the function's owner (42501), a stored value that does not cast (22P02, 22004), a lock that cannot be had (55P03, 40P01). Before each check the function sets a variable `v_check` to the check's name (`epoch`, `rule_o`, `rule_c`, `claim`, `reference`, `read_set`, `effect_class`, `readiness`, …), so the reason is `<v_check>: its input could not be read (SQLSTATE <code>)`.
   - **(iv) Any error in the write block**: `write_failed` (a failed write, a constraint, a unique index such as S2's `event_transferred_key`, a planted trigger that raises, 40P01 or 40001 at the write), except the private SQLSTATE `P0D02`. A check that cannot run in the read block because it is a trigger on a written table (W-C02-10's sample-share, hidden-position and path-list reads, T-W07-6ST) raises `P0D02` with a fixed reason in its message when its own input cannot be read; the write block's handler maps it to `could_not_check` with that reason. W-C02-10 builds those triggers to that form, or revises this item.
   - **After either block's handler**, the block's writes, records and events are undone; then, outside both blocks, the function writes one per-call RejectedAttempt row and returns `{"status": "refused", "reason_code", "reason"}` and no other key (T-W07-6RG:41; T-W07-ROC:45). `reason` holds fixed text and the SQLSTATE only: never `SQLERRM` or its detail, which can carry input values or a key's hash (B:270: "keeps no input content, and never a token or anything derived from one"). If that last write itself fails (`rejected_attempt` unreadable), the call ends with an error and its transaction rolls back whole; a test reads a raised error as its own "could not check", never a pass (R:400).
   - **The derivation (step (a))** reads `env_tokens` in its own block: an error there gives `could_not_check`, counted in the counted form (`role_class` `none`), since no class is verified.
   - **The cases served.** T-W07-6RG (`T-W07-6RG_rule_gate_could_not_check.md:25, :32, :36`; `job/w07_6rg_rule_gate_could_not_check.sql:431-432, :450-451, :463-466`): **6RG-e2** (the epoch table renamed, at the effect: 42P01 in the claim check, (iii)), **6RG-r4** (the work revision table renamed, at `relate`: 42P01 reading the end, (iii)), **6RG-s3** (the work table renamed, at `prepare_operation`: 42P01 reading the read-set element, (iii)); with them c2, g3 and l2 by (iii), and e1, e3, e4, r1 to r3, s1, s2, c1, c3, l1, l3 and l4 by (ii). T-W07-ROC (`T-W07-ROC_ownership_and_claim_class.md:42-45`): **ROC-x-o-mission-unreadable**, **ROC-x-o-event-unreadable** and **ROC-x-c-claims-unreadable** (every privilege revoked from the function's owner: 42501, (iii)); **ROC-x-c-claims-missing** (`assignment` renamed: 42P01, (iii)); **ROC-x-o-mission-missing** (the work item's Mission link NULL, so the work item joins no Mission: (ii)) and **ROC-x-o-event-missing** (the relation's events deleted, so it has no creation event: (ii)); the three `-partial` cases by (ii). Every one of these plants an input the read block reads, so none reaches the write block.
   - **Residual.** An error in reading that happens only inside a write (a trigger of W-C02-10 that does not raise `P0D02`, a foreign-key check) is `write_failed`. That is a refusal that names the wrong cause, never an acceptance; no merged test plants one and wants `could_not_check`.

   So FN-T-half-* see "not accepted, nothing changed" from a returned refusal, and B-FN-5, written for a build that raises (FN:43), is revised (section 5, D-6). **Not caught**: PL/pgSQL's `others` does not match a query cancellation (a statement timeout) or an assertion failure **[Inf: from PostgreSQL's documentation as remembered, not re-read for this record; the build cites the page with its reading date]**; such a call ends with an error, its transaction rolls back whole, and no RejectedAttempt is left. The build records this as a residual.
8. **Token reason codes** (EV3:1312; B:377; the cases of T-W07-6TK:24-40). `header_unreadable`: `request.headers` not set, the empty string, not JSON, or a JSON value that is not an object. `missing`: an object without the lower-case key `x-devos-env-token`, or the key with JSON `null` (another case or name is not read, so it is `missing`). `empty`: a string that is empty or only whitespace. `malformed`: a value that is not a string, or a string not of the environment token's format (`tests/C02/W-C02-07/shared/token_format.md`; the marker followed by 43 URL-safe characters, T-W07-IDC:29). `unknown`: its hash matches no row. `revoked`: its hash matches a revoked row.
9. **RejectedAttempt** (B:270; EV2 DM-19, EV2:208; M2 `rejected_attempt` and its check `rejected_attempt_form`). A call without a verified token: the derivation upserts the counted row (`function_name`, `reason_code`, `counted_hour` = `date_trunc('hour', now() at time zone 'UTC')`, `role_class` `none`, `count` + 1, increased in place under the unique index `rejected_attempt_counted_key`). A verified caller refused for any reason: one row with its `role_class`, `reason_code`, `reason`, `declared_session_id` and `target_ref` (+`target_revision`) when the call names one. No input content, no token, no hash. The counted row's write is inside the function's own transaction: a caller that rolls its transaction back (a test's subtransaction) also rolls the row back (B principle 2 binds state, not the caller's choice). Every function records its refusals, read functions included (DM-36; EV4 X-14).
10. **Events** (B 3.13, B:264-266; DM-31). Every accepted state change writes its event(s) in the same transaction, through one private writer `devos_private.write_event`: `aggregate_type` (the family's table name: `mission`, `need`, `work`, `relation`, `assignment`, `decision`, `effort_policy`, `finding`, `artifact`, `review`, `verdict`, `acceptance`, `operation`, `observation`, `eval_run`, `env_token`, `transfer_run`, `export`), `aggregate_id`, `aggregate_revision`, `event_type` (section 2), `payload` (the change, never a token or claim token or hash of either), `role_class` from the derivation, `origin` `call` (or `rule` for a record the database makes inside the call, `owner` for the owner-only functions), `declared_session_id`. **An exact repeat** (the same change again) writes no record and no event and returns `ok` with the existing `id` and `"repeat": true` (B principle 2; W9 point 5). Which calls have an exact repeat is listed per function; a creating call with no idempotency key creates a new record (`job/w07_f06_state_change_event.sql:519-523` lists them). *[R2-9, CHK-C02-077 finding 2's side observation (CHK-C02-077:146).]* **The repeat check comes first.** Where a row names an exact repeat, the function compares the call with the stored state before any check that the first call's own write would now fail (`stale_revision` in `revise_work` and `revise_mission`, whose sent fields equal the current revision's; `run_not_open` in `end_transfer_run`, whose run is completed with the same counts), so an exact repeat answers `ok` with the existing `id` and `"repeat": true`, never a refusal. Three functions have no exact repeat that answers `ok`; their second identical call is refused by their own rule, with nothing written and no event: `claim` (`already_claimed`, 2.4), `release` (`claim_not_active`, 2.4) and `record_handover` (`handed_over`: B:397 has every transfer function but four refuse after the `ledger_handed_over` event, and a second identical hand-over comes after it by definition). W9 point 5's "an exact repeat writes no new event and raises no error" (W9:40) holds for both forms.
11. **Read marker** (DM-36, EV2:290). A read function's catalogue comment begins `devos:read`, set by the migration that defines it; it changes no table but `rejected_attempt`; it is `VOLATILE`. Every other function counts as state-changing (F06). `deployment_drift` gets the marker (TABLES G20; A2.9, EV2:453).
12. **Definer rights and `search_path`** (W9 point 2, W9:26). Every function: `security definer`, owner `postgres`, `set search_path = pg_catalog, pg_temp`, and every relation, type and function it names schema-qualified. Reason: PostgreSQL searches the session's temporary schema first when it is not listed, and only for relations and types (**[Inf: from PostgreSQL's documentation of `search_path` as remembered; the build cites it]**); listing it last and qualifying every name leaves nothing the path can redirect. **For the checker (D-9):** point 2's ✘ look ("no application role may create objects in a schema on that path") is met for `pg_catalog`; `pg_temp` is each session's own temporary schema, which a role holding `TEMP` on the database can create in, and which the qualified names make unreachable. The build shows the qualification by a catalogue scan of each function's source for unqualified relation names, and states the residual.
13. **Grants** (R:442; T-W08-PRIV, its "Interface assumed"). In each migration that defines a function: `revoke all on function ... from public` (and from `anon`, `authenticated`, `authenticator`, `service_role`); for a `devos_api` function, then `grant execute ... to anon`; for a `devos_private` function, nothing is granted (owner only). Every `devos_private` type a migration adds, a table's or view's row type included, gets `revoke all on type ... from public` and from the same four roles (EV12:146; N-278 (7), `plan/work/C02.md:470`). An array type needs nothing: it follows its element (EV12:136).
14. **Other reason codes (chosen; no merged test compares any but `could_not_check`, `role_class_not_permitted` and the six token codes, found by a search of `tests/C02/` for compared `reason_code` values).** *[C-20, N-279 (20) (b): that statement no longer holds. T-W14-FN now compares `conflict`, `run_not_open`, `mission_authority`, `cycle` and `handed_over`, and break B-FN-5 reads `write_failed`; section 15 (b) gives the cases and lines.]* `missing_field`, `invalid_field` (the reason names the field), `not_found` (an id that names no record the caller may see: also the answer for an exam record and an open sample, EV8 5.1 and 5.2, R:424, R:428), *[R1-2, CHK-C02-076 C1 and C2: `not_found` is narrowed to the id parameter that names the record a call acts on or reads (`need_id`, `assignment_id`, `operation_id`, `review_id`, …). ### 2.4 Readiness and claim

**Ready** (chosen, from B:132, B principle 6, B 3.5): a work item whose `execution` is `planned`, `ready` or `waiting`, whose Mission is `active`, with no active claim whose lease has not run out, and whose every hard `depends_on` group is true under three-valued logic (ALL: one false gives false, else one unknown gives unknown; ANY: one true gives true; an empty group is not ready). *[R2-5, N-279 (12).]* A group is the current hard `depends_on` relations from the work item that share one `group_id`, under their common `group_mode`; a hard `depends_on` whose `group_id` is NULL (sent with neither key) is a group of one, and a group of one has the value of its member whichever its mode (`relate`'s group rule, 2.5). ## 3. The ledger transfer's fourteen functions (S5; item 2; T-W14-FN's 12 cases)

All are `devos_api.<name>(p jsonb) returns jsonb`, permitted to `kur` only at the gate (B:397; EV8 1.7.3), security definer, fixed `search_path` (FN-M-cat, FNJ:321-326). Four payloads keep README 8.1's keys (R:413-417) as T-W14-FN sends them (FNJ:234-263); this section adds the ten.

### 3.1 Rules common to the group

- **`transfer_source`** (S1, EV5:363; R:417): `{kind, source_id, path, input_commit, last_commit, sha256}`, required in every call but `begin_transfer_run`, `end_transfer_run`, `record_handover` and `record_ledger_entry`. **Kinds** (chosen, the record kind named by EV5 §3.1, EV5:198, with the spelling W-C02-07's and T-W14-FN's calls already send for three): `mission`, `work`, `effort_policy`, `relation`, `decision`, `verdict` (a Review with its Verdict), `acceptance`, `finding`, `need`, `artifact`, and the six event kinds `ledger_entry`, `note_line`, `record_line`, `usage_reading`, `batu_step`, `ledger_state_row`. **Source IDs** per EV5 §3.1: Mission `INSTALL`; Work `W-…`/`Cnn`; EffortPolicy the Work's ID; Relation `<type>:<from source id>:<to source id>`; Decision `D-`/`PC-`/`FR-…`; verdict the verdict ID; Acceptance `<target ID>:<verdict IDs in order, comma-separated>`; Finding `FND-…`; Need `N-…`; Artifact its path, or `tree:<commit>` for a `git_tree`; `ledger_entry` `L-…`; `note_line` `<note ID>#<ordinal>`; `record_line` `<item ID>#<ordinal>`; `usage_reading` `<stage>@<Read at>`; `batu_step` `<stage>#<row>`; `ledger_state_row` its row name.
- **Optional in every writing call:** `declared` (object: the source's own date and actor, labelled declared, B:268) and `source_fields` (object: the source's other front-matter keys and its whole unit of text, verbatim; EV5 §1.2's field rule, EV5:104). Both go into the `transferred` event's payload, never into a record field.
- **The `transferred` event** (B:268; EV5 §3.1, §3.2): one per transferred key, in the same transaction as the record(s), on the record's aggregate (for `verdict`, the Review; FNJ:469-490 reads `aggregate_id` = the returned id), payload `{transfer_source, run_id, declared, source_fields, lacks}`; `lacks` lists the fields or steps the record lacks (EV5 §2.2, §2.1). `role_class` from the token, `origin` `call`.
- **Exact repeat and conflict** (EV5 §3.1; W9 point 10): a `transferred` event of the same (`kind`, `source_id`) with the same `sha256` already exists: nothing is written, the answer is `ok` with the existing `id` and `"repeat": true`. Another `sha256`: refused `conflict`, one per-call RejectedAttempt. Both are read before writing; S2's unique index `event_transferred_key` is the backstop, whose violation inside the block is caught as section 1 item 7 says (*[R1-1]* the write block: `write_failed`).
- **The run (the second point of CHK-C02-075 finding 2 (d); FN "Not covered" (4), FN:71). Decided:** before the `ledger_handed_over` event, every writing call but `begin_transfer_run` and `record_ledger_entry` carries `run_id`, which names an **open run** (a `transfer_run` event with `phase` `begun` and none with `phase` `completed` for it); otherwise `run_not_open`. **After the hand-over a copy names no run:** `transfer_review`, `transfer_acceptance` and `transfer_artifact` take no `run_id` (absent or JSON null); one present is refused `run_not_open`, since `begin_transfer_run` refuses after the hand-over (B:397) and no run can be open then. *[R1-8, CHK-C02-076 finding 2: "no run can be open then" is inaccurate. `record_handover` needs only a begun run (section 3.2), and `end_transfer_run` is refused after the hand-over (Closing, below), so a run begun before the hand-over and not completed stays open for good. Alternative weighed: accept any begun run (FN's current recipe, FNJ:434-439): a run would then mean nothing for these copies. **T-W14-FN's FN-O recipes drop `run_id` (section 5, D-7).** *[C-M10, section 25 (1) and (7): the exact repeat is judged before the run; before the hand-over a `transfer_artifact` call with no `run_id` is `run_not_open`, and one of `transfer_event` (whose `run_id` is starred) `missing_field`]*
- **Closing** (B:397; EV5 §12, EV5:325): with a `ledger_handed_over` event present, every function refuses `handed_over` except `transfer_review`, `transfer_acceptance`, `transfer_artifact` (a verdict file and its tree only) and `record_ledger_entry`. *[C-M10, section 25 (1): the closing check comes after the form and before the exact repeat, so a closed function refuses even an exact repeat after the hand-over, as `record_handover`'s second call is refused (R2-9)]*

- **Sampling** (EV8 2.7): `transfer_decision`, `transfer_work` (its EffortPolicy), `transfer_finding` and `transfer_need` call W-C02-10's sampling function when it exists; until W-C02-10 builds it, they call nothing, and W-C02-10 replaces them.

**(6) The read set: its form, and what the server fills.**
- **The caller's entries.** `read_set` is an array (default `[]`) of `{"ref": <uuid>, "revision": <integer of at least 1>}`.
