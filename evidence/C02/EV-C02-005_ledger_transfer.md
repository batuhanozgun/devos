## 3. The four conditions made checkable (point 3)

Appendix C N18 (C:135): negative "No duplication on a repeated transfer; a transfer cut off halfway resumes; writing to `ledger.md` after the transfer is rejected in the check"; positive "Links and versions match". PC-44 place 12 adds the other homes, the mark, "could not check" and the allowed-change control. The test designer writes N18 after this design is accepted (W-C02-14 point 13).

### 3.1 (i) No duplication when it is run again (LT-19)

- **Mechanism.** Every record the transfer writes has one creation event of type `transferred`, whose payload holds `transfer_source`: the record kind, the source ID, the file's path, the input commit, the last commit that changed the file, and the SHA-256 of the transferred text. A unique index on (`transfer_source` kind, source ID) over events of that type is the **idempotency key** (B principle 2: "An exact repeat of the same change produces no new event"; B:146 for relations). Per kind: Mission `INSTALL`; Work `W-…`/`Cnn`; EffortPolicy the Work's ID; Relation (type, from, to); Decision `D-`/`PC-`/`FR-…`; Review and Verdict the verdict ID; Acceptance (target ID, verdict ID); Finding `FND-…`; Need `N-…`; Artifact the path; `ledger_entry` `L-…`; `note_line` (note ID, ordinal); `record_line` (item ID, ordinal); `usage_reading` (stage, its "Read at" value); `batu_step` (stage, row number); `ledger_state_row` (row name). A second write of the same key with the same hash writes nothing and returns the existing record; with another hash it is refused as a conflict (RejectedAttempt, per call, B 3.13) and the run stops, listing it, never overwriting.
- **Observation for W-C02-14 (point 4).** After a complete run, a second run on the same input writes no record and no event: per family, the counts of records and of events before and after are equal, and its output says it found nothing to write. ✘ in N18: a changed source after its transfer is refused, not overwritten. Break: without the unique index, the second run duplicates.

### 3.2 (ii) It resumes from where it left off (LT-20)

- **Mechanism.** A run is fixed by its **input commit**. The transfer's tool (W-C02-14's, read-only on git: `git show <input>:<path>`, no checkout) builds the **manifest** (every source key with its hash, in phase order: Artifacts; Decisions; the Mission; Works with their policies; Relations; Reviews and Verdicts; Acceptances; Findings; Needs; Events) deterministically from that commit. `begin_transfer_run` records a `transfer_run` event with the input commit, the manifest's hash and its counts per kind; that event and the `transferred` events are the **progress record**. Each record, its revision and its creation event are written in one transaction, so a record never exists without its mark, nor a mark without its record. A resumed run rebuilds the manifest from the same commit, checks its hash against the run's, reads the set of keys already written, and writes only the others, in phase order; a function refuses a record whose referenced record is not yet written, so an order error stops the run rather than writing a dangling link. Resuming and running again are the same operation.
- **Observation for W-C02-14 (point 5).** An interruption planted in N18's fixture at two points at least, one between a record's write and its progress mark (inside the one transaction, so both roll back), and once in the real transfer on `devos`: the next run writes exactly the missing keys (its count of writes equals the manifest minus the written set), no duplicate and no gap, and its record set equals an uninterrupted run's, by content hash. Break: with the mark written in its own transaction after the record, an interruption between them leaves a record with no mark, which the resumed run writes again.

### 3.3 (iii) The records' links and versions match (LT-21)

- **Versions.** Every transferred record is revision 1 (B principle 3; DM-02), with the content of its source at the input commit; the transfer does not replay git history as revisions: commits mix state and text, a replay would mint revisions for state changes (DM-02: state is not content) and write revisions after answers (B:299), and git keeps every version. Each record's creation event names the input commit and the last commit that changed its file; an Artifact's `commit` is that last commit. `acceptance_ref` points to the item file at the first `main` commit, on the first-parent history, that holds its acceptance block as it now stands (`git log --first-parent -S'<!-- acceptance -->'`; a block changed later through the class-high route has every earlier form's commit listed in the payload). A verdict's `reviewed_head` becomes a `git_tree` Artifact at that commit.
- **Links.** Each kept as a Relation (3.4), pointing at the target's revision 1: `parent` → `part_of`, or `mission_ref` for stages; `depends_on` → `depends_on`; `accepted_by` → Acceptance with its verdict; a note's `origin` → `derived_from`; a verdict's targets → `reviews`; a decision's `record`, a log entry's Record changes, a decision's `affected_stages` → `about`; `superseded_by` → `supersedes`; an evidence ID named in a record → `about` to the file's Artifact.
- **Observation for W-C02-14 (point 7).** A comparison reads every link in the input and finds its counterpart in the database at the mapped revision, run in full on the real transfer; in N18's fixture, planted mismatches (a link to a record not transferred, a revision that does not match its commit, a link to the wrong record) are each reported. With input missing, unreadable or partial, it says "could not check".

### 3.4 (iv) `ledger.md` is not an authoritative write surface (LT-22)

- **The mark.** The hand-over pull request (W-C02-14's) writes, in `plan/ledger.md`, a machine-readable block `<!-- ledger-handover … -->` that lists every handed-over file and region (§4) with the transfer run's ID, its input commit and the date, followed by one plain paragraph: the date, the transfer's record, that these parts are no longer authoritative, where their records now live (the database `devos`; the generated views), and how to proceed if the database cannot be read (Appendix G G7: "could not check" stops the affected work). Each other handed-over file carries a one-line mark of the same form after its front matter, or at its top if it has none. After the merge, `record_handover` writes the `ledger_handed_over` event with the run and the merge commit, which closes the transfer's functions (section 12).
- **The check.** `tools/merge_gate.py`, which the guard runs before every merge (M7), reads the block from the merge base on `main` and the pull request's diff, and fails (GATE FAIL), whatever verdict is attached, a diff that adds, changes or removes a line in a frozen region, removes or alters a mark, or creates a file under `plan/work/` or `plan/decisions/` that carries a state key, a note block or a "Batu's steps", "Usage" or "Record" section. For the generated regions (`plan/ledger.md`'s blocks, `DURUM.md`, the stage logs' entries below their mark) it renders them from the database with `tools/records.py`'s renderer, through the `devos_kurulum` token the working session holds, and fails a diff whose generated text differs from that rendering or whose appended log entry names no event of the database with the same hash. `records.py render --check`, which `tools/stop_check.sh` runs, repeats the comparison before every stop.
- **Missing, unreadable or partial input** (plan Section 8 item 14): a block that is missing where the base's history has one, malformed, or names a path the base lacks; a file it cannot read; a database it cannot reach or that answers in part: the gate says "could not check" (GATE ERROR) and the merge is blocked. A pull request that touches no handed-over file needs no database read.
- **Observation for W-C02-14 (point 8).** After the mark merges, a planted write (a record line in `plan/ledger.md` and one in each other handed-over file) by the route records reached `main` by (a `claude/` branch and a pull request) is refused by the gate and does not reach `main`; the controls pass: a change the hand-over allows (a new item file with text only, a re-rendered view) and the same record written through the database's functions. Break: without the frozen-region rule, the planted line merges.
