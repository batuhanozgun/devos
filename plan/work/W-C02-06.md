# W-C02-06 · The ledger transfer, designed (task 8)

A design record, `evidence/C02/EV-C02-*`, and a plan change through Section 14 if the plan text changes, for task 8: the transfer of the installation ledger into existing families ("work items into Work, decisions into Decision, log entries into Event, checker verdicts into Review and Verdict, findings into Finding, notes into Event or Finding by kind; no new family", plan C02 task 8), with the four acceptance conditions of plan Section 9's "Installation ledger" (no duplication when it is run again; it resumes from where it left off; the records' links and versions match; after the transfer `ledger.md` is not an authoritative write surface, with an explicit hand-over mark and a later write attempt rejected by the checks). It takes R1 section 4's fit table: every record kind's target family, including those with none stated (stages, frame reviews, evidence files, gaps, open items, Batu's constraints, usage readings, Batu's steps, task texts); the role that writes each, since binding verdicts and acceptances are written only with `devos_denetim` (B:237) while the installation's verdicts and C02's own come from the builder; the Mission and effort policy each transferred work item needs (B:104, B:117, B:299); decisions whose class and fields do not match Decision's (B:287, B:290); notes, which have no kind; the idempotency key, the progress record for resuming, and how git versions map to revisions. It decides which files stop being write surfaces after the transfer (R3 G10: the ledger is spread over `plan/work`, `plan/decisions`, `plan/ledger/*-log.md` and `evidence/`), what stays in git and why, and where the working order's records (discipline answers, frame reviews, usage readings, the hand-over, Batu's constraints) live from then on (R1 2.8), and what Appendix F line 27 then means for C12's acceptance record. Owner: the executor. Deadline: before W-C02-14.
