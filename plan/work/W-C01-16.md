# W-C01-16 · Row 9: single- and multi-repository sessions; the guard hook (C01 #9)

Plan C01 row 9. Probe: P2: the `devos-probe-a` routine is a single-repository session; the `devos-probe-b` routine has `devos` and `devos-evals`, as an exam session would have. N-048 (whether a session with several repositories loads the hooks and permission rules of `devos`) is this row's second part. The fault injection uses the means W-C01-04 provides, if it needs one. It waits for rows 1 to 4 and 17 (the purpose). N-063's P4 and U2 draw on it (W-C01-27).

## Acceptance

<!-- acceptance -->
Row 9's result is recorded in an evidence file under `evidence/C01/` with the common evidence envelope (plan Section 8 item 9: the source commit, the deployment configuration, the criterion version, the input, the actual observation, the raw evidence ID and the independence level); its deployment configuration names the probe environment, the routine, the repositories attached and the Claude Code version, and its raw evidence is the probe sessions' own records on their `claude/probe-c01-…` branches.

Success condition (plan C01 row 9, verbatim):

> In a single-repository session the permission rules and hooks are applied; the check before writing to the public repository runs. The guard hook (the installation guard, which phase B carries over, K-9 item 4) denies a tool that is not on its list, never answers "ask", and denies when it is made to fail or runs past its own time limit (fault injection). In a session with `devos` and `devos-evals`, as an exam session would have, it is recorded which repositories load and whether the hooks and permission rules of `devos` load there (N-048) (probe: P2)

It counts as met only when every part of it is observed and recorded; the record shows at least:

- in the single-repository session: the permission rules and hooks applied (the guard's decision log in that session counts its decisions), and the check before writing to the public repository run on a push;
- the guard hook denying a tool that is not on its list, never answering "ask", and denying when it is made to fail and when it runs past its own time limit (fault injection);
- in the `devos-probe-b` session: which repositories load, and whether the hooks and permission rules of `devos` load there; this answers N-048;
- for plan 6.7's row "Interactive sessions and phase A", whose mark names this row ("a session whose checkout does not carry `.claude/` runs without it **[Awaiting verification: C01 #9]**"): whether such a session runs without the guard, from the platform's current official documentation on where a cloud session takes its hooks from, read with its date (plan 0.3 item 12), and from the `devos-probe-b` session where it shows such a checkout. If the result differs from that row, the row is corrected through plan Section 14 before C01 closes.

Fail path (plan C01 row 9, verbatim):

> If the check before writing does not run: the check stays only at the PR layer; the residual risk goes to Batu. If the guard does not fail closed, it is corrected before C02 opens DevOS's environments. If the hooks do not load in a multi-repository session, no DevOS session runs with more than one repository, and the exam environment reads its material from the database with its own token (7.3); C05 designs this before the exam setup

If the success condition is not met, a plan-change decision is taken and recorded that applies the fail path above: a plan-change record `plan/decisions/PC-<nn>.md` (plan Section 14; working order section 6) and, where the fail path sends a choice to a decision that is Batu's (working order section 8), its decision record as well.

The decision applies each branch of the fail path that the result meets, with its deadline: the check stays only at the PR layer and the residual risk goes to Batu; a guard that does not fail closed is corrected before C02 opens DevOS's environments; if the hooks do not load in a multi-repository session, no DevOS session runs with more than one repository, the exam environment reads its material from the database with its own token (7.3), and C05 designs this before the exam setup, carried by a note on `plan/work/C05.md`.

A part that could not be observed is recorded as "could not check" (plan Section 8 item 14), never as met: it is handled as a failed part, or, where its components cannot be stood in for, it moves to the stage where they exist (plan C01, the paragraph after the probe setup), and the record names that stage and the work its fail path comes before.

A fresh-context checker that did not produce the result (same session, fresh-context subagent; declared, Ek A 5.3; PC-06) judges the record against this condition, plan C01 row 9 and the mark of plan 6.7 named above, at the head that records it, and states its independence level.
