**Plan 6.8's auto-merge, moved here from C01 row 8** (W-C01-15; `evidence/C01/EV-C01-009_W-C01-15_row8_release_chain.md` section 3; PC-25 place 2; 2026-10-11). Plan 6.8 asks "Whether auto-merge works with the session's GitHub connection". C01 could not try it, so test 5 shows it, before automatic merging of ordinary changes is relied on after this stage. What it needs, from GitHub's documentation (read 2026-10-11):
- (1) the repository setting **Allow auto-merge** on. On a personal-account repository only the owner can turn it on, and the public API read it `false` on 2026-10-11. This is Batu's step in plan Section 12 item 1 (PC-25 place 2);
- (2) a pull request that cannot merge at once: a required status check on its base that has not passed yet. The rule of `main` gets its required checks at this stage (Section 12 item 1); on 2026-10-11 it had none;
- (3) write permission for the account that enables it (the machine account merges pull requests today);
- (4) a route through the session's GitHub connection. GitHub offers enabling as the GraphQL mutation `enablePullRequestAutoMerge`, and the platform's proxy rejects every GraphQL request, the built-in GitHub tools' included. Whether the built-in `enable_pr_auto_merge` works through the proxy is not documented;
- (5) the guard's rule M4 denies that tool, so the attempt needs a checked guard change (class high) scoped to the test.
