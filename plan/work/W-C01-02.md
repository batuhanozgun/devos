# W-C01-02 · Key inventory (N-105)

Plan Section 12, "Key inventory" ("The builder keeps a single inventory in C00"), carried to C01 by N-105 (CHK-C00-067 condition 4(c)). It needs no probe setup and is due before the first C01 probe token is created (Section 12 item 0), so it lies on the path to Batu's setup steps (W-C01-05). C03 reads it too: N-107 on `plan/work/C03.md` matches the keys it lists in test 3.

## Acceptance

<!-- acceptance -->
One file in `devos`, named in the log entry that records it, lists for each key and token its owner, where it is kept, its permissions and its revocation path, and never a value: no key, token or password, and no fragment, hash or other derivative of one. Its first entries are `GH_TOKEN` and `GITHUB_TOKEN` in the working session's environment, with condition 1's result (N-027 on `plan/work/C00.md`; `evidence/C00/EV-C00-022_closure_conditions.md` section 1). It says which credential-like variables and files the platform itself puts into sessions (from `evidence/C00/closure/C1_probe_output.txt`), as platform-issued (PC-18). It says that every key and token plan Section 12 names is entered when it is created, the C01 probe tokens first, and that the probe tokens stay listed until C02's first migration removes them. The file is merged into `main` before Batu is asked to create the first probe token (git order against the date of that step under "Batu's steps" in `plan/work/C01.md`). A fresh-context checker (same session, fresh-context subagent; declared, Ek A 5.3; PC-06) reads every entry and judges the file against this condition, N-105 and plan Section 12, and states its independence level; an entry that holds a value, or anything derived from one, fails it.
