# W-C02-21 · The guard denies Monitor by rule T1

**The finding.** W-C02-20's test designer found it, and the executor confirmed it on 2026-10-13. At `main` `3262699`, `.claude/hooks/tool_allowlist.py` allows `Monitor` by name: the tool is on `ALLOWED_NON_MCP` (line 104), and `decide()` answers "allow" under rule T1 (line 2082) without reading its arguments. The shell rules (B1 to B11, G0, and the leak check's L1 and L2) run only when the tool is `Bash` (`decide()`, line 2070). `summary()`, which writes the call into the log and into a denial, also reads a command only from `Bash` (line 434). This item's test designer reproduced it at that commit by calling the guard's `decide()` with no hook wrapper and no log. `Monitor` was allowed under T1 in four cases: with a harmless command; with commands that `Bash` is denied under B6 (`curl -d`), B1 (a push to `main`) and B8 (an environment dump); with a command the shell rules cannot parse, which `Bash` is denied under G0; and with a WebSocket URL or with no input at all.

What `Monitor` does, by two sources:
- **The tool's schema**, read by the executor through the tool-search tool on 2026-10-13 (observed in the session). Its `command` field is "Shell command or script. Each stdout line is an event". It says "The script runs in the same shell environment as Bash". Its `ws` field is "WebSocket to open", with any `url`.
- **The platform's tools reference**, `https://code.claude.com/docs/en/tools-reference.md` ("Monitor tool" and "WebSocket source"), read on 2026-10-13 by this item's test designer (documented, not independently tested). It says Monitor "Runs a command in the background and feeds each output line back to Claude" and "Can also open a WebSocket". It also says: "When Monitor runs a command, it uses the same permission rules as Bash". That is Claude Code's own permission layer, and `.claude/settings.json` has no `Bash` rule in it. "Opening a WebSocket prompts for approval", which in this repository's sessions the guard answers on `PermissionRequest`. Finally, "Plugins can declare monitors that start automatically when the plugin is active".

So a `Monitor` call can run a shell command, or open a connection to any address, and none of the guard's shell or network rules applies to it.

Records that say otherwise:
- `evidence/C02/EV-C02-006_session_tools_bridge.md` line 98: "`Monitor` and the `Task…` tools in CTL act on the session's own background work".
- `evidence/C01/checks/CHK-C01-051.md` line 116 treats waiting through `Monitor` as covered because the guard "allows every listed non-MCP tool by name with no argument checks".
- `evidence/C01/checks/CHK-C01-052.md` line 44 records `Monitor` as `allow T1`. Line 54 recommends: "wait inside the turn (Monitor, allowed T1)".

**The executor's decision** (technical, the builder's). The guard denies `Monitor` by taking it off `ALLOWED_NON_MCP`, so that rule T1 denies it like any tool not on the list. Nothing in the installation needs it: waiting uses `Bash` with `run_in_background`, or the session's `send_later`. The alternative not chosen was to run `Monitor`'s `command` through the shell rules. That would be a new mechanism, and `ws` has no shell form to check.

**Tests.** The cases are in `tools/test_tool_allowlist.sh` (block "W-C02-21", labels `W21-*`). Their form-C0 text and the breaks are in `tests/C02/W-C02-21/README.md`. The test designer wrote them before any change exists. W-C02-20's tests were revised in the same change: its `Monitor` cases are withdrawn, and `tests/C02/W-C02-20/README.md` section 11 says why.

Owner: the executor. Deadline: the executor sets it (point 7 asks the record to state it).
