# W-C02-14 · The ledger transfer (task 8)

The installation ledger is transferred into the database as W-C02-06 designs it, and the four acceptance conditions of plan Section 9's "Installation ledger" are shown: no duplication when it is run again; it resumes from where it left off when interrupted midway; the records' links and versions match; and after the transfer `ledger.md` (and the other files W-C02-06 names) is not an authoritative write surface, with an explicit hand-over mark and a later write attempt rejected by the checks (N18). The working order's and the records tools' references to the ledger files are changed with it (class high where they are). The transfer's own schema (its progress, idempotency and hand-over records, as W-C02-06 designs them) is built with the rest of C02's schema and functions in W-C02-08 to W-C02-10, so this item deploys no migration and W-C02-13's full run does not wait for it; if it must deploy one after all, the tests of W-C02-13 that the migration touches are run again before the stage close (W-C02-18 point 1). Its N18 test and the tests of the transfer's checks with missing, unreadable and partial input (plan Section 8 item 14) are written by the test designer once W-C02-06's design is accepted, and merged before this item's work starts. Owner: the executor. Deadline: before W-C02-17; the ledger moves "at the end of C02" (plan Section 9).

A departure stops the transfer until a new decision record is merged.
2. **Through the rule gate.** ✔ The transfer writes only through `devos_api` functions, with the environment token of the role class W-C02-06 names. ✘ Looked for: every transferred record has its creation event with that role class, and none was written another way (per family, the counts of records and of their creation events match). Transferred records pass the same gates as any other record, except where Appendix B states an exception for records the ledger transfer writes (3.3, 3.8, 3.11, 3.17 and 3.18, as PC-44 adds them), and no other; a record a gate refuses is listed with its reason, never forced in. ✘ Looked for: every record that takes an exception is of the kind and field that exception names, was written through the transfer's path before the `ledger_handed_over` event, or, for 3.11's verdict and Acceptance copies, after it through `transfer_review`, `transfer_acceptance` or `transfer_artifact` from a verdict file merged into `main`, as Appendix B section 4 states, and has a creation event that lists the fields or steps it lacks, and, for 3.8 and 3.17, its source at the input commit lacks the field the exception covers; the record gives, per exception, the count of records that take it. ✘ Planted: for each exception, a record of that kind that takes it, written through the ordinary functions, and one written through the transfer's path after the `ledger_handed_over` event, are each refused; for 3.11, the case after the event is a copy whose verdict file is missing on `main` or differs from it by hash.
3. **Complete and faithful.** ✔ The record names the transfer's input commit; for each record kind, the IDs in the input and the IDs in the database are compared both ways and differ by nothing, or only by what W-C02-06's record excludes, each listed with its reason. ✘ Looked for: no transferred record states a different author, date or independence level than its source (a checker verdict stays "same session, fresh-context subagent", declared; Batu's words stay verbatim, with their interpretation). 4. **"no duplication when it is run again".** ✘ After the transfer completes, it is run again on the same input: it writes no record and no event (per family, the counts of records and of events before and after are equal), and its output says the run found nothing to write.
5. **"if it is interrupted midway, it resumes from where it left off".** ✘ An interruption is planted: (a) in N18's test (point 6), at two points at least, one of them between a record's write and its progress mark; (b) once in the real transfer on `devos`, at a point (a) covered. After each, the next run resumes: it writes only the records not yet written (its count of writes equals what was missing), leaves no duplicate and no gap, and ends with the record set an uninterrupted run gives (for (a), compared record by record, by content hash, with an uninterrupted run on the same fixture). A pass in `devos-test` alone does not close the real transfer on `devos` (plan Section 8 item 9).
