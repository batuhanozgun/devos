# W-C02-14 · The ledger transfer (task 8)

The installation ledger is transferred into the database as W-C02-06 designs it, and the four acceptance conditions of plan Section 9's "Installation ledger" are shown: no duplication when it is run again; it resumes from where it left off when interrupted midway; the records' links and versions match; and after the transfer `ledger.md` (and the other files W-C02-06 names) is not an authoritative write surface, with an explicit hand-over mark and a later write attempt rejected by the checks (N18). The working order's and the records tools' references to the ledger files are changed with it (class high where they are). Owner: the executor. Deadline: before W-C02-17; the ledger moves "at the end of C02" (plan Section 9).

Task 8, word for word: "Transfer of the installation ledger (with the acceptance conditions in the introduction of Section 9) into existing families: work items into Work, decisions into Decision, log entries into Event, checker verdicts into Review and Verdict, findings into Finding, notes into Event or Finding by kind; no new family (PC-08)." 1. **As designed.** The transfer follows W-C02-06's design record and its plan change, merged before the transfer starts: each record kind of its fit table goes to the family it names, with "no new family"; each family is written with the role class it names, and with the right it names where Appendix B 3.11 ("Binding verdicts and acceptance are written only with the `devos_denetim` role") or EV-C01-004 S8 line 1 bears; and its idempotency key, its progress record, its mapping of git versions to revisions, the files that stop being write surfaces, and where each kind's records live afterwards are as it states. A departure stops the transfer until a new decision record is merged.
2. **Through the rule gate.** ✔ The transfer writes only through `devos_api` functions, with the environment token of the role class W-C02-06 names. ✘ Looked for: every transferred record has its creation event with that role class, and none was written another way (per family, the counts of records and of their creation events match). Transferred records pass the same gates as any other record; a record a gate refuses is listed with its reason, never forced in.
3. **Complete and faithful.** ✔ The record names the transfer's input commit; for each record kind, the IDs in the input and the IDs in the database are compared both ways and differ by nothing, or only by what W-C02-06's record excludes, each listed with its reason. ✘ Looked for: no transferred record states a different author, date or independence level than its source (a checker verdict stays "same session, fresh-context subagent", declared; Batu's words stay verbatim, with their interpretation). Every record written to the ledger files after the input commit and before the hand-over mark is in the database too, or is listed with its reason; none stays only in git unnoticed.
4. **"no duplication when it is run again".** ✘ After the transfer completes, it is run again on the same input: it writes no record and no event (per family, the counts of records and of events before and after are equal), and its output says the run found nothing to write.
5. **"if it is interrupted midway, it resumes from where it left off".** ✘ An interruption is planted: (a) in N18's test (point 6), at two points at least, one of them between a record's write and its progress mark; (b) once in the real transfer on `devos`, at a point (a) covered. After each, the next run resumes: it writes only the records not yet written (its count of writes equals what was missing), leaves no duplicate and no gap, and ends with the record set an uninterrupted run gives (for (a), compared record by record, by content hash, with an uninterrupted run on the same fixture). A pass in `devos-test` alone does not close the real transfer on `devos` (plan Section 8 item 9).
6. **N18 (W-C02-07's test).** ✔ In `devos-test`, on a synthetic fixture ledger labelled as such (plan Section 8 item 13), N18 passes with its negatives and its positive, with the raw output filed. The test files are those W-C02-07 merged, unchanged, or changed only under ledger rule 3 with the earlier results void; a test that could not run is "could not check", never a pass.
7. **"the records' links and versions match".** ✔ Every link in the input (among them `parent`, `depends_on`, `accepted_by`, a note's `origin`, the records a log entry or a decision names, a verdict's target and `reviewed_head`) has its counterpart in the database, pointing at the transferred record of that ID, at the revision W-C02-06's mapping gives for its git version; the comparison ran in full on the real transfer and reports no mismatch. ✘ In point 6's fixture, planted mismatches (a link to a record not transferred, a revision that does not match its commit, a link to the wrong record) are each reported by the comparison.
8. **"after the transfer, `ledger.md` is not an authoritative write surface (an explicit hand-over mark in the file; a later write attempt is rejected by the checks)".** ✔ `plan/ledger.md`, and each other file W-C02-06 names, carries an explicit hand-over mark: its date, the transfer's record, that the file is no longer authoritative, and where its records now live. ✘ After that mark is merged, a planted write attempt (a new record line in `plan/ledger.md`, and one in each other file W-C02-06 names), made by the route records reached `main` by before (a commit on a `claude/` branch and a pull request), is rejected by the checks, with their raw output, and does not reach `main`. ✔ Controls (plan Section 8 item 2): a change W-C02-06 allows passes the same checks, and the same record written through the database's function path is accepted. ✘ Looked for: no rule or tool (the working order, `CLAUDE.md`, `tools/records.py`, `tools/stop_check.sh`, `tools/merge_gate.py`, the generation of `DURUM.md`) still names a ledger file as the authoritative home of a kind W-C02-06 moved, so each kind has one authoritative home; the tools' own tests pass after their change.
9. **Appendix F line 27.** ✔ C12's stage record is in the database, and the record says, as W-C02-06 decided, where the `/goal`'s proof reads C12's acceptance from.
10. **Missing, unreadable and partial input (plan Section 8 item 14).** The transfer's checks (the ID comparison, the link and version comparison, the write rejection) are each run with missing, unreadable and partial input, and each reports "could not check", apart from clean and from fail; the write rejection, which guards a merge, blocks when it could not check.
11. **Parameters (PC-23).** If the transfer holds other work (for example, no record writes between its input commit and the hand-over mark), the record gives what plan 6.12 item 1 names for that hold: the time it adds on the critical path, its reason's source with that source's date, and, for a reason taken from the plan ("At the end of C02"), a check against Batu's later decisions.
12. **Order.** W-C02-15 (N-127, N-198) is accepted before the transfer starts, so that the log entries move under the discipline checks as they then stand.
