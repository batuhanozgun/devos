# W-C02-20 · The guard stops both token formats in URLs and outbound text, except on the client path

The identity chain's accepted design (`evidence/C02/EV-C02-003_identity_chain_and_environments.md`, W-C02-05, accepted on CHK-C02-014) gives the guard work that no item's acceptance block carries. Its section 1.6: "W-C02-11 (before task 7): the guard allows that client path in DevOS's sessions, and stops strings of the environment token's format and of the claim token's format (§1.7) in URLs and outbound text (P:734), each shown with a planted synthetic case." Its section 1.7: "The guard and the leak check stop strings of the claim token's format in URLs and outbound text, as for the environment token (W-C02-11; C03, C04), except on the client path to the live project's host (§1.6)." Its section 0, rows 2 and 36, give the stop and the client path to other items before task 7. Plan 6.7's row "Network: outbound requests and URLs" (plan line 734) counts on the "guard hook, which also stops planted fake secrets and strings of the token format in URLs". W-C02-11's acceptance block was written before that design and covers S9's bridge, the recorder hook, the uses list and the guard's tests; W-C02-11 is accepted on that block. The work also needs what W-C02-11 does not have: the formats' literal markers and finder patterns, which W-C02-07 fixes in `tests/C02/W-C02-07/shared/token_format.md` (with its machine copy `shared/scan_patterns.json`), and the client script, which W-C02-09 builds in the identity chain's first part (EV-C02-003 section 1.6: "a small script in the repository that calls the Data API with the publishable key from its variable, lets the proxy add the header, and never prints request headers"). Note N-221 on `plan/work/C02.md` has the working session call `token_role_class()` over that path at its step 5. W-C02-07's Group D also found that the guard's log redaction (`REDACT` in `.claude/hooks/tool_allowlist.py`) can mask a string of either format (`token_format.md` section 6), so the stop must read the raw input. So the executor carries this work in its own item: the stop of both formats, and the client path's exception.

**The client script.** It is not an accepted item's output when this item starts. This item names it by its path as merged into `main` through the merge gate, with the merge commit that added it, not by W-C02-09's acceptance, so `depends_on` does not wait for W-C02-09 as a whole. The guard change that names the script merges only after that commit. The item may land in two changes: the stop first, and the client path's exception once the script is on `main`. Each change is class high (`.claude/`).

Owner: the executor. Deadline: before N-221 step 5 (the working session's first call over the client path), and in any case before any session runs in `devos-calisma`, `devos-denetim` or `devos-sinav` (W-C02-12).
