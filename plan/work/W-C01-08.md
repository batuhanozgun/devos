# W-C01-08 · Row 3: environment token (C01 #3)

Plan C01 row 3, on the critical path. Probe: P1 and P3: each probe session sends a request to `devos-test` carrying its environment's probe token in a separate header, and records only whether the token is visible to it and by which route, never the token or anything derived from it. Because each probe environment has both the broad network access and its own token (P1), it also answers 6.3's "[Awaiting verification: do broad network access and adding the token work together? C01]". N-063's D07, P3, U1, U3, Q1 and B4 draw on it (W-C01-27).

## Acceptance

<!-- acceptance -->
Row 3's result is recorded in an evidence file under `evidence/C01/` with the common evidence envelope (plan Section 8 item 9: the source commit, the deployment configuration, the criterion version, the input, the actual observation, the raw evidence ID and the independence level); its deployment configuration names the probe environment, the routine, the repositories attached and the Claude Code version, and its raw evidence is the probe sessions' own records on their `claude/probe-c01-…` branches.

Success condition (plan C01 row 3, verbatim):

> The token is added to the Supabase request in a separate header; the session cannot see the token by any route; the database derives the role class correctly (probe: P1, P3; the probe records only whether the token is visible and by which route, never the token or anything derived from it)

It counts as met only when every part of it is observed and recorded; the record shows at least:

- the probe token carried to `devos-test` in a separate header of the request, with the environment's broad network access on (6.3);
- the role class the database derives: `devos-probe-a`'s class for a request from `devos-probe-a`, `devos-probe-b`'s class for one from `devos-probe-b`;
- every route tried by which a session might see its own token or the other environment's token, and the answer on each; the finding "cannot see the token" is stated for the routes tried only, and a route that the platform's documentation or the guard's credential rules (B7, B8, F4) name and the probe did not try is a gap the checker names;
- nothing in any record that is the token or derived from it.

Fail path (plan C01 row 3, verbatim):

> If the header cannot be added: an Edge Function gate that authenticates. If the session can see its own token, the threat model decides. The token is what lets the database tell the environments apart (criteria 8, 30); the threats are a session using another environment's token, and a token leaving its environment (a public write, a URL, a record). Separation of authority still holds while no session can read or set another environment's token or settings (C01 #17, C03 test 3), and while a token that leaves is caught: tokens get a recognisable format, every outbound check (the public-write leak check, the guard hook) stops strings of that format, and a token found outside its settings field is revoked and renewed. Visibility is then recorded as a residual risk before C02 builds the identity chain. If a session can read another environment's token, separation of authority fails, and the identity chain is redesigned before C02

If the success condition is not met, a plan-change decision is taken and recorded that applies the fail path above: a plan-change record `plan/decisions/PC-<nn>.md` (plan Section 14; working order section 6) and, where the fail path sends a choice to a decision that is Batu's (working order section 8), its decision record as well.

The decision follows the branch of the fail path that the result meets: the header cannot be added (an Edge Function gate that authenticates); the session can see its own token (the threat model decides, and visibility is recorded as a residual risk before C02 builds the identity chain, on the conditions the fail path lists); a session can read another environment's token (separation of authority fails, and the identity chain is redesigned before C02).

A part that could not be observed is recorded as "could not check" (plan Section 8 item 14), never as met: it is handled as a failed part, or, where its components cannot be stood in for, it moves to the stage where they exist (plan C01, the paragraph after the probe setup), and the record names that stage and the work its fail path comes before.

A fresh-context checker that did not produce the result (same session, fresh-context subagent; declared, Ek A 5.3; PC-06) judges the record against this condition and plan C01 row 3, at the head that records it, and states its independence level.
