# W-C01-03 · Probe design: the setup P1 to P3, each probe, N-109's check and Batu's steps

Plan C01, "Probe setup" (P1 to P3) and "Platform and guard apart", with the probe each row names (rows 1, 2, 3, 4, 5, 7, 9, 12, 13 and 17), row 8's two attempts for the marks of plan 5.6 and 6.8 (W-C01-15), and N-109's check, which "is designed in C01 with the probe environments, is written down before it runs". This item is the written design of all of them, merged before any probe runs and before Batu is asked for a step, so that the reading of every probe is fixed before its result exists (working order section 4; plan Section 8 item 6). It also prepares the text of Batu's C01 steps (plan Section 12 item 0), which W-C01-05, W-C01-13 and W-C01-29 post. It needs no probe setup.

## Acceptance

<!-- acceptance -->
A design record under `evidence/C01/`, with the files it names, states:

1. **P1:** the settings of `devos-probe-a` and `devos-probe-b`, each with the broad network access the working environment will have (6.3) and its own probe token in its settings field, and no other secret;
2. **P3:** the one-off probe text for `devos-test` (a token check that derives one of two probe role classes from a token's hash; a small queue of synthetic work items, labelled synthetic, plan Section 8 item 13, with items left for C01's combined scenario, W-C01-29 item 1); the single line per probe environment that shows its probe token once (6.3); a recognisable format for the probe tokens, so that a scan can look for them (as row 3's fail path asks of tokens); and that this text is not the migration path (6.2) and C02's first migration removes the schema and the probe tokens with it;
3. **P2:** the two probe routines (one in `devos-probe-a` with only `devos`; one in `devos-probe-b` with `devos` and `devos-evals`), without connectors, each with its starting instruction, how each of its runs starts, and the number of runs planned per day, counted against the daily routine limit that Batu's own routines share (row 5: the limit is not used up on purpose); and how each probe session's checkout holds the revision from which the guard derives the service names, since the guard fails closed on a shallow checkout (working order section 10);
4. for every probe row (1, 2, 3, 4, 5, 7, 8, 9, 12, 13 and 17) and for N-109: the probe target, the exact attempt, what the probe session records, and how the record is read against the row's success condition (met, failed, or could not check, plan Section 8 item 14); where a row asks what the platform itself allows, the attempt is made only on the named probe target, under the probe-only guard rule (W-C01-04), and the guard's own answer is recorded apart; for row 7, the time limit the session part is held to; for row 8, a push from a probe routine session, its settings left at their defaults, of a commit already on its `claude/probe-c01-…` branch to a new branch of `devos` outside `claude/` (never `main` or another existing branch), and how a branch it creates is deleted, and an attempt to enable auto-merge on a probe pull request whose merge cannot change `main` or any branch outside `claude/probe-c01-…`; for row 13, how many tries of each way of triggering the probe skill are made, so that "reliably" is read from them;
5. for N-109, the check as that note fixes it: the credentials (the messaging token; the session's token file); each reach tried (another session in the same environment; a session in the other probe environment; the account's settings or services, by an attempt whose success changes nothing of Batu's); for each credential, a control showing that the probe's use of it works in its own session by the same route; and the reading red, green or neither, as N-109 defines them;
6. the bounds every probe session keeps: it writes only to a `claude/probe-c01-…` branch of `devos` (row 8's two named attempts excepted: the push to a new branch outside `claude/`, and enabling auto-merge on the probe pull request, which is a GitHub write but no branch write); it never writes a token, a secret or anything derived from one; it never lists, reads or messages the account's other sessions or routines; it reads no content from Batu's other repositories; it names no service connected to Batu's account; it records the model, the permission mode, the effort and the Claude Code version as they are shown to it, and "not visible" for what is not shown; the builder does not open or steer probe sessions and reads only their branches;
7. that no step of the setup or of any probe enables a paid feature;
8. Batu's steps: exactly those of plan Section 12 item 0, each a single action written as Appendix E section 7 sets out: the setup steps in one batch (W-C01-05; Appendix E section 8: his tasks are gathered and passed to him in one go); row 6's question when W-C01-13 opens its probe issue, after rows 1 to 4 and 17 (plan C01's purpose), with any other of his tasks pending then; the deletion steps with W-C01-29; a step beyond Section 12 item 0 is recorded as a finding and routed by working order section 8 before he is asked for it.

A fresh-context checker that did not write the design (same session, fresh-context subagent; declared, Ek A 5.3; PC-06) judges it against this condition, plan C01's "Probe setup", "Platform and guard apart" and each row's probe, W-C01-15 (the marks of plan 5.6 and 6.8), and N-109, at the head that adds it and before any probe runs, and states its independence level.
