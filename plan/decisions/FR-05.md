# FR-05

**What it is.** The frame review Batu directed before any further C01 work on platform separation (L-178), made by the executor as coordinator under plan 6.12 item 2. Its question is his: is each of three parts of the security scope required by DevOS, or more than its need? It is kept at the level of need, by D-017's standing constraint.

**The squeeze.** Three working sessions in a row were interrupted by the host's automatic content review while reading or writing this material, and the response was a series of added mechanisms (the interim leak check's extensions, PC-18 and N-109, the probe-only guard rule, FR-04's run orchestration, D-017). That is the signal of plan 6.12 item 2: question the frame before adding another mechanism.

**The test.** For each part: which criterion or Batu decision requires it; whether shrinking it lowers a requirement or only removes more than the need (plan 0.3 items 2, 5 and 10; Appendix E section 5: quality is not lowered, and the simpler solution at the same quality is preferred); and plan 6.12 item 4.

## Decision

**A. Separation between environments (C01).** The property is required (criteria 8 and 30; PC-05). Showing it by active trials against the platform tests the platform, not DevOS. What the official documentation states (counter-assessment; read 2026-10-10; no page showed a last-updated date, so the date recorded is the reading date): each session runs isolated; each environment has its own variables, secrets and network setting; the GitHub identity and the account's connectors are shared across the account. What it does not state: whether a session in one environment can act on sessions, routines or settings of another (row 17's cross-environment part); whether the credentials the platform places in a session act beyond it (N-109); which credential the session's git path uses and which repositories it can reach (row 12). So:
1. C01 establishes the separation facts the documentation states from that documentation (plan 0.3 item 12; D-017 item 2(a), 2(c)), and DevOS's own side by reading its own configuration (which environment, repositories and settings each routine has). DevOS's own enforcement (its database's role rules) is shown by its own negative tests in C02 and C03, which test DevOS's code, not the platform.
2. No active trial across environments is made. The probe environments with tokens (P1), the probe schema (P3) and the probe-only guard rule are not built. For the facts listed above, this supersedes D-017 item 2(b)'s minimal self-check: such a check is still an active trial against the platform's boundary, it tests the platform and not DevOS, it is the content that interrupted three sessions, and a design path that does not depend on the fact is available (item 4). A session's ordinary observation of itself in one environment (item 3) stays under D-017 item 2(a).
3. Ordinary platform facts that need a session started by a routine (session duration and hand-over, the tools such a session has, subagents in it, the routine limit, the skill inventory) are observed with one ordinary routine in one environment, attached to `devos` only, without tokens or connectors, recording only what that session observes about itself. Creating it is Batu's step, given to him step by step (Appendix E section 7); his C01 account steps (plan Section 12 item 0) change accordingly under PC-21.
4. **A fact the documentation does not state** is recorded as not stated, and the design takes a path that does not depend on it, named per row in PC-21 before the work that depends on it:
   - row 17's cross-environment part, before C02 builds the environments and the identity chain; the path follows row 17's own fail path (plan Section 9, C01, row 17);
   - row 12, before C04's ingestion and before C03 test 5; the paths follow row 12's own fail path (exam answers behind the exam role in the database, plan 7.3; the closing step redesigned; the account step before C03 test 5);
   - N-109, before C02 builds DevOS's environments; C00's sixth condition stays provisional on it until PC-21 names that path (`plan/work/C00.md`; plan C00, the PC-18 note).
   In each case the requirement holds because the binding enforcement sits where DevOS controls it (its database and GitHub's rules), not on the unstated platform fact; where that cannot be shown, the existing fail path applies, and any option it brings that is Batu's goes to him (below).
5. The claim is limited and recorded, per fact, as: "guaranteed by platform (documented in <source>, read <date>); not independently tested. Per environment only the variables, secrets and network setting are separate; the GitHub identity and the account's connectors are shared across the account; an environment's variables are readable inside its own sessions." The requirement is not lowered; the level of its evidence is stated (plan 8 item 7).
6. **No wholesale substitution.** PC-21 handles each affected row separately: its success condition and fail path, the old and the new text, and whether any of its results has already been seen (plan Section 14; ledger rule 3), with its own checker, as D-017 item 3 requires. The frame is decided now rather than "when that row is worked" (D-017 item 3) because the probe setup is shared by all these rows and is the first item on C01's critical path (W-C01-03); deciding row by row later would keep building the shared setup this frame removes.

**B. The installation's guard.** Its required core stays: D-008 (Batu's) and D-003's barrier until the audit environment. It is kept as it is for the installation and grows no new rule families; the probe-only rule falls with A. Its phase-B form (K-9 item 4, a [Proposal]) is sized by need at the stage that builds it: platform configuration first, to remove what must never be used; custom code only where D-008's written reasons need it. A check that runs inside the session is not counted as an authority boundary; authority lives in the tokens, the database and GitHub's rules, as K-9 item 4 already says. The service-name check stays with the guard as it is. No change to D-008 or D-003. Notes carry this to C03 and C05.

**C. The leak and credential checks.** Their required core stays: K6's code-based pre-check before public writes (criteria 8 and 31), the interim check until C04 and the phase-B check from C04. GitHub's secret scanning and push protection carry known secret types (criterion 27). The one-off C00 credential tools are spent installation scaffolding: not extended and not used further; N-109 is answered under A.4, not by them. Whether the semantic layer is kept is decided at C04 with its measurement; because Batu was told that both layers exist (plan 0.5, PC-07 note; U-6), dropping it would go to him then. The key inventory stays: it is ordinary operations, needed for revocation and restore. Notes carry this to C03 and C04.

## Second-order effects (12 to 24 months)

Fewer custom parts mean less upkeep, fewer false blocks of unattended runs and less exposure to the host's review. More of the control state lives in web settings outside git, so a periodic read-only record of the configuration is needed (carried to C06 by a note). Documentation-based claims go stale when the platform changes, so they are re-read then (plan 0.3 item 12; 6.12 item 4).
