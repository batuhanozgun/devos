# D-008

**What Batu decided** (his words are in `briefs/conversation/BATU_PERMISSION_MODEL_TR.md`; the interpretation is above). The system leaves Claude Code's auto mode. Its sessions run in "Accept edits", and the repository's own rule file decides every tool call: it allows the call, or it denies it and writes in detail what was attempted, which rule stopped it, why that rule exists and what to do instead, and it keeps a log of its decisions for audit. Every session the builder opens runs on `claude-opus-5-5` at `xhigh` effort with ultracode on, as a standing rule. Important changes keep their independent session review (operating model section 5).

**What it does not decide.** How the rules are built is the builder's technical work, item W-C00-12.6, judged by an independent session review before merge (PC-05). No action refused on 2026-10-04 is authorised by this record: L-088's refused outcome stays refused, and section 11 still governs it. The reads refused in L-090 protected nothing; reads like them are allowed (see chosen_because).

**An effect beyond his words.** The model, effort and mode are set in the repository's settings, so they also apply to sessions Batu opens on this repository himself, not only to the sessions the builder opens ("açtığın oturumlar"). That matches his text (2), "auto mode'da çalışmayalım" ("let us not work in auto mode"); he can still choose another mode for his own session in the app, and the guard applies in every mode. The effort is also set through `CLAUDE_CODE_EFFORT_LEVEL` in the settings' `env` block, which outranks a lower effort he might choose for his own session on this repository (R-D008-2 N-8).

**Residual risk, stated to Batu before he decided.** The rule file is written by the builder that it constrains. D-003 (accepted by Batu on 2026-10-02) already covers a hook the builder can edit; this decision gives that hook more weight, because no classifier stands behind it. The design item answers with independent review before merge, a merge gate that checks for the review verdict, and a written list of what is not protected.

**Update of 2026-10-05 (D-010, PC-06).** (1) A one-time exception, Batu's own decision (D-010 item 34): his conversation session runs in auto mode for about one minute, once, to start the one independent review session of the transition, and goes back to Accept edits once that session is opened. (2) The operating model named above is retired (D-010), and W-C00-12.6 closes by cancellation with W-C00-12. The merge gate's condition is now a checker (Denetçi) verdict file that names the full head SHA it judged and states its independence level ("same session, fresh-context subagent"), in place of a separate review session's verdict (`tools/merge_gate.py`, guard rule M7; summary item 28). A class-high change merges only when the pull request itself adds or changes such a file with verdict PASS or PASS-WITH-CONDITIONS, naming the head or a commit of this pull request (not one already on `main`) after which only class-normal paths change; a verdict already on `main` covers no later pull request (R-TRANS-1 B2). The gate checks the verdict file, not who wrote it; until C03 the verdict comes at this stated, lower level. Class high is decided by path (the list is in `tools/merge_gate.py`) and, in `plan/work/`, by two record triggers: deleting an item file, or changing or removing an existing acceptance block; adding a block where none existed is class normal (R-TRANS-1 B1). The old gate's other record-content triggers ended with `tools/check_records.py`: in `plan/work/`, among others, a cancelled admitted item and `depends_on`, `waits_for` or `hold_until` edits, and in `plan/ledger.md` the Stage and Governing rows. The rest of this decision stands: Accept edits, the guard deciding every call with a written reason, Opus 5.5 at ultracode effort.
