Plan Section 14 and the working order section 6 apply.

**Written after the result.** The question of the reading arose from the probe's result (EV-C00-022 section 1), so this note is written after it. The reasons below argue only from text fixed before the result; where a cited text is itself later than 2026-10-01, when the credentials were first recorded, the reason says so. Under Appendix G G8 item 3 and plan Section 14, the earlier reading of the probe stays exploratory, and the test is repeated under the reading recorded here (CHK-C00-069 condition 2). If a checker finds an easing, or that only reading B holds, the C00 close goes to a frame review (plan 6.12 item 2; working order section 6 item 3), not to a PASS.

**Labelled text.** C00's Acceptance line carries no label; no passage labelled as Batu's decision is edited; no Turkish original is touched. Criterion 25 ([Batu's decision]) is cited, not changed.

## Reasons, from text fixed before the result

1. **The condition's own term.** Its Turkish original says "gizli bilgi". Plan 2.1 uses the same term for credentials: Section 12's head, "Anahtar ve belirteç gibi gizli bilgiler hiçbir zaman sohbete yazılmaz" ("Secret information such as keys and tokens is never written into the chat"), which the condition's "or the chat" mirrors; 6.2: the publishable keys "are not secret information" ("gizli bilgi değildir"); criterion 27's secret scanning. It keeps the term apart from private content. The term means keys, tokens and passwords; which of them the condition is about is reasons 2 and 3.
2. **What C00 checks.** C00's purpose is "To see that the preparation is really complete" (Section 9, C00). The preparation handled keys issued for Batu's accounts and DevOS: "deleting the GitHub access key" (Section 12, "In preparation") and criterion 25, served by C00: "No Anthropic API key in the environment settings" (C00's criteria: 18, 21, 25–27, 29, 34); 11.1 lists among Batu's decisions "no Anthropic API key in the environment"; the key inventory that the builder keeps from C00 lists DevOS's keys and tokens (Section 12).
3. **Where the plan forbids a secret in an environment.** K-9 item 3: "Supabase's secret (service) key is never present in agent environments"; 6.3: environments get only the publishable key and their own environment token, and the builder never sees a token's value (both in plan 2.1). Plan 2.1 keeps other keys out of agent environments too: its key inventory lists the routine API trigger key ("routine API tetik anahtarı", Section 12 at `333d1b2`), and its C03 test 3 asks that there be "no secret key in the agent environment" ("ajan ortamında gizli anahtar yok", `333d1b2`). Plan 6.7's routine API trigger row says the same ("never in an agent environment", tested in C03 test 3), but that row is PC-09's text (`b17899c`, 2026-10-05T22:44Z), later than 2026-10-01.
4. **A credential visible to the session it sits in.** C01 row 3's current sentence, "If the session can see its own token, the threat model decides", with visibility "recorded as a residual risk", is PC-09's (b17899c, 2026-10-05T22:44Z), later than 2026-10-01. Plan 2.1's row (333d1b2) was stricter: the session cannot see the token by any route, and the fail path was an authenticating Edge Function gate. That row is about DevOS's own environment token, which is a secret under this note. So the row shows that the plan tolerates such visibility as a residual risk, not that such a token is not a secret; this reason supports only the handling, not the exclusion.
5. **What a ✘ condition states.** The legend of `plan/work/C00.md` (0dc0d9d, 2026-10-05T23:36Z): a ✘ condition's sentence "states what must be observed (for C00's two ✘ conditions: that the thing did not happen)". That the thing is a secret put where it shows "by the preparation or the builder" is this note's own gloss, not the legend's words.
6. **The handling before the probe** (P1). The platform's session credentials in the shell were recorded on 2026-10-01 (R-C00-BOM-5 R-1), accepted as a stated residual risk (L-023), put in the working order's "Not protected" list and the D-003 brief (L-028), and covered by Batu's acceptance of D-003's residual risk until the audit environment, re-assessed at C03. Plan Section 9 item 6 names the barrier and its limits. Before the probe, nobody treated their presence as a breach of C00's sixth condition.

## What is not shown, and the texts that point the other way

That these credentials act only within the session is not shown. The platform's undated documentation describes "a short-lived credential scoped to that session" as its design (EV-C00-022 section 1 (a)); it does not say so of the messaging token or the token file, and the probe did not test it. Texts fixed before the result point the other way (each later than 2026-10-01 is dated): the guard's B8 reason, "The session's tokens, token files and environment reach the account's other sessions and services", and F4's, "The session's credential files reach the account's other sessions and services" (`.claude/hooks/tool_allowlist.py`, from 889cb68, 2026-10-04); R-C00-BOM-5 R-1 (2026-10-01): the messaging socket and token are what `SendMessage` uses, and whether these routes reach the account's other sessions, and the scope of the other cloud credentials, were not probed; R-C00-BOM-4 B1 (filed at 5b0b176, 2026-10-03): `SendMessage` and `ListAgents` reach the account's other sessions; plan 6.7's control-surface row (PC-09, b17899c, 2026-10-05T22:44Z): the credential of opening, steering or messaging sessions is Batu's Claude account. So the exclusion holds only while they are confined to the session, and that is checked (N-109 on `plan/work/C01.md`), with its consequence fixed now.
