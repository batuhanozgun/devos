# FR-07

**Why it opened.** W-C02-03 (the migration path) had its second FAIL: CHK-C02-029 on the build (GitHub expressions inside `run:` bodies, which every offline check ran past) and CHK-C02-045 on revision H1 of its live campaign (with lenses CHK-C02-043 and CHK-C02-044). Working order section 6 item 2 and plan 6.12 item 2: a second FAIL on the same item opens a frame review before a third attempt. Between the two, a third defect of the first one's class was found on GitHub: the pull-request check could never read the migration job's run report, because every run skips two of its four jobs and GitHub answers 404 for a skipped job's log, while the offline stub listed two jobs, both run (L-304). Three fresh-context researchers worked in parallel: a premise inventory from the records, the failure class across the item's FAILs and defects, and an independent counter-assessment that read only W-C02-03's acceptance block, the plan's text and stated platform facts; a fourth weighed them (the inputs, verbatim, under `evidence/C02/raw/FR-07_*.md`). The executor decides here.

**What was found.** The premises are in the front matter (P-A to P-E). Their common frame: the campaign kept class-high merges and scheduled waits few by bundling parts made in parallel and by modelling GitHub offline, so consistency and the truth about the platform were checked only by a reader at the end. The checkers caught eight of nine defects before a merge, and the one that reached `main` failed closed: the failures were costly, not unguarded. The class is still open for the search, the next GitHub-facing code, which has never run on GitHub: its archive layout is "could not check", and no scheduled run of `migrate.yml` has yet been created (none by 2026-10-13T01:15Z, for the 00:41Z slot).

**The decision.**

1. **Before any verdict, code that needs no secret runs on GitHub.** The pull request's own check shows the workflows load and their secret-free steps behave; the search is run before its verdict by a never-merged rehearsal workflow with no environment (`issues: read`, `actions: read`, the search's own code, the plant only in base64, the unbroken copy only), on a branch based on the revision; its log is read against the expected counts. The rehearsal is exploratory: it is never T-W03-09's result. Repeatable tests replay shapes taken from GitHub, each labelled observed (seen in a run) or derived (worked out from the workflow's own text), never a shape written from belief. Before H2, H2 to H5's sequence is rehearsed with the pinned CLI on a throwaway PostgreSQL of the projects' major version where reachable (for example a service container in a never-merged workflow with no environment), the gap stated where not. H1-prime's own fixture is rehearsed the same way, in its rehearsal workflow: `main`'s migration, the fixture and every file of `supabase/migrations/tests/` on PostgreSQL 17 with Supabase's roles stubbed, because its database tests have run only on PostgreSQL 16.15 (CHK-C02-044 F4) and a failure in `devos-test` holds `go` at no until a class-high repair (CHK-C02-050 F-7).
2. **A revision is built in sequence from facts its tasks fix.** The executor writes the shared facts into every task (for H1-prime: the plant step stays in `check-devos-test`, whose reason in EV-C02-007 14.2 holds; S1, the first scheduled run after the merge, prints; S2, the second, searches; the expected count is one per job, read from S1's archive by the search's rule; S1's own logs place reads "could not check" by design; CHK-C02-045 C1's windows; T-W03-08 (e) after S2's search; and the baseline, decided before the test designer's task goes out: if by then a scheduled run of `migrate.yml` has completed whose two comparison jobs both passed the head check and ran the search, at a head before H1-prime, and its two job logs are saved unedited, the revised T-W03-09 names it as its baseline; otherwise it drops the baseline under CHK-C02-045 C4's own exception, with its reason). The producer builds first; the test designer revises the test after reading the build, before any result (the role may read the product and never writes it). Once a revision's tasks are out its scope is frozen; a finding made meanwhile outside the revision's tasks becomes its own change (defects in the revision itself are what its rehearsal and checker exist to find, and are fixed in it). The checker compares the facts in the tests with the facts in the build.
3. **The plant is made last and never held as text.** For each round the executor makes a new tag and the plants from it at the point of use, last, after the revision's other parts are judged ready; the value is never written to any file other than its planted places p1 and p2 (scratch files included), commit message, pull-request text, verdict or record; records name the tag only. Before each push the search's own counting code runs over the local clone and prints counts only; on GitHub the rehearsal counts it before the verdict, against CHK-C02-045 C2's numbers. Tag `20261012T2338Z` is retired. A separate tag per place, a repository variable, or object IDs instead of totals come in only if a second tag is spoiled. Not adopted from the counter-assessment: deriving the value inside the job from its tag (in this frame it is no safer than the base64 already used, and masking it would hide p4's printed line, which the count needs); a near-miss decoy (the search counts exact fixed strings, so a decoy tests nothing the exact counts do not); p4 in a log outside `migrate.yml` (a second workflow to keep, against item 1's "never merged" rehearsal and M22's one-workflow rule).
4. **A class guard rides on the change that can repeat the class.** For the rest of W-C02-03's campaign: when a verdict finds a class that the next change can repeat, the executor's task to the checker of that next change names the class, and its guard is a condition of that verdict, not a note. N-265 is met, not re-dated, by H0 below. Whether DevOS carries this as a rule is C05's question (note N-268).
5. **The schedule stays** (M04). S1 and S2 are planned explicitly, and the fixture track runs beside them. The trigger:
   - **When it is read.** At 2026-10-13T07:41Z, from GitHub's run list of `migrate.yml` filtered by the event `schedule`. The 06:41Z slot counts as fired if a scheduled run was created by 07:41Z (an hour late at most). Later, the schedule is "hours late" when two scheduled runs in a row are created more than an hour after their slots.
   - **Merging H1-prime before it is read.** H1-prime may merge as soon as any scheduled run of `migrate.yml` has been created (the schedule then fires); until then it does not merge before 07:41Z. Cost: if H1-prime is ready before 06:41Z and no scheduled run has yet appeared, waiting moves S1 from 06:41Z to 12:41Z and S2 from 12:41Z to 18:41Z, six hours on the critical path; the reason is that merging it before the schedule is shown would set facts (S1 and S2 as scheduled runs) that E2 would make stale, with a re-revision and a re-check.
   - **If it fires** (no scheduled run by 07:41Z, or hours late later): `workflow_dispatch` for the compare-only jobs (E2) is reopened as a design change with its own record and verdict, which also checks D-003's stated residual (if E2 changed it, that goes to Batu). H1-prime does not merge before E2's record and verdict exist. If E2 changes how S1 and S2 start, item 2's facts and T-W03-09 are revised again before any result and judged again.
   - **If no scheduled run ever fires.** Taking p4 out of the binding control (E3) does not help, because the search runs only in scheduled jobs; E2 is the only route named. If E2 is not accepted either, W-C02-03 point 9 has no route to its search: the executor records it as a blocker (working order section 7 (c)), shown in `DURUM.md`, and opens a frame review of point 9's stage; that is the builder's, unless the review would change the acceptance's scope, which is Batu's.
