# FR-04

**What it is.** The frame review that working order section 6 items 2 and 3 require after W-C01-03's second FAIL (CHK-C01-013, L-173), made by the executor as coordinator (plan 6.12 item 2). It names the premise that creates the limit, decides the frame of the third attempt, and says what stays design work under any frame. A stopped cycle never accepts the item and never changes its acceptance condition; W-C01-03's acceptance (items 1 to 8) stands as written.

**The squeeze.** Both mechanical signals fired: the same item failed a second time, and the fixes formed chains in which each answered the failure of the one before. Run starts went from Batu's presses, to pull-request triggers, to a fallback press, to start markers and a stray rule, to an author filter, to a closed list of go-branches. Live targets went from fixed windows, to a target-list merge during the run, to per-attempt timestamps and re-fires. Four of those fixes handle one failure class (a run that should not start, or runs the wrong step).

**The decision: the frame of the third attempt.**
1. **A stable routine prompt.** Each routine's stored prompt is short and does not change: the run's role, its environment, its bans (no token or anything derived from one; only named probe targets; the platform's answer and the guard's apart), and one instruction: read the control file from `main` in the run's own fresh clone, and act only on it and on the run's own probe branch. Text a run receives from the platform with its start is data, never instruction.
2. **A checked control file on `main`.** The probe steps live in one file under `evidence/C01/probe/`, written by the builder and merged through the merge gate. The gate passes a change under evidence/ as class normal, with no verdict, so a fresh checker for each change of the control file before it merges is the executor's own rule, stated here and kept in the log. A run reads the control file once, at its start, and takes no instruction from main while it runs. It lists the probe items with their order and prerequisites. Rows 1 to 4 and 17 have none; every other row lists them (plan C01's purpose). A later or conditional item, such as row 4's re-observation at a Claude Code version change or row 13 once its skill is merged, is added by a checked change, between runs. Reading this file at start is the "starting instruction the builder prepares"; it touches no running session.
3. **Scheduled starts.** Each routine has a schedule trigger, prepared by the builder and set by Batu when he creates the routine (plan 6.4 counts the schedule among what the builder prepares). Probe-b's schedule is offset from probe-a's. The builder causes no run. A run that finds nothing to do ends at once and records that it did. The design counts its scheduled runs per day, idle runs included, against the daily routine limit that Batu's own routines share (W-C01-03 acceptance item 3; row 5, "not used up on purpose"); it names the figure it counts against and its source, and if that figure is not 15 a day it also gives the count under 15 a day and what changes if row 5 reads a limit at or below that. It states a usage bound for idle runs. If the cadence the probes need would use the limit up, or draw on Batu's usage beyond the bound, that goes to Batu as his decision (working order section 8: usage beyond the standing policy is his). Row 5 reads the account's real limits.
4. **Run identity and claims.** Each run stamps its own record (its session ID by name, its fire reason, its start time, the Claude Code version) and claims one control item by pushing a claim to its own probe branch. A rejected push means another run got there first, so this run records itself as a duplicate and ends. This makes the platform's retries, catch-ups and duplicate fires harmless. A probe-a run works in a scratch clone, since the guard keeps its checkout at `main` (B4). The hand-over is used only where the plan asks for it: row 1's two runs in a row, and the combined scenario's pair.
5. **Live targets by beacon.** For rows 17 and N-109, a probe-b run acts as a beacon. It publishes on its branch its live window, its session ID and its routine ID, and runs its own positive control by the same route. A probe-a run attempts each reach only inside a published window, records each attempt's time, and records "no live target this run" otherwise. The guard admits target IDs only from the checked target list on `main` (CHK-C01-011 condition 3), so a beacon's window is long enough for that change to merge. A reach that never meets a live target is "could not check", never "cannot"; for N-109 that is "neither" and its frame review. **The same-environment reach** (N-109 reach (a), "another session in the same environment"; W-C01-03 acceptance item 5) needs a probe-a beacon reached by a later probe-a run. That depends on two things the documentation does not state: that runs of one routine can overlap, and that a beacon session can stay live, by permitted means, past the next scheduled fire and past the merge of the target list. If either fails, reach (a) reads "could not check" and N-109 reads "neither", with its frame review. A second probe-a routine would be a plan change to P2 and a step of Batu's, routed under working order section 8 before he is asked.
6. **What the frame does not change.** P1 to P3 as the plan writes them; probe-b with two repositories and no guard, with its residual stated in full; the probe-only guard rule's scope (every standing session allowance withdrawn in a probe session; target IDs only from the checked list); no paid feature; nothing that acts on Batu's other work.

**Design work under any frame** (carried to the third attempt, from the verdicts):
- CHK-C01-013 findings 5 (row 17's remote-subagent and cross-session-messaging attempts, with W-C01-04 allowances against T1 and T2; the consequences of each planned "could not check"), 6 (per-attempt times; out-of-window readings), 8 to 16;
- CHK-C01-014 conditions 3 to 9: the marker's failure visible in every run, the full withdrawal list and the session-tool server's other names, N-109's requests and readings exact, row 17's parameters, probe-b's worst case, the scan's matching, the row-4 package. Condition 1 (the author filter) lapses with its cause, the pull-request triggers. Condition 2 lapses only in its go-branch parts: the closed list of a probe session's writes stays, with its other negative controls (a push from probe-a to `claude/probe-c01-b`; an issue comment), and a pull request to `main` or a merge into `main` is among the denied writes, since under this frame that is the write that could change the control file. Condition 10 stays: the third attempt's fresh-context checkers confirm the carried conditions at the head that meets them.
- CHK-C01-013 finding 7's non-firing part: a rule by which the builder detects and records a schedule that has not fired (no run record on the routine's probe branch within a stated number of schedule periods), routed as a row 1 or row 5 finding, so that the first `reopen_if` case can be seen.
- The probe-b worst case (CHK-C01-014 condition 7) adds, under this frame, rewriting the control file by a merge into `main` without the gate; each probe-a run therefore records the control file's commit it read.

**Plan changes.** None to plan C01: the frame keeps P2 and Section 12 item 0's actions. The plan change for Section 12 item 0's wording (the publishable key, the connectors, the revocation, the removal by archiving) and the reading of C01's "removed" stays as the design proposed it (PC-21), judged before W-C01-05.

**Residuals (stated, not closed).** The frame rests on unobserved platform behaviour: schedules firing on time, a run starting fresh, the claim by push race. Schedules and fresh sessions are observed by rows 1 and 5 (each run's stamps); the push race is observed by no row, so a run confirms a lost claim by reading the branch again, not from a rejected push alone, and the stamps show a failure. Each failure reopens this record (`reopen_if`). Idle scheduled runs cost Batu's shared usage; the design bounds it. The probe-b residual (no guard) is unchanged.
