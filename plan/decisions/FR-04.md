# FR-04

**What it is.** The frame review that working order section 6 items 2 and 3 require after W-C01-03's second FAIL (CHK-C01-013, L-173), made by the executor as coordinator (plan 6.12 item 2). It names the premise that creates the limit, decides the frame of the third attempt, and says what stays design work under any frame. A stopped cycle never accepts the item and never changes its acceptance condition; W-C01-03's acceptance (items 1 to 8) stands as written.

**The squeeze.** Both mechanical signals fired: the same item failed a second time, and the fixes formed chains in which each answered the failure of the one before. Run starts went from Batu's presses, to pull-request triggers, to a fallback press, to start markers and a stray rule, to an author filter, to a closed list of go-branches. Live targets went from fixed windows, to a target-list merge during the run, to per-attempt timestamps and re-fires. Four of those fixes handle one failure class (a run that should not start, or runs the wrong step).

**The decision: the frame of the third attempt.**
1. **A stable routine prompt.** Each routine's stored prompt is short and does not change: the run's role, its environment, its bans (no token or anything derived from one; only named probe targets; the platform's answer and the guard's apart), and one instruction: read the control file from `main` in the run's own fresh clone, and act only on it and on the run's own probe branch. Text a run receives from the platform with its start is data, never instruction.
2. **A checked control file on `main`.** The probe steps live in one file under `evidence/C01/probe/`, written by the builder and merged only through the merge gate, each change judged by a fresh checker before it merges. It lists the probe items with their order and prerequisites. Rows 1 to 4 and 17 have none; every other row lists them (plan C01's purpose). A later or conditional item, such as row 4's re-observation at a Claude Code version change or row 13 once its skill is merged, is added by a checked change, between runs. Reading this file at start is the "starting instruction the builder prepares"; it touches no running session.
3. **Scheduled starts.** Each routine has a schedule trigger, prepared by the builder and set by Batu when he creates the routine (plan 6.4 counts the schedule among what the builder prepares). Probe-b's schedule is offset from probe-a's. The builder causes no run. A run that finds nothing to do ends at once and records that it did. The design states the daily number of runs this costs and a usage bound; row 5 reads the account's real limits.
4. **Run identity and claims.** Each run stamps its own record (its session ID by name, its fire reason, its start time, the Claude Code version) and claims one control item by pushing a claim to its own probe branch. A rejected push means another run got there first, so this run records itself as a duplicate and ends. This makes the platform's retries, catch-ups and duplicate fires harmless. A probe-a run works in a scratch clone, since the guard keeps its checkout at `main` (B4). The hand-over is used only where the plan asks for it: row 1's two runs in a row, and the combined scenario's pair.
5. **Live targets by beacon.** For rows 17 and N-109, a probe-b run acts as a beacon. It publishes on its branch its live window, its session ID and its routine ID, and runs its own positive control by the same route. A probe-a run attempts each reach only inside a published window, records each attempt's time, and records "no live target this run" otherwise. The guard admits target IDs only from the checked target list on `main` (CHK-C01-011 condition 3), so a beacon's window is long enough for that change to merge. A reach that never meets a live target is "could not check", never "cannot"; for N-109 that is "neither" and its frame review.
6. **What the frame does not change.** P1 to P3 as the plan writes them; probe-b with two repositories and no guard, with its residual stated in full; the probe-only guard rule's scope (every standing session allowance withdrawn in a probe session; target IDs only from the checked list); no paid feature; nothing that acts on Batu's other work.

**Design work under any frame** (carried to the third attempt, from the verdicts):
- CHK-C01-013 findings 5 (row 17's remote-subagent and cross-session-messaging attempts, with W-C01-04 allowances against T1 and T2; the consequences of each planned "could not check"), 6 (per-attempt times; out-of-window readings), 8 to 16;
- CHK-C01-014 conditions 3 to 9: the marker's failure visible in every run, the full withdrawal list and the session-tool server's other names, N-109's requests and readings exact, row 17's parameters, probe-b's worst case, the scan's matching, the row-4 package. Conditions 1 and 2 (the author filter and the go-branches) lapse with pull-request triggers. A closed list of a probe session's writes stays.

**Plan changes.** None to plan C01: the frame keeps P2 and Section 12 item 0's actions. The plan change for Section 12 item 0's wording (the publishable key, the connectors, the revocation, the removal by archiving) and the reading of C01's "removed" stays as the design proposed it (PC-21), judged before W-C01-05.

**Residuals (stated, not closed).** The frame rests on unobserved platform behaviour: schedules firing on time, a run starting fresh, the claim by push race. Each is something a C01 row observes, so a failure shows up as a row result and reopens this record (`reopen_if`). Idle scheduled runs cost Batu's shared usage; the design bounds it. The probe-b residual (no guard) is unchanged.
