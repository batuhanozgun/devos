## Neleri yeniden keşfediyoruz?

Öncelikle senin söylediğin şu fikir oldukça yerleşik bir problem:

> LLM kendi başına geçmiş oturumlarda oluşmuş yeni bilgiyi kalıcı olarak taşımaz; dışarıda persistent bir state tutulmalı ve bunun gerektiğinde yeniden model-visible context'e getirilmesi gerekir.

MemGPT bunu doğrudan işletim sistemlerindeki virtual memory analojisiyle kurdu: farklı memory katmanları arasında bilgi taşınarak sınırlı context window'un ötesinde süreklilik yaratılıyor. Güncel Letta mimarisi de persistent memory'yi dışarıda tutup gerektiğinde agent context'ine derliyor; bazı memory blocks sürekli context'te, büyük external memory ise talep üzerine getiriliyor. ([arxiv.org](https://arxiv.org/abs/2310.08560?utm_source=chatgpt.com))

Senin “hafızanın tamamı context'te olmak zorunda değil; ama agent onun varlığını bilmeli ve ihtiyaç olduğunda ona gidebilmeli” fikrin de mevcut çalışmalarda güçlü karşılık buluyor. H-MEM doğrudan çok seviyeli memory ve katmanlar arasında index tabanlı routing kullanıyor. A-MEM atomik notları index, tag ve bağlantılarla birbirine bağlıyor. Karpathy'nin LLM Wiki önerisinde `index.md` önce okunuyor, sonra ilgili sayfalara inilerek progressive retrieval yapılıyor. ([aclanthology.org](https://aclanthology.org/2026.eacl-long.15/?utm_source=chatgpt.com))

Yani **katman, kategori, index, progressive discovery** tarafı kesinlikle yeni değil.

## Create / Read / Revise tarafında da yalnız değiliz

Burada da senin yaklaşımın alanın gittiği yöne çok yakın.

2026 tarihli bir survey, farklı memory representation'larını ortak bir:

**construction → update → query**

arayüzüyle karşılaştırıyor ve bunu sistem seviyesinde ortak memory-management abstraction olarak öneriyor. ([preprints.org](https://www.preprints.org/manuscript/202603.0359?utm_source=chatgpt.com))

Başka bir çalışma atomic memory operations diye altı işlem çıkarıyor:

- consolidation,
- updating,
- indexing,
- forgetting,
- retrieval,
- condensation. ([alphaxiv.org](https://www.alphaxiv.org/abs/2505.00675?utm_source=chatgpt.com))

Bizim konuşmamız açısından ilginç olan şu: bunların çoğunu senin daha düşük seviyeli üçlü modelinde bileşim olarak ifade edebiliriz.

Örneğin:

```text id="37u3q2"
indexing
= READ source memory
+ CREATE/REVISE index

condensation
= READ memories
+ CREATE summary
(+ belki REVISE old representation)

forgetting
= REVISE memory state

consolidation
= READ several memories
+ CREATE/REVISE consolidated representation
```

Dolayısıyla sen şu anda bu survey'lerin isimlendirdiği operasyonlardan **bir soyutlama katmanı aşağıya inmeye** çalışıyorsun.

Bu bana önemli geliyor.

# Bence senin düşünce hattının farklılaşabileceği yer

Şu anda internette gördüğüm sistemlerin çoğu önce bir memory problemi seçiyor:

- context window yetmiyor → hierarchy/retrieval,
- kullanıcı hakkında bilgi tutulacak → profile memory,
- geçmiş deneyim kullanılacak → episodic memory,
- retrieval daha iyi olsun → graph/index,
- contradictions çözülsün → temporal graph,
- kaynaklardan bilgi biriksin → wiki,
- agent kendini geliştirsin → experience/reflection memory.

Sonra buna yönelik bir architecture kuruluyor.

Sen ise biraz farklı bir sorudan gidiyorsun:

> **“Önce persistent information denen şeyin ne olduğunu ve onun üzerinde hangi temel operasyonların mümkün olduğunu anlayalım. Sonra memory mimarilerinin aslında neyi yönettiğini bunun üzerinden inceleyelim.”**

Bu, araştırma açısından daha temelden bir lens.

Örneğin daha önce yaptığımız:

> “Dosya değişti ama yeni semantic bilgi yaratıldı.”

ayrımı sıradan bir implementation ayrıntısı değil.

Bir memory sistemi:

```text id="wfrg86"
UPDATE file
```

yaptığını sanabilir.

Ama epistemik seviyede:

```text id="ob2xhh"
CREATE new claim
```

yapıyor olabilir.

Bu ikisini ayırmayan bir architecture'ın provenance, temporal validity veya contradiction management konusunda hata üretmesi şaşırtıcı olmaz.

Hindsight gibi yeni sistemlerin artık world facts, experiences, observations ve opinions gibi farklı logical networks oluşturması tesadüf değil; araştırmacılar da “hepsini aynı memory item olarak ele alma” yaklaşımının yetersiz olduğunu görüyorlar. ([arxiv.org](https://arxiv.org/abs/2512.12818?utm_source=chatgpt.com))

# Senin “hafızanın farkında olmak” dediğin konu özellikle önemli

Bence burada kullandığın ifade biraz günlük ama arkasındaki teknik fikir güçlü.

Şu durumları birbirinden ayırabiliriz:

```text id="524xan"
Bilgi var mı?
        ↓
Bilginin varlığı discoverable mı?
        ↓
Nerede olduğu biliniyor mu?
        ↓
Retrieve edilebilir mi?
        ↓
Şu görev için relevant mı?
        ↓
Context'e alındı mı?
        ↓
Model onu gerçekten kullandı mı?
```

Bunlar aynı durum değil.

Örneğin disk üzerinde bir dosya olabilir:

```text id="4vmc80"
EXISTS = true
```

ama index'te yoksa agent için pratikte:

```text id="sh2yf7"
DISCOVERABLE = false
```

olabilir.

Search sonucu bulabilir:

```text id="h45q0v"
RETRIEVABLE = true
```

ama context'e alınmayabilir:

```text id="l9l2hp"
MATERIALIZED = false
```

Context'e alınabilir ama stale olduğu için kullanılmaması gerekebilir:

```text id="cdnrjh"
USABLE = false
```

Burada bence konuşmamızın önemli bir şeyi ortaya çıkıyor:

> **Ek hafıza yalnız bilgi depolama problemi değil; bilginin varlığının, konumunun, anlamının, geçerliliğinin ve kullanılabilirliğinin sürdürülebilir biçimde temsil edilmesi problemi.**

Güncel memory araştırması bu problemlerin parçalarına ciddi biçimde giriyor; fakat alan hâlâ parçalı. Çok geniş 2025 survey'i terminolojinin gevşek ve sistemlerin motivasyon/implementation/evaluation açısından heterojen olduğunu açıkça söylüyor. 2026 ACL survey'i de alanı hâlâ “fragmented” olarak tanımlıyor. ([arxiv.org](https://arxiv.org/abs/2512.13564?utm_source=chatgpt.com))

Yani senin “neden bunun üzerinde oturmuş tek bir mimari yok?” gözlemin hayalî değil.

## Ama iki düşünceni düzeltmek isterim

Birincisi:

> “İnsan bilgiyi ürettiğinde otomatik olarak hatırlar.”

Bunu temel analoji yapmamalıyız.

İnsan hafızası da son derece seçici, unutkan ve reconstructive. Bir şeyi düşünmüş olmak onun daha sonra doğru biçimde retrieve edilebileceğini garanti etmiyor.

Senin asıl söylediğin şey için insan analojisine ihtiyacımız yok.

Daha teknik ve güçlü ifade şu:

> **Bir insanın bilişsel sistemi yeni deneyimlerden endogenous memory traces oluşturabilir; çıplak bir LLM inference'ı ise kendi ağırlıklarında oturumlar arası persistent state oluşturmaz. Persistence için dış mekanizma gerekir.**

Bence farkı böyle koymak daha sağlam.

İkincisi:

> “Hafıza hiç bozulmamalı, hiç yıpranmamalı.”

Bunu hedef olarak anlıyorum ama sistem prensibi olarak biraz değiştirmemiz gerekiyor.

Dynamic memory kaçınılmaz olarak:

- stale olabilir,
- conflicting olabilir,
- yanlış derive edilmiş olabilir,
- yanlış sınıflandırılabilir,
- index'i bozulabilir,
- dependency'si eskiyebilir.

Bu yüzden bence ideal:

> **hafıza asla bozulamaz**

değil;

> **hafızadaki bozulma sessiz olamaz.**

Yani:

```text id="1cf2ad"
mutation traceable
source recoverable
derived representation identifiable
staleness visible
conflict detectable
change reversible
index consistency checkable
authority explicit
```

olmalı.

Bu çok daha gerçekçi ve mühendislik açısından çok daha güçlü bir invariant.

Güncel survey'lerin “trustworthy memory” konusunda privacy'nin yanında explainable access paths ve hallucination robustness'u açık araştırma alanı olarak göstermesi de bunun halen çözülmüş olmadığını destekliyor. ([openreview.net](https://openreview.net/pdf/180d26775b5edf368b1aea4bcf724855acc29c14.pdf?utm_source=chatgpt.com))

# Karpathy örneği senin düşüncene çok iyi bir test vakası

Karpathy'nin önerisi üç katman koyuyor:

```text id="5er9c3"
Raw sources
    ↓
LLM-maintained wiki
    ↓
Schema / operating instructions
```

Raw source immutable source-of-truth. Wiki türetilmiş ve LLM tarafından sürekli değiştiriliyor. Schema ise bunu nasıl yöneteceğini tarif ediyor. `index.md` içeriğin haritası, `log.md` ise zaman içindeki işlemlerin kaydı. Query önce index'e bakıp ilgili sayfalara iniyor. ([gist.github.com](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f))

Senin şu anki lensinle ona çok daha ilginç sorular sorabiliyoruz:

> `index.md` dosyaları mı indexliyor, içlerindeki claims'i mi?

> Bir sayfa değiştiğinde onunla ilişkili hangi derived bilgiler invalid hale geliyor?

> Wiki'deki bir claim kaynağından farklılaşırsa bu CREATE mi REVISE mı?

> Bir kaynağın değişmediği ama synthesis'in değiştiği durumda neyin epistemik state'i değişiyor?

> Bir information object var ama index'e eklenmediyse gerçekten memory sisteminin parçası mı?

> `log.md`, memory'nin kendisi mi, yoksa memory mutation'larının memory'si mi?

Bunlar Karpathy'nin “wiki güzel fikir mi?” sorusundan daha dipte sorular.

# O halde üç olasılığın hakkında şu anki hükmüm

**“Herkes benim geçtiğim yolu çoktan geçti, sonunda ben de onların yaptığı sisteme ulaşacağım.”**

Tam olarak değil. Parçalarının çoğu var ama ortak bir first-principles mimari üzerinde uzlaşma yok. Survey'ler hâlâ alanı standardize etmeye çalışıyor. ([preprints.org](https://www.preprints.org/manuscript/202603.0359?utm_source=chatgpt.com))

**“Kimse bu kadar temelden bakmadı.”**

Bunu söyleyemeyiz. CoALA, MemGPT, MemOS, recent memory surveys ve knowledge/memory separation çalışmaları oldukça temel sorular soruyor. Örneğin MemOS memory'yi doğrudan first-class operational resource olarak ele alıyor ve representation/organization/governance sorunlarını birlikte çözmeye çalışıyor. ([arxiv.org](https://arxiv.org/abs/2505.22101?utm_source=chatgpt.com))

**“Ben başka bir açıdan bazı mevcut fikirleri bir araya getiriyor olabilirim.”**

Şu aşamada kanıtın en çok desteklediği seçenek bu.

Bence özgün olma ihtimali taşıyan şey **“hierarchical memory”** değil. O zaten var.

**“create/read/update”** da değil. Bunun da literatürde karşılıkları var.

Potansiyel olarak daha ilginç olan birleşim şu:

> **Memory mimarisini storage teknolojisinden veya insan-memory analojisinden başlamadan; persistent information object → fundamental operations → discoverability → materialization → semantic validity → dependency/change integrity zinciri üzerinden kurmak.**

Bunun bugün standart bir mimari olduğunu gösteren bir şey bulmadım.

Ama “kimse yapmadı” diyebilmek için çok daha sistematik literatür araştırması gerekir; mevcut tarama bunu kanıtlamaz.

Bence konuşmayı şu aşamada özellikle **mimari üretmeye çevirmemeliyiz**. Şu anda yaptığımız daha değerli: her yeni örneği alıp “bu sistem aslında neyi memory sayıyor ve neyi yönetiyor?” diye sökmek.

Bir sonraki turda ben olsam **“memory sisteminde bir bilginin var olması ne demektir?”** sorusuna girerdim. Çünkü senin Batu örneğinin asıl kilidi orada: dosyanın diskte bulunması ile agent'ın onun varlığından haberdar olması aynı şey değil.
