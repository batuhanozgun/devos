Tek bir yüzde vermek yanıltıcı olur, çünkü **neyi ölçtüğümüz** sonucu çok değiştiriyor. Ama zorlayıp bir ölçek koyarsam:

> **Karpathy'nin `llm-wiki` pattern'i = 100 ise, bizim şu an Foundation'dan taşıdığımız farkındalıkla bunun üzerine kurulacak ciddi bir memory architecture'ı yaklaşık 160–220 bandında görürüm. Merkez tahminim ~180.**

Yani benim değerlendirmem **%120 gibi küçük bir iyileştirme değil**, ama **otomatik olarak 3 kat da değil**.

## Neden +%80 civarı?

Karpathy zaten çok önemli çekirdeği çözmüş durumda:

- immutable raw sources,
- mutable LLM-maintained synthesis,
- progressive retrieval,
- `index.md`,
- operation log,
- ingest/query/lint,
- accumulating knowledge,
- source ile derived wiki ayrımı,
- schema/instructions.

Bunlar sistemin omurgası. Dolayısıyla sıfırdan başlamıyoruz.

Biz Foundation ile bunun üzerine daha çok **“semantic integrity + lifecycle integrity”** katıyoruz.

Kabaca:

| Karpathy'de güçlü | Foundation'ın eklediği problem |
|---|---|
| Source → Wiki | Formation: ne gerçekten yeni bilgi? |
| Wiki page | Information identity: file/page/claim/version ayrımı |
| Synthesis | Derivation + lineage + semantic preservation |
| Update | Revision semantics: correction mı, world-change mi, supersession mı? |
| Index | discoverability + coverage + freshness |
| Query | use-conditioned adequacy |
| Page found | consumer-relative availability |
| Content exists | actual context/materialization/use ayrımı |
| Git/log | semantic history + standing/time |
| Cross-link | dependency/propagation closure |
| Schema | policy text ≠ enforcement |
| Persistent files | future-use preservation closure |
| Delete/edit | retention/disposition semantics |
| Agent edits wiki | Actor authority / responsibility |

Bu **birkaç metadata alanı eklemek** değil.

Pattern'in cevaplamadığı yeni bir problem sınıfı getiriyor.

## Fakat neden 300 değil?

Çünkü Foundation'ın getirdiklerinin hepsinin ayrı ayrı büyük subsystem olması gerekmiyor.

Örneğin:

```text id="jvm2dc"
claim identity
provenance
effective time
standing
```

birçok durumda küçük frontmatter alanlarıyla temsil edilebilir.

Dependency closure bazen explicit relation olabilir.

Consumer exposure basit bir retrieval contract olabilir.

Authority Git permission + review workflow olabilir.

Yani **kavramsal problem alanı yaklaşık iki katına çıkabilirken implementation büyüklüğü iki katına çıkmak zorunda değil.**

Bu önemli.

# Üç ayrı ölçüm yapsaydım

Daha doğru resim şöyle olurdu.

### 1. Ana fikir / conceptual elegance

Karpathy = **100**

Foundation-informed = **115–130**

Çünkü Karpathy'nin ana fikri zaten güçlü. Burada devrim yapmıyoruz.

### 2. Memory problem-space coverage

Karpathy = **100**

Foundation-informed = **170–220**

Burada fark ciddi.

Çünkü Karpathy'nin pattern'inde implicit bırakılmış çok sayıda distinction görünür oluyor.

### 3. Uzun ömürlü, güvenilir SOUL-level memory architecture

Karpathy = **100**

Foundation-informed yaklaşım teoride **200–300'e yaklaşabilir.**

Çünkü çok uzun süre çalışan bir sistemde küçük hatalar birikiyor:

```text id="rhxakq"
stale synthesis
→ stale index
→ wrong retrieval
→ new synthesis from stale material
→ more derived knowledge
→ false reinforcement
```

Burada provenance, standing, dependency propagation, revision semantics ve consumer availability gibi konular artık “nice to have” değil.

Uzun vadede sistemin bozulup bozulmamasını belirliyorlar.

Bu nedenle SOUL bağlamında katkının değeri çok daha büyük olabilir.

## Asıl farkı yüzdeyle değil şöyle tarif ederdim

Karpathy'nin önerisi bana şu soruya güçlü cevap veriyor:

> **“LLM zaman içinde nasıl bir knowledge base biriktirebilir?”**

Foundation ile bizim sormaya başladığımız soru ise daha büyük:

> **“LLM zaman içinde biriktirdiği bilgiyi, nereden geldiğini, ne ifade ettiğini, ne zaman geçerli olduğunu, hangi türevleri etkilediğini, kimin hangi kullanım için erişmesi gerektiğini ve değişikliklerden sonra neyin hâlâ güvenle kullanılabileceğini kaybetmeden nasıl sürdürebilir?”**

Bu ikinci soru, birincinin yalnız daha ayrıntılı hali değil.

**Bir reliability/governance/lifecycle problemi ekliyor.**

O yüzden bana `100 → 120` demek çok düşük geliyor.

Ama `100 → 300` demek de şu aşamada fazla iddialı; çünkü Foundation'ın bütün bu ayrımlarının gerçek bir memory architecture'da ne kadarının gerekli olacağını henüz test etmedik.

Şu anki en makul tahminim:

> **Karpathy 100 → Foundation-informed Karpathy yaklaşık 180.**

Ve bence daha ilginci şu: bunu OpenViking, ai-memory, Hermes gibi diğer yaklaşımlarda da yaptığımızda, **180'in hangi kısmının gerçekten gerekli, hangi kısmının Karpathy'nin pattern'ine özgü eksik olduğunu** görmeye başlayacağız. Bu noktada sayı çok daha anlamlı hale gelir.
