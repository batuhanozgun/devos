# S003 — U003'e verilen substantive cevap

---

Ayırınca yapı belirgin biçimde temizleşiyor. Önceki **10 alan aslında aynı türden 10 modül değilmiş**. İçlerinde farklı ontolojik seviyeler var.

# 1. En altta dört temel “durum alanı” var

Foundation'ın dört ground'u:

```text
WORK
ACTORS
INFORMATION
ENVIRONMENT
```

Bunları SOUL'un kurduğu çalışma sisteminin dört temel gerçeklik alanı gibi düşünmeye başladım.

- Work: ne yapılmakta/yapılabilir/gerekli/tamamlandı/bloke/reopened?
- Actors: kim/ne katılıyor, hangi rolde, neye yetkili, neyi yapabilir, neden sorumlu?
- Information: ne biliniyor/temsil ediliyor, hangi kaynak/kanıt/karar/geçmiş var, hangisi güncel/kime açık?
- Environment: gerçek çalışma koşulları; araçlar, sistemler, kaynaklar, runtime, erişim, kapasite ve dış durum.

# 2. Purpose / Target bunların beşincisi değil

Önceki modelimde Purpose'ı Work ile aynı seviyeye koymuştum. Bunu düzeltirim.

Foundation Work zaten amaçlara/sonuçlara doğru pursuits'in organize edilmesi ve evrilmesiyle ilgileniyor. Bu nedenle Purpose daha çok **Mission Contract / Intent Frame** gibi:

```text
MISSION
────────────────────────
desired target condition
scope
constraints
success criteria
failure criteria
acceptance authority
non-negotiables
```

Mission Work'e yön verir, Actor authority'yi sınırlar, önemli Information'ı ve gerekli Environment koşullarını tanımlar.

# 3. Dört temel Composition semantiği

Foundation Composition:

```text
BINDING
STANDING / QUALIFICATION
CONTROL / CONSTRAINT
TRANSITION / EFFECT / FEEDBACK
```

Bunlar dört temel alanı çalışan sisteme dönüştürüyor.

## Binding — ne neye bağlı?

Actor A assigned-to Work W; Information I supports W; Tool T available-to A; Evidence E verifies Result R. Bağ rol/scope/version/time/authority nitelikleriyle anlam kazanabilir.

## Standing / Qualification — şu anda durumu ne?

Work planned/ready/blocked/actionable/executing/reported-complete/verified/accepted/integrated gibi; Actor available/capable/authorized/assigned/claimed/live/qualified; Information current/stale/partial/verified/hypothesis/superseded/sufficient/available-to-X; Environment available/healthy/reachable/authorized/capacity-sufficient.

Bazı standings birden fazla ground'dan hesaplanır. “Bu iş şimdi yapılabilir mi?” sorusu Work prerequisites + qualified Actor + adequate Information + Environment capabilities + authority birlikteliğine bağlı olabilir.

## Control / Constraint

Kim Work yaratabilir, priority değiştirebilir, Actor atayabilir, harcama/production etkisi yapabilir, sonucu kabul edebilir, planı değiştirebilir; capability ≠ permission ≠ authority ≠ control.

## Transition / Effect / Feedback

```text
requested change
≠
attempted change
≠
actual change
≠
propagated change
≠
verified change
```

Foundation'ın Transition/Propagation, Causal Effect/Contribution, Returned Influence ve Persistent Adaptation ayrımları burada anlam kazanıyor.

```text

+
Actor

Information
+

+

Standing

──────────────

```

# Verification süreç olarak ortaya çıkıyor

Work acceptance criterion + artifact + evidence + verifier Actor + verification capability + oracle + acceptance authority üzerinden yeni standing üretilir. Verification, Information + Actors + Work + Environment + Composition kullanan süreçtir.

# Continuity / Recovery

Work/Actor/Information/Environment/Bindings/previous transitions/current standing üzerinden yeniden karar verir. Recovery özel transition/work-management davranışı; implementasyonda subsystem olabilir ama conceptual ground değil.

# Learning / Adaptation

Execution → Outcome → Observation → Failure pattern → Returned influence → method/role/control/info change proposal → verification → persistent adaptation.

Sistemin bir şey yaşaması ≠ öğrenmesi; öğrenme kaydı ≠ future behavior'ın değişmesi.

# Memory de cross-cutting

Work memory, Actor memory, Information memory, Environment history, composition history ve learned memory gibi farklı zaman-koruma işlevleri var. Persistence/history/retrieval cross-cutting capability.

# Statik ve dinamik bakış

Statik state model:


Dinamik operating loop:

```text
1. SITUATE
2. DISCOVER / PLAN
3. QUALIFY
4. CONFIGURE
5. GOVERN
6. EXECUTE
7. OBSERVE
8. VERIFY / ACCEPT
9. UPDATE / REPLAN / RECOVER
10. FEEDBACK / ADAPT
```

Bu önceki 10 kutudan daha anlamlı geliyor.

# SOUL'un rolü

İlk bakışta SOUL bu sistemin içindeki en büyük agent gibi düşünülebilirdi. Şimdi daha çok Mission, Work, roles/Actors, Information, Environment, relations/control, verification/recovery'yi **forms/configures** eden yapı gibi.

Ancak “SOUL sistemi kurduktan sonra çekiliyor mu, yoksa içinde yaşamaya devam mı ediyor?” sorusu açıldı. Büyük Work baştan bilinmediği için formation → supervision → reconfiguration → adaptation işlevleriyle **system steward** gibi davranması olası; henüz sabitlenmedi.

# Meta-work

Object Work (research/design/code/test/deploy) ile working system'i yönetmek için yapılan meta-work (plan değiştirme, Actor ekleme/değiştirme, verifier/tool/memory/control kurma, failure analysis) ayrımı çıktı.

Şu anki kompakt model:

```text
LEVEL 0 — MISSION
LEVEL 1 — SYSTEM STATE
  Work / Actors / Information / Environment
LEVEL 2 — COMPOSITION
  Binding / Standing / Control / Transition
LEVEL 3 — OPERATING LOOP
  Discover / Plan / Qualify / Configure / Govern / Execute / Observe / Verify / Accept / Recover / Replan / Adapt
LEVEL 4 — META-WORK
  Change the working system itself when evidence requires it.
```

Başlangıç sorusu “hangi modüller?” iken artık daha güçlü soru: **hangi gerçeklikler temsil edilmeli, hangi ilişkiler korunmalı ve hangi yaşam döngüsü yürütülmeli?**
