# S001 — U001'e verilen substantive cevap

Kaynak yanıtın görünür substantive aktarımı. Operasyonel routing/progress satırları arşiv gövdesine dahil edilmemiştir.

---

Bence burada gerçekten iyi bir exploration hattı var. Fakat ilk düzeltmem şu olur:

> **SOUL'un kuracağı sistemi “agent'lar + roller + işler + plan + memory” diye modellemek erken aşamada biraz fazla agent-merkezli ve biraz fazla task-manager gibi kalıyor.**

Repository'deki Foundation, work-management, context/memory/harness ve gstack araştırmalarını birlikte düşününce daha farklı bir merkez görüyorum:

> **Merkezde agent değil, gerçekleştirilmeye çalışılan bir durum ve onu gerçekleştirecek çalışma sistemi var.**

Agent bunun parçalarından biri.

# Önce senin beş maddeyi parçalayalım

Sen kabaca şunu söyledin:

1. agent'lar
2. roller
3. yapılacak iş
4. iş planı / workflow
5. memory

Bunların hiçbirine “yanlış” demem. Ama bazıları başka şeylerin altında kalıyor.

Örneğin **3 — ortada bir iş olacak** dediğimiz şeyin öncesinde bir ayrım gerekiyor:

```text
İstenen sonuç
≠
yapılması planlanan iş
≠
yapılmış iş
≠
sonucun gerçekten oluşmuş olması
```

Bu ayrım hem Foundation'da hem work-management araştırmasında hem de gstack'te tekrar tekrar karşımıza çıkıyor.

Bir agent:

> “Görevimi yaptım.”

diyebilir.

Ama hedef gerçekleşmemiş olabilir.

Dolayısıyla sistemin başlangıcı aslında:

## 1. PURPOSE / TARGET STATE

olmalı.

Yani:

- Ne meydana getirmeye çalışıyoruz?
- Neden?
- Başarının anlamı ne?
- Ne başarısızlık sayılır?
- Hangi sınırlar içinde?
- Kim bunu istemeye/yetkilendirmeye yetkili?
- Sonucun gerçekten gerçekleştiğini ne gösterecek?

Bunun ardından ancak **Work** doğuyor.

# İkinci önemli düzeltme: Agent en başta gelmeyebilir

Ben şu anda şöyle kurardım:

```text
AMAÇ
 ↓
GEREKLİ WORK
 ↓
WORK'Ü YAPABİLMEK İÇİN GEREKLİ ROL / YETENEKLER
 ↓
BU ROLLERİ GERÇEKLEŞTİRECEK ACTOR'LAR
```

Yani:

> önce agent yarat → sonra ona rol ver → sonra iş ver

yerine,

> işin ne gerektirdiğini anla → gerekli rolleri çıkar → rolleri gerçekleştirecek Actor'ları seç/yarat

daha güçlü model.

Çünkü her rolün bir AI agent olması gerekmiyor.

Bir Actor:

- bir LLM agent olabilir,
- insan olabilir,
- verifier olabilir,
- deterministic program olabilir,
- CI sistemi olabilir,
- browser/runtime olabilir,
- dış servis olabilir.

Bu bizim eski EXP-002'deki **role ≠ instance** düşüncesiyle de uyuşuyor.

Dolayısıyla senin:

> “Agent'lar olacak.”

ifaden bence exploration boyunca sorgulanmalı.

Daha güvenli başlangıç:

> **Sistemde Actors olacak; bazı Actor'lar agent olabilir.**

- schedule

- assignment

- wait

- verification

Ve bunlar birbirinin eş anlamlısı değil.

# Memory konusunda ise daha radikal bir ayrım gerekiyor

Senin 5. madden:

> hem işi unutmayacaklar, hem işin neresinde olduklarını unutmayacaklar.

Burada aslında en az üç farklı problem var.

### A. Actor memory

Actor daha önce ne öğrendi?

### B. Work state

İş şu anda nesnel olarak nerede?

### C. Execution/session state

Şu anki yürütme örneği nerede kaldı?

Bunlar aynı şey değil.

Repository'deki work-management araştırmasının çok temiz ayrımı:

```text
conversation context
≠
durable work state
≠
execution state
```

Bunu çok önemli buluyorum.

Örneğin bir agent unutabilir.

Ama proje unutmamalı.

Hatta daha ileri gidelim:

> **Sistemin doğru çalışması, agent'ın kişisel hafızasına mümkün olduğunca az bağımlı olmalı.**

Agent yeniden yaratıldığında canonical Work state'i okuyup devam edebilmeli.

Memory bunun üstüne gelir.

# Bu alanların anlamı

### 1. Purpose / Intent / Target

Sistemin niçin var olduğunu ve neyi gerçekleştirmeye çalıştığını tutar.

Bu sadece prompt değildir.

Burada:

- objective,
- scope,
- constraints,
- desired state,
- success criteria,
- acceptance,
- authority

gibi şeyler bulunabilir.

Dolayısıyla sistem sürekli yalnız “hangi task sırada?” diye değil:

> **“Hâlâ doğru sonucu mu üretmeye çalışıyoruz?”**

diye de bakabilmeli.

### 2. Work

Amacı gerçekleştirmek için yapılması gereken şeylerin yaşayan modeli.

Burada kritik kelime **living**.

Planın başta tamamen bilinmesi gerekmiyor.

```text
bilinen işler
+
keşfedilecek işler
+
bağımlılıklar
+
hazır olan işler
+
blokajlar
+
yeni ortaya çıkan işler
+
geri açılan işler
```

birlikte yaşayabilir.

EXP-001'de konuştuğumuz **yaşayan plan** fikri burada tekrar karşımıza geliyor.

### 3. Actors

“Kim yapacak?”

Ama yalnız isim listesi değil.

Bir Actor için en azından şu ayrımlar gerekebilir:

```text
role
capability
competence
authority
responsibility
assignment
claim
availability/liveness
```

Örneğin:

> “Bu agent deploy edebilir.”

ile

> “Bu agent deploy etmeye yetkilidir.”

aynı şey değil.

gstack araştırması bunu çok net gösteriyordu:

```text
participates
≠
capable
≠
authorized
≠
decision owner
```

### 4. Information

Ben bunu doğrudan `memory` olarak adlandırmazdım.

Çünkü bundan çok daha geniş.

Sistem şunlarla çalışıyor:

- kaynaklar,
- artefaktlar,
- kanıtlar,
- kararlar,
- geçmiş,
- knowledge,
- work records,
- observations,
- instructions,
- context,
- memory.

Burada ayrıca:

```text
source
provenance
version
freshness
authority
scope
confidence / standing
```

gibi nitelikler önemli.

Memory bunun bir alt problemi olur.

### 5. Environment

Senin ilk listende en belirgin eksiklerden biri bu.

Actor'ın ne bildiği yetmez.

**Gerçekte ne yapabildiği** de bilinmeli.

Örneğin:

- hangi araçlara erişebilir?
- filesystem var mı?
- browser var mı?
- hangi API'ler mevcut?
- credential var mı?
- network var mı?
- budget nedir?
- compute nedir?
- sandbox nedir?
- permissions nedir?
- runtime çalışıyor mu?
- dış sistem hangi durumda?

Bir agent'ın rolü:

> “GitHub'da PR merge et.”

olabilir.

Ama Environment'da GitHub erişimi yoksa rolün hiçbir anlamı yok.

# 6. Composition / Control bence çok kritik

Foundation'ın Composition çalışması ile gstack burada birleşiyor.

Çünkü tek tek şunların var olması sistemi oluşturmuyor:

```text
Actor
Work
Information
Environment
```

Bunların **doğru biçimde bağlanması** gerekiyor.

Örneğin:

> Hangi Actor, hangi Work item'ını, hangi Information ile, hangi Environment içinde, hangi authority altında, hangi şart gerçekleşince yapabilir?

Burada şunlar yaşayabilir:

- orchestration,
- routing,
- dispatch,
- assignment,
- admission,
- permissions,
- authority,
- sequencing,
- coordination,
- synchronization,
- handoff,
- gating,
- state transitions,
- escalation.

Bir anlamda sistemin **trafik ve kontrol düzeni**.

# 7. Verification / Qualification ayrı olmalı

Bence bunu Work'ün içine gömmemek gerekiyor.

Çünkü:

```text
work performed
≠
work correct
≠
target condition achieved
≠
evidence supports achievement
≠
authorized acceptance
```

Verifier'ın kendisi de Actor olabilir.

Ama **verification fonksiyonu** sistem düzeyinde ayrı bir sorumluluk.

# 8. Continuity / Recovery

Senin memory ihtiyacının önemli kısmı burada.

Büyük iş tek session'da bitmeyecek; Actor değişecek; context kaybolacak; model değişecek; crash olacak; yanlış dala gidilecek; iş yeniden açılacak; plan değişecek.

Yeni Actor:

> “Ne konuşulmuştu?”

diye chat geçmişini tahmin etmemeli.

Şunları recover edebilmeli:

```text
amacımız ne?
şu anda nerede kaldık?
ne tamamlandı?
ne doğrulandı?
ne başarısız oldu?
hangi işler açık?
hangi işler bloke?
hangi kararlar geçerli?
kim neye sahip?
sonraki actionable work ne?
```

# 9. Learning / Adaptation

Sistem yalnız işi yürütmemeli; büyük ve uzun işte kendi çalışma biçiminden de öğrenebilmeli.

Örneğin:

```text
aynı failure tekrarlandı
        ↓
failure pattern bulundu
        ↓
neden araştırıldı
        ↓
yeni yöntem / kontrol önerildi
        ↓
test edildi
        ↓
kabul edilirse çalışma sistemi değiştirildi
```

Ama bu “agent kendi kendini istediği gibi günceller” demek değil.

# Memory nerede kaldı?

Bu modelde memory ortadan kalkmıyor. Tam tersine daha doğru yere dağılıyor.

### Actor Memory
Bir Actor'ın öğrendiği/hatırladığı şeyler.

### Shared / System Memory
Sistemin uzun vadeli bilgi birikimi.

### Work State
İşin nesnel durumu.

### Execution State
Devam eden çalıştırmanın durumu.

### Historical Record
Ne oldu, neden oldu, hangi karar verildi.

### Learned Knowledge
Gelecekte davranışı etkileyebilecek çıkarımlar.

Bunların hepsine “memory” deyip tek kutuya koyarsak önemli ayrımları kaybedebiliriz.

# En kısa haliyle

SOUL'un ürettiği şey bir **agent takımı** değil.

Daha çok:

> **Bir amacı gerçekleştirebilecek, durumunu koruyabilecek, aktörlerini organize edebilecek, gerekli bilgiyi ve kabiliyetleri sağlayabilecek, kendi ilerlemesini ve sonuçlarını sınayabilecek bir çalışma sistemi.**

Agent takımı bunun yalnızca bir konfigürasyonu olabilir.

Basit bir işte SOUL küçük bir yapı, büyük bir işte çok daha geniş yapı kurabilir. SOUL'un başarısı her zaman çok karmaşık sistem kurması değil, **işin gerektirdiği minimum yeterli çalışma sistemini kurabilmesi** olmalı.

Bu konuşmada henüz “mimari bulduk” demiyorum. Foundation established zemin; studies gerçek mekanizma/counterexample; EXP-001/002/003 düşünce mirası. Buradaki model bunlardan türetilmiş yeni exploration hipotezi.

Doğal devam “başka hangi modülü ekleyelim?” değil; modeli büyük bir iş üzerinde zorlayıp hangi alanın gerçekten gerekli, yanlış ayrılmış veya eksik olduğunu görmek.
