# S004 — U004'e verilen substantive cevap

---

Testi **simülasyon + adversarial stress test** şeklinde yapmalıyız. Sadece “bu büyük işi bizim modelle tarif edebiliyor muyuz?” diye bakarsak model hemen her şeyi içine alabilir ve sahte başarı üretir. Modelin gerçekten kırılabilmesi gerekiyor.

## Test nesnesi

İlk vaka olarak Foundation konuşmasından tanıdığımız örneği büyütmeyi önerdim:

> **SOUL'a, sıfırdan başlayarak bir eğitim yılı boyunca kullanılacak kapsamlı bir 4. sınıf matematik soru bankası ve onu üreten/işleten çalışma sistemini kurma görevi veriliyor.**

Yalnız soru bankası değil; ihtiyacı anlama → araştırma → kapsam → üretim sistemi → ekip/agent → içerik → kalite → araç/yazılım → yayın → kullanım sonuçları → düzeltme → adaptasyon.

İş aylar sürüyor; insanlar/agent'lar var; işler başta tam bilinmiyor; dış kaynaklar, hata, Actor değişimi ve kalite kapıları var.

Gerçek ülke/mevzuat/müfredat seçmeyiz; domain araştırmasına sapmadan çalışma sistemi modelini sınarız.

# Önce modeli donduracağız

```text
LEVEL 0 — MISSION
LEVEL 1 — SYSTEM STATE
  Work / Actors / Information / Environment
LEVEL 2 — COMPOSITION
  Binding / Standing / Control / Transition
LEVEL 3 — OPERATING LOOP
  Discover / Plan / Qualify / Configure / Govern / Execute / Observe / Verify / Accept / Recover / Replan / Adapt
LEVEL 4 — META-WORK
```

Test sırasında hemen yeni kutu eklemeyiz. Problemde önce mevcut modelin kötü kullanılıp kullanılmadığını sınarız. Ancak kavramları zorlamamız, decision-critical durumları collapse etmemiz veya önemli state'i kaybetmemiz gerekiyorsa gap candidate işaretleriz.

# Beş aşamalı test

### Aşama 1 — Büyük işi sıfırdan kurdurmak

Mission → Work discovery → Work structure → roles → Actors → Information → Environment → bindings → authority/control → verification → execution.

Soru: model başlangıçta çalışma sistemi kurmaya yeterli mi?

### Aşama 2 — Sistemi gerçekten yürütmeye başlamak

Örneğin curriculum research Work yaratılır; Researcher Actor gerekir; source access sağlanır; artifact üretilir; verifier ve downstream Work oluşur. Her adımda “sistem şimdi ne biliyor ve sonra ne yapacağını nasıl biliyor?” sorusu sorulur. Cevap chat history ise model başarısızdır.

### Aşama 3 — Kasıtlı belalar

- kritik Actor kaybı,
- stale Information,
- verifier disagreement,
- late prerequisite,
- completed Work reopen,
- tool/API kaybı,
- capable but unauthorized Actor,
- Mission drift,
- green tests but bad user outcome,
- competing artifact versions,
- parallel Work invalidation,
- role structure change,
- repeated method failure.

### Aşama 4 — Gap register

| Sonuç | Anlam |
|---|---|
| Represented | Model doğal taşıyor |
| Mechanism missing | Kavram var, mekanizma eksik |
| Model ambiguity | İki farklı şey yanlış collapse |
| Candidate primitive | Doğal yeri olmayan temel ihtiyaç |

Örneğin “agent communication” hemen yeni ground değildir; Information + Binding + Environment + Transition taşıyabilir.

### Aşama 5 — Başka büyük işe taşıma

İlk fixture'a overfit riskini azaltmak için çok farklı ikinci vaka gerekir: büyük software product, fiziksel operasyon/şirket/üretim vb.

# Başarısızlık kriterleri

Model kırılmış sayılır eğer:

- önemli sistem durumunu temsil edemiyoruz;
- iki decision-critical durumu aynı state'e zorluyoruz;
- “şimdi ne yapılabilir?” cevabı yok;
- authority belli değil;
- Work completed ile Mission achieved ayrımı kayboluyor;
- Actor/session kaybından canonical state ile devam edilemiyor;
- actual effect ile kaydı ayrılamıyor;
- verification'ın neyi doğruladığı temsil edilemiyor;
- working-system değişimi normal Work kadar kontrollü yönetilemiyor.

İlk gerçek tur: SOUL ham talebi aldı; henüz hiçbir Actor/plan/sistem yok. Yalnız ham talepten çalıştırılabilir Mission ve ilk çalışma sistemi durumuna geçişi sınarız.
