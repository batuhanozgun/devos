## Test 5 — Environment ve gerçek execution

Şu ana kadar SOUL şunları yaptı:

```text
Intent
→ Mission qualification
→ gerekli koşulları keşfetme
→ Work discovery
→ Work admission
→ actionable frontier
→ capability ihtiyaçları
→ roller
→ Actors
→ Actor context'leri
```

Artık ilk kez gerçekten **dış dünyada bir şey yaptırmaya** yaklaşıyoruz.

Örneğin:

```text
W01 — Authoritative curriculum source acquisition

Actor:
A101 — Domain Research Actor

Context:
target grade
education system
academic period
source criteria
authority boundary
```

İlk bakışta eksik kalan tek şey:

> “Web aracını verelim ve başlasın.”

Ama burası beklediğimden daha karmaşık çıktı.

---

# 1. “Tool var” demek neredeyse hiçbir şey söylemiyor

Diyelim SOUL'un environment kayıtlarında şöyle bir şey var:

```text
Browser
PDF reader
Web search
Filesystem
```

Bundan:

> A101 W01'i yapabilir.

sonucunu çıkaramayız.

En azından şunlar farklı:

```text
capability required
≠
tool exists
≠
tool currently available
≠
Actor can access tool
≠
Actor has required credentials
≠
Actor is allowed to use it
≠
tool is healthy
≠
tool can produce the needed effect
```

Örneğin web browser mevcut.

Ama:

- hedef resmi siteye erişilemiyor,
- login gerekiyor,
- PDF indirmeye izin yok,
- PDF reader bozuk,
- network policy engelliyor,
- kaynak yalnız fiziksel arşivde.

Dolayısıyla Environment bir **araç katalogu** değil.

> **Environment = işin gerçekleştiği actual operating reality.**

---

# Yeni bir zincir ortaya çıktı

Actors tarafında:

```text
Work
→ capability requirement
→ role
→ Actor
```

çıkmıştı.

Environment tarafında benzer bir şey var:

```text
Work
→ capability requirement
→ candidate mechanism/tool
→ configured capability instance
→ Actor access/binding
→ actual operational standing
```

Örneğin:

```text
Need:
official document retrieval

Capability:
authenticated web access

Mechanism:
browser

Instance:
Browser Session #17

Access:
A101 can use it

Standing:
healthy / authenticated / target reachable
```

Bu ayrım önemli olabilir.

---

# 2. Authority ile Environment permission yine farklı

Diyelim Actor'ın kullandığı GitHub token'ı repository'de merge yapabilecek teknik yetkiye sahip.

Bu:

```text
TECHNICAL EFFECT POWER = YES
```

demektir.

Ama çalışma sisteminin Control tarafı:

```text
A101 MAY NOT MERGE
```

diyebilir.

Tersi de olabilir:

```text
Actor authorized to publish
BUT
required credential unavailable
```

Yani:

```text
AUTHORIZED
≠
TECHNICALLY ABLE
```

Bu ayrım SOUL'un kuracağı büyük sistem için çok temel görünüyor.

---

# 3. Readiness'i yeniden değiştirmek zorundayız

Daha önce:

```text
ACTIONABLE =
Work prerequisites satisfied
AND Information adequate
AND qualified Actor available
AND Environment supports effect
AND Control permits effect
```

demiştik.

Şimdi Environment kısmını açınca daha ayrıntılı bir standing görüyoruz.

Belki:

```text
LOGICALLY READY
```

başka,

```text
EXECUTION-ADMISSIBLE
```

başka.

Örneğin:

```text
W01

prerequisites satisfied          YES
information sufficient          YES
qualified actor                 YES
required capability known       YES
actual browser session healthy  NO
```

Bu Work mantıksal olarak ready.

Ama **şimdi çalıştırılamaz**.

Dolayısıyla:

```text
READY
≠
DISPATCHABLE
≠
EXECUTABLE NOW
```

ayrımını korumamız gerekiyor.

Work-management araştırmasındaki farklı readiness standing'lerinin niçin önemli olduğu burada çok somut hale geliyor.

---

# 4. Environment eksikse ne oluyor?

Diyelim bu işi yapmak için OCR gerekiyor fakat SOUL'da OCR capability'si yok.

İki seçenek var:

```text
A) Work'ü blocked bırak.

B) Capability acquisition Work oluştur.
```

SOUL şunu keşfedebilir:

```text
N:
PDF içeriğinin güvenilir okunabilmesi gerekiyor.

Environment gap:
No adequate PDF/OCR capability.

New Work:
W09 — acquire/build/configure adequate document-reading capability
```

Bu çok ilginç.

Çünkü SOUL sadece:

- Work,
- Actor,
- Information

üretmiyor.

**Kendi Environment'ını da işe göre genişletebiliyor.**

Senin biraz önceki:

> SOUL işe göre büyüyor

hipotezini Environment tarafı da destekliyor.

SOUL gerekirse:

- araç ekliyor,
- servis bağlıyor,
- database kuruyor,
- browser sağlıyor,
- sandbox yaratıyor,
- credential provision ediyor,
- yeni runtime hazırlıyor.

Yani “genişleme” yalnız agent eklemek değil.

---

# 5. Şimdi ilk gerçek execution başlasın

Her şey hazır diyelim.

SOUL şu binding'i oluşturdu:

```text
WORK
W01

ACTOR
A101

CONTEXT
CTX-W01-A101-v1

ENVIRONMENT
Browser Session B17
PDF capability P04

CONTROL
research access permitted
external mutation prohibited
```

Ve execution başlatıldı.

Burada yeni bir şeyin kaydına ihtiyaç duyuyoruz.

Geçici adı:

# Run / Execution Attempt

```text
R001

work      = W01
actor     = A101
context   = CTX-W01-A101-v1
tools     = B17, P04
started   = ...
standing  = RUNNING
```

Bu önemli çünkü Work ile Run aynı şey değil.

---

# Work ≠ Run

W01 bir Work.

Ama W01 birkaç kez çalıştırılabilir:

```text
W01
 ├─ R001 failed
 ├─ R002 partial
 └─ R003 succeeded
```

Aynı Work:

- retry olabilir,
- başka Actor'a devredilebilir,
- başka Environment'ta yeniden çalışabilir.

Dolayısıyla:

```text
WORK IDENTITY
≠
EXECUTION ATTEMPT
```

ayrımına ihtiyacımız var.

Bu yeni bir Foundation ground değil.

Ama **çalışma sisteminin önemli bir nesnesi** olmaya güçlü aday.

---

# Neden Run kaydı gerekli?

Çünkü birkaç dakika sonra Environment değişebilir.

Örneğin:

```text
R001 used:
curriculum source version X
browser config Y
Actor A101
context version 3
```

Bir ay sonra aynı Work yeniden yapılırsa bunların hepsi değişebilir.

Sadece:

> W01 tamamlandı.

kaydı, ne olduğunu anlamaya yetmez.

---

# 6. Tool call success ≠ Work success

Şimdi Actor browser'ı çağırdı.

```text
browser.open(...)
→ success
```

Ne biliyoruz?

Sadece browser'ın bir işlemi gerçekleştirdiğini.

Şunu bilmiyoruz:

> doğru curriculum bulundu mu?

Dolayısıyla:

```text
TOOL INVOCATION SUCCESS
≠
WORK SUCCESS
```

Bu çok temel.

---

# Daha kuvvetli bir örnek: Publication

İleride soru bankası hazır.

Actor deploy/publish aracını kullanıyor.

```text
publish(book-v3)
→ API: 200 OK
```

Naif sistem:

```text
Publication = COMPLETE
```

der.

Ama gerçekte site hâlâ `book-v2` gösteriyor olabilir:

- cache,
- asynchronous propagation,
- yanlış environment,
- yanlış artifact,
- failed downstream job.

Dolayısıyla:

```text
command accepted
≠
effect realized
≠
target condition achieved
```

---

# 7. Authoritative readback gerekiyor

İşlem yaptıktan sonra Environment'a yeniden bakmak gerekiyor.

```text
REQUESTED EFFECT
      ↓
ACTION ATTEMPT
      ↓
SYSTEM RESPONSE
      ↓
AUTHORITATIVE READBACK
      ↓
REALIZED EFFECT STANDING
```

Örneğin:

```text
publish(book-v3)
       ↓
200 OK
       ↓
GET live-site/current-version
       ↓
book-v3 confirmed
```

Ancak şimdi:

```text
REALIZED = TRUE
```

diyebiliriz.

Bu gstack araştırmasında çok güçlü biçimde gördüğümüz ayrımlardan biriydi.

---

# 8. Ama readback de son başarı değil

Canlı sitede v3 var.

Harika.

Ama:

> Öğrenciler doğru soru bankasını kullanabiliyor mu?

ayrı soru.

> İçerik doğru mu?

ayrı.

> Mission'ın hedeflediği öğrenme ihtiyacını karşılıyor mu?

daha da ayrı.

Dolayısıyla:

```text
ACTION SUCCEEDED
≠
EFFECT REALIZED
≠
WORK ACCEPTED
≠
MISSION OUTCOME ACHIEVED
```

Bu zincir sistemin her yerinde korunmak zorunda.

---

# 9. Daha tehlikeli senaryo: partial effect

Actor 10.000 sorunun bulunduğu paketi yayınlıyor.

5.000 tanesi yüklendi.

Sonra işlem çöktü.

Ne durumda?

```text
SUCCESS        NO
NO EFFECT      NO
```

Aslında:

```text
PARTIAL EFFECT
```

var.

Bu durumda kör retry tehlikeli olabilir.

Çünkü tekrar yükleme:

- duplicate kayıt,
- versiyon çatışması,
- iki farklı canlı durum

oluşturabilir.

Dolayısıyla Transition yalnız:

```text
SUCCESS / FAILURE
```

değil.

En azından:

```text
NOT ATTEMPTED
ATTEMPTING
NO EFFECT
PARTIAL EFFECT
REALIZED
UNKNOWN EFFECT
```

gibi standing'lere ihtiyaç duyabilir.

Kesin enum önermiyorum; kavramsal ayrım önemli.

---

# 10. En ilginç senaryolardan biri: Actor öldü

Şöyle düşünelim:

```text
Actor publish çağrısını yaptı.
```

Sonra bağlantı koptu.

Actor sonucu state'e yazamadan öldü.

Yeni Actor geliyor.

Repository'de son kayıt:

```text
R104 = RUNNING
```

Gerçekte ne oldu?

Bilmiyoruz.

Belki publish gerçekleşti.

Belki gerçekleşmedi.

Burada sistem:

```text
retry immediately
```

yapmamalı.

Önce:

```text
RECONCILE WITH REALITY
```

yapmalı.

Yani Environment'a bakmalı.

Bu da çok önemli.

> **Recorded execution state ile actual environment state çatıştığında Environment gözlemi yeniden standing üretmeli.**

---

# Bu durumda Continuity'nin gerçek anlamı da değişiyor

Continuity yalnız:

> “nerede kaldığımızı kaydet”

değil.

Bazen kayıt yeterli değil.

Yeni Actor'ın:

```text
canonical Work record
+
execution record
+
actual Environment observation
```

üçünü uzlaştırması gerekiyor.

Örneğin:

```text
record says RUNNING
environment says artifact LIVE
```

Sonuç:

```text
R104 probably realized
→ verify exact version
→ reconcile record
```

Bu gerçek recovery.

---

# 11. SOUL Environment'ı değiştirebilir

Burada SOUL'un büyümesi hipotezinin başka bir boyutu çıktı.

SOUL bir işi yapmak için:

```text
Actors ekliyor
Information ekliyor
Work ekliyor
```

demiştik.

Şimdi:

```text
Environment capabilities de ekliyor.
```

Örneğin soru bankası büyüdükçe:

```text
başlangıç:
filesystem + web

sonra:
database
document parser
evaluation runner
publishing system
analytics
monitoring
```

gerekebilir.

Yani SOUL'un işi yapması gerçekten:

> **kendi çalışma organizmasını material olarak genişletmesi**

gibi görünmeye devam ediyor.

---

# Şimdi daha genel resim

Bir Work'ün gerçek yürütülmesi için şu closure gerekiyor:

```text
WORK
│
├─ prerequisites satisfied
│
├─ ACTOR
│    ├ capable
│    ├ competent
│    ├ available
│    └ authorized
│
├─ INFORMATION
│    ├ available
│    ├ current
│    └ adequate
│
├─ ENVIRONMENT
│    ├ capability materialized
│    ├ access available
│    ├ healthy
│    └ sufficient
│
└─ CONTROL
     └ effect allowed
```

Sonra:

```text
EXECUTION ATTEMPT
        ↓
ACTUAL EFFECT
        ↓
OBSERVATION
        ↓
QUALIFICATION
        ↓
WORK / SYSTEM STATE UPDATE
```

Bu bana oldukça temel bir loop gibi görünmeye başladı.

---

# Gap register — Test 5

| Gözlem | Sonuç |
|---|---|
| Tool existence = capability available mı? | **Hayır.** |
| Actor technically capable = authorized mı? | **Hayır.** |
| Ready Work = executable now mı? | **Hayır.** |
| Work = execution attempt mı? | **Hayır.** |
| Run/Attempt faydalı ayrı nesne mi? | **Güçlü candidate system object.** Yeni ground değil. |
| Tool success = effect success mı? | **Hayır.** |
| Effect realized = Work accepted mı? | **Hayır.** |
| Failure = no effect mi? | **Hayır. Partial/unknown effect mümkün.** |
| Retry her zaman güvenli mi? | **Hayır. Önce reality reconciliation gerekebilir.** |
| Canonical record = actual reality mi? | **Hayır.** |
| Environment statik capability listesi mi? | **Hayır. Dynamic operating reality.** |
| SOUL Environment'ını genişletebilir mi? | **Evet, güçlü çalışma hipotezi.** |
| Yeni Foundation-level primitive çıktı mı? | **Henüz hayır.** |

---

# Şu anda önemli bir pattern oluştu

Her testte aynı yapı geri geliyor:

```text
REPRESENTATION
≠
REALITY
```

Work'te:

```text
plan
≠
actual Work
```

Actors'da:

```text
declared capability
≠
actual capability
```

Information'da:

```text
stored information
≠
current/adequate information
```

Environment'ta:

```text
declared tool
≠
actual capability
```

Execution'da:

```text
attempt record
≠
actual effect
```

Bu tesadüf olmayabilir.

SOUL'un çok temel davranışlarından biri muhtemelen sürekli:

> **Temsil ettiği dünya ile gerçek dünyanın hâlâ aynı şey olup olmadığını sınamak.**

olacak.

Bu bizi doğal olarak bir sonraki stress testine getiriyor:

# Verification / acceptance

Çünkü artık Actor'larımız gerçekten sonuç üretmeye başladı.

Şimdi en zor sorulardan biri ortaya çıkıyor:

> **SOUL ne zaman “bu iş doğru yapıldı” diyebilir?**

Orada `self-review`, bağımsız verifier, test, evidence, oracle, acceptance authority, integration ve mission outcome ayrımlarını zorlayacağız. Bu muhtemelen sistemin en kritik kontrol katmanlarından birini görünür hale getirecek.
