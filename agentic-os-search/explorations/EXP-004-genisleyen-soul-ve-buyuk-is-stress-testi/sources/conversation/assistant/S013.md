## Test 7 — Continuity / Recovery

Şimdi büyük iş varsayımımızı gerçekten kullanalım.

Proje aylardır devam ediyor. SOUL artık başlangıçtaki yapı değil; işe göre genişlemiş durumda:

```text
SOUL
├─ current Mission
├─ Work / need structures
├─ Actors + roles
├─ Information + evidence + memory
├─ Environment capabilities
├─ Controls
├─ Runs / execution attempts
├─ Qualification cases
└─ accumulated history
```

Ve aynı anda birkaç şey ters gidiyor.

### Durum

Domain Research Actor `A101` ortadan kayboluyor.

Üzerindeki `W31` şu durumda:

```text
Work:           IN PROGRESS
Last run R88:   RUNNING
Actor A101:     UNREACHABLE
```

Aynı anda başka şeyler de olmuş:

- A101 bir dış sisteme yazma işlemi başlatmış olabilir;
- işlemin gerçekleşip gerçekleşmediği bilinmiyor;
- kullandığı context'in bir kısmı eski;
- bu sırada curriculum version değişmiş;
- eski plan hâlâ eski version'a göre bazı işleri `ready` gösteriyor;
- başka bir Actor eski planın türetilmiş özetini kullanıyor.

Yeni bir Actor devralacak.

Şimdi “memory sistemi var, konuşmaları sakladık” demek bunu çözmüyor.

# İlk ayrım: Actor continuity ≠ Work continuity

A101 kayboldu.

Ama:

```text

≠
WORK LOST
```

olması gerekiyor.

Büyük sistemin kalitesi tam burada ölçülür.

Eğer W31'in ne olduğu yalnızca A101'in context window'unda yaşıyorsa sistem aslında durable değil.

Dolayısıyla Work:

```text

```

bakımından Actor'dan bağımsız yaşayabilmeli.

Bu, önceki düşüncemizi güçlendiriyor:

> **Actor değiştirilebilir olmalı; Work state Actor'ın zihnine gömülmemeli.**

# Recovery aslında ayrı bir Work doğuruyor

Sistem şunu yaratabilir:

```text

```

Bu recovery Work'ünün kendisi de:

- Information ister,
- Environment read access ister,
- yetkili Actor ister,
- verification ister.

Yani recovery gizemli bir runtime özelliği değil.

> **Recovery de Work.**

Bu pattern tekrar ediyor:

- Planning de Work.
- Work discovery de Work.
- Verification da Work.
- Recovery de Work.
- Sistem değişikliği de Work.

Bu oldukça önemli.

# Bence burada gerçekten önemli bir checkpoint'e geldik

Şimdiye kadar stress testinden çıkan yapı, ilk konuştuğumuz `agent + role + task + workflow + memory` çerçevesinden ciddi biçimde ileri gitti.

En temel sonuçlar şu hale geldi:

1. **SOUL ile kurduğu sistem arasında keskin bir ayrım olmayabilir.** Baz SOUL, Work'e göre genişleyen yaşayan bir çalışma organizmasına dönüşüyor.
2. **İlk Work object work olmayabilir.** Mission qualification, Work discovery ve system formation kendileri Work.
3. **Need / Condition ≠ Work ≠ Action.**
4. **Plan ≠ Work.** Plan, Work hakkında Information.
5. **Work baştan tamamen bilinmez.** Sürekli yeniden keşfedilebilir.
6. **Ready ≠ priority ≠ selected ≠ assigned ≠ claimed ≠ executing.**
7. **Role ≠ Actor; capability ≠ competence ≠ authority.**
8. **System Information ≠ Actor Context.**
9. **Memory ≠ Context ≠ canonical Work state.**
10. **Tool exists ≠ capability materialized ≠ Actor access ≠ authority.**
11. **Work ≠ Run / Execution Attempt.**
12. **Tool success ≠ realized effect ≠ Work success.**
13. **Work complete ≠ verified ≠ accepted ≠ integrated ≠ Mission achieved.**
14. **Verification da Work ve claim/criterion-specific.**
15. **Acceptance epistemik truth yaratmıyor; progression authority yaratıyor.**
16. **Persistence ≠ continuity.**
17. **Handoff ≠ source of truth.**
18. **Recovery actual reality ile reconciliation gerektirebilir.**
19. **Binding yalnız ilişki değil; freshness, invalidation ve change-impact için kritik.**
20. **SOUL'un önemli bir işi object work kadar meta-work: kendi çalışma sistemini oluşturmak, düzeltmek ve yeniden yapılandırmak.**

Ve stress test boyunca Foundation'ın dört ground'u ile Composition yapısı **henüz kırılmadı**:

```text
Work
Actors
Information
Environment

+

Binding
Standing / Qualification
Control / Constraint
Transition / Effect / Feedback
```

Yeni runtime nesneler çıkıyor — örneğin `Run / Execution Attempt`, `Qualification Case` — ama bunlar şu ana kadar yeni foundational ground gerektirmedi.
