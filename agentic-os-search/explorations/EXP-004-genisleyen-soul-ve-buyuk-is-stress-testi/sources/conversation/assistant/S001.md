# Önce senin beş maddeyi parçalayalım

Sen kabaca şunu söyledin:

1. agent'lar
2. roller

4. iş planı / workflow
5. memory

Bunların hiçbirine “yanlış” demem. Ama bazıları başka şeylerin altında kalıyor.

Örneğin **3 — ortada bir iş olacak** dediğimiz şeyin öncesinde bir ayrım gerekiyor:

```text
İstenen sonuç
≠
yapılması planlanan iş
≠
yapılmış iş
≠
sonucun gerçekten oluşmuş olması
```

Bu ayrım hem Foundation'da hem work-management araştırmasında hem de gstack'te tekrar tekrar karşımıza çıkıyor.

Bir agent:

> “Görevimi yaptım.”

diyebilir.

Dolayısıyla sistemin başlangıcı aslında:

## 1. PURPOSE / TARGET STATE

olmalı.

- Ne meydana getirmeye çalışıyoruz?
- Neden?
- Başarının anlamı ne?
- Ne başarısızlık sayılır?

# Bu alanların anlamı

### 1. Purpose / Intent / Target

Sistemin niçin var olduğunu ve neyi gerçekleştirmeye çalıştığını tutar.

Bu sadece prompt değildir.

Burada:

- objective,
- scope,
- constraints,
- desired state,
- success criteria,
- acceptance,
- authority

gibi şeyler bulunabilir.

---

### 2. Work

Amacı gerçekleştirmek için yapılması gereken şeylerin yaşayan modeli.

Burada kritik kelime **living**.

Planın başta tamamen bilinmesi gerekmiyor.

```text
bilinen işler
+
keşfedilecek işler
+
bağımlılıklar
+
hazır olan işler
+
blokajlar
+
yeni ortaya çıkan işler
+
geri açılan işler
```

birlikte yaşayabilir.

EXP-001'de konuştuğumuz **yaşayan plan** fikri burada tekrar karşımıza geliyor.

---

### 3. Actors

“Kim yapacak?”

Ama yalnız isim listesi değil.

Bir Actor için en azından şu ayrımlar gerekebilir:

```text
role
capability
competence
authority
responsibility
assignment
claim
availability/liveness
```

Örneğin:

> “Bu agent deploy edebilir.”

ile

> “Bu agent deploy etmeye yetkilidir.”

aynı şey değil.

gstack araştırması bunu çok net gösteriyordu:

```text
participates
≠
capable
≠
authorized
≠
decision owner
```

### 4. Information

Ben bunu doğrudan `memory` olarak adlandırmazdım.

Çünkü bundan çok daha geniş.

Sistem şunlarla çalışıyor:

- artefaktlar,
- kanıtlar,
- kararlar,
- geçmiş,

### 5. Environment

Senin ilk listende en belirgin eksiklerden biri bu.

Actor'ın ne bildiği yetmez.

**Gerçekte ne yapabildiği** de bilinmeli.

Örneğin:

- hangi araçlara erişebilir?
- filesystem var mı?
- browser var mı?
- hangi API'ler mevcut?
- credential var mı?
- network var mı?
- budget nedir?
- compute nedir?
- sandbox nedir?
- permissions nedir?
- runtime çalışıyor mu?
- dış sistem hangi durumda?

Bir agent'ın rolü:

> “GitHub'da PR merge et.”

olabilir.

Ama Environment'da GitHub erişimi yoksa rolün hiçbir anlamı yok.

# 6. Composition / Control bence çok kritik

Foundation'ın Composition çalışması ile gstack burada birleşiyor.

Çünkü tek tek şunların var olması sistemi oluşturmuyor:

```text
Actor
Work
Information
Environment
```

Bunların **doğru biçimde bağlanması** gerekiyor.

Örneğin:

```text
hangi Actor
hangi Work'ü
hangi authority ile
hangi Information'ı kullanarak
hangi Environment içinde
hangi şart gerçekleştiğinde
hangi effect'i üretmek üzere
yapacak?
```

İşte bence Harness tartışmasının önemli bir kısmı burada gerçekleşiyor.

Harness tek başına bu plane değildir ama bunun birçok mekanizmasını **operationalize** edebilir.

Burada:

- dispatch,
- orchestration,
- admission,
- handoff,
- permissions,
- gating,
- transitions,
- routing,
- coordination

gibi mekanizmalar bulunabilir.

# 7. Verification / Qualification ayrı olmalı

Bence bunu Work'ün içine gömmemek gerekiyor.

Çünkü:

```text

≠
work correct
≠
target condition achieved
≠
evidence supports achievement
≠
authorized acceptance
```

Verifier'ın kendisi de Actor olabilir.

Ama **verification fonksiyonu** sistem düzeyinde ayrı bir sorumluluk.

Bunun içinde:

- tests,
- review,
- critics,
- independent checks,
- authoritative readback,
- acceptance criteria,
- evidence

olabilir.

---

# 8. Continuity / Recovery

Senin memory ihtiyacının önemli kısmı aslında burada.

Sistem şu olaylardan sağ çıkabilmeli:

- agent ölür,
- session kapanır,
- model değişir,
- başka agent devralır,
- iş bloke olur,
- plan değişir,
- hata bulunur,
- tamamlanmış iş yeniden açılır,
- environment değişir.

Yeni Actor'ın:

> “Önceki konuşmada ne vardı acaba?”

diye chat history'ye bağımlı olması yerine:

```text
canonical target
canonical work state
canonical artifacts
current standing
current responsibilities
next actionable work
```

geri kazanılabilmeli.

---

# 9. Learning / Adaptation

Bu da memory ile aynı şey değil.

Geçmişin tutulması başka şey:

> sistemin geçmişten dolayı davranışını değiştirmesi

başka şey.

Örneğin sistem sürekli aynı tür hatayı yapıyorsa:

```text
incident
→ diagnosis
→ reusable lesson
→ method/control change proposal
→ validation
→ accepted change
```

şeklinde bir meta-work oluşabilir.

EXP-001–003 hattının bazı fikirleri ve gstack'in self-development mekanizmaları burada buluşuyor.

Ama otomatik self-improvement varsaymamak lazım. Değişiklik de normal Work gibi doğrulanmalı.

# Bunları birleştirince benim için daha temel model şu oluyor

SOUL'un ürettiği şey bir **agent takımı** değil.

Daha çok:

> **Bir amacı gerçekleştirebilecek, durumunu koruyabilecek, aktörlerini organize edebilecek, gerekli bilgiyi ve kabiliyetleri sağlayabilecek, kendi ilerlemesini ve sonuçlarını sınayabilecek bir çalışma sistemi.**

Agent takımı bunun yalnızca bir konfigürasyonu olabilir.

Mesela basit bir işte SOUL şunu kurabilir:

```text
1 Actor
1 Work item
local context
2 tools
1 deterministic test
```

Büyük bir işte ise:

```text
multiple Actors
role separation
dependency graph
persistent work substrate
memory
RAG
artifact store
review agents
human approval gates
browser/runtime
CI
issue tracker
recovery
monitoring
```

kurabilir.

Yani SOUL'un başarısı:

> **her zaman çok karmaşık sistem kurması**

değil,

> **işin gerektirdiği minimum yeterli çalışma sistemini kurabilmesi**

olmalı.

Bu ayrımı önemli buluyorum.

# SOUL ile oluşturduğu sistem arasındaki ilişki de böyle görünmeye başladı

Burada bence iki katman var:

```text
SOUL
│
│ anlayacak
│ tasarlayacak
│ oluşturacak
│ doğrulayacak
│ gerektiğinde değiştirecek
▼
GENERATED WORK SYSTEM
│
├─ Purpose
├─ Work
├─ Actors
├─ Information
├─ Environment
├─ Composition / Control
├─ Verification
├─ Continuity / Recovery
└─ Learning / Adaptation
```

Fakat aşağıdaki kutular **sabit software modules olmak zorunda değil**.

Bence SOUL'un sabit taşıması gereken şey daha çok şu soruları sorabilme kapasitesi:

1. Ne gerçekleştirmeye çalışıyoruz?
2. Bunun için hangi Work gerekli?
3. Hangi Work henüz bilinmiyor?
4. Hangi Actor/rol/yetenek gerekiyor?
5. Actor'ın hangi Information'a ihtiyacı var?
6. Gerçek Environment bunu yapmaya izin veriyor mu?
7. Bunları birbirine hangi kontrol ilişkileri bağlamalı?
8. İşin yapılmış değil, **başarılı olmuş** olduğunu nasıl bileceğiz?
9. Kesinti/değişiklik olduğunda nasıl devam edeceğiz?
10. Deneyim gelecekteki sistemi değiştirmeli mi?

Bana şu anda **SOUL'un üreteceği yapının ilk ciddi iskeleti** bunlarmış gibi geliyor.

Ve önemli olan şu: bunu doğrudan “mimari bulduk” diye okumuyorum. Foundation established zemin sağlıyor; work-management, gstack, context-memory-harness ve Superpowers bize gerçek mekanizma/counterexample veriyor; EXP-001/002/003 ise düşünce mirasını sağlıyor. Buradaki model bunlardan türetilmiş **yeni exploration hipotezi**.

Bence bu konuşmanın doğal devamı da artık “başka hangi modülü ekleyelim?” değil. Bir sonraki turda bu modeli **zorlamamız** daha verimli olur: örneğin bir muhasebe denetimi, bir yazılım ürünü geliştirme, bir araştırma projesi veya çok daha basit bir iş seçip bu dokuz alanın hangilerinin gerçekten gerekli olduğunu, hangilerinin yanlış ayrıldığını, hangisinin eksik kaldığını görelim. Böyle yaparsak liste yapmaktan sistem modeline geçmeye başlarız.

Bu turda repository'ye herhangi bir kayıt yazmadım; şu anki statüsü **yeni exploration için güçlü aday düşünce hattı**, kabul edilmiş SOUL mimarisi değil.
