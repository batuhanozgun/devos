## 1. Purpose / Target

Bütün sistemin yönünü belirleyen şey.

Sadece “yapılacak iş” değil:

- ne gerçekleştirilmek isteniyor,
- neden,
- kapsam ne,
- sınırlar ne,
- başarı nedir,
- başarısızlık nedir,
- kabulü kim yapar,
- hangi constraint'ler ihlal edilemez.

Dolayısıyla sistem sürekli yalnız “hangi task sırada?” diye değil:

> **“Hâlâ doğru sonucu mu üretmeye çalışıyoruz?”**

diye de bakabilmeli.

---

## 2. Work System

Büyük işi temsil eden yaşayan yapı.

Senin söylediğin:

> hangi parçanın önce/sonra yapılacağı, bağımlılıkları, planı...

burada.

Ama task list'ten daha geniş:

```text
işler
alt işler
hedefler
deliverable'lar
dependencies
prerequisites
blockers
readiness
priority
schedule
milestones
unknown work
discovered work
replanning
reopening
retry
revision
backtracking
completion state
```

Önemli nokta:

> **Plan başta tamamen bilinmek zorunda değil.**

Sistem çalıştıkça Work modeli değişebilir.

---

## 3. Actors

İşi gerçekleştirecek katılımcılar.

Bunların bazıları agent olabilir ama hepsinin agent olması gerekmiyor.

Büyük bir sistemde:

- planner,
- researcher,
- builder,
- reviewer,
- verifier,
- integrator,
- coordinator,
- human decision-maker,
- deterministic tool/service

gibi farklı Actor'lar olabilir.

Ve her Actor için sadece rol adı değil:

```text
role
responsibility
capability
competence
authority
assignment
ownership
availability
current state
```

gibi şeyler gerekebilir.

Özellikle:

```text
yapabiliyor
≠
görevlendirildi
≠
yetkili
≠
sorumlu
```

ayrımını korumamız gerekiyor.

---

## 4. Information

Bütün çalışma boyunca ihtiyaç duyulan bilgi dünyası.

Burayı `memory`den daha büyük düşünüyorum.

İçinde:

- kaynaklar,
- araştırmalar,
- spesifikasyonlar,
- kararlar,
- artefaktlar,
- kanıtlar,
- geçmiş,
- observations,
- instructions,
- work records,
- knowledge,
- context,
- actor memory,
- learned information

bulunabilir.

Ayrıca bilginin yalnız içeriği değil:

```text
nereden geldi?
hangi sürüm?
güncel mi?
hangi kapsamda doğru?
kim üretti?
kanıt mı, hipotez mi?
hangi Actor'a gösterilmeli?
```

soruları da burada.

---

## 5. Environment

Actors'ın gerçek çalışma dünyası.

Örneğin:

- tools,
- APIs,
- filesystem,
- GitHub,
- databases,
- browsers,
- compute,
- network,
- credentials,
- permissions,
- sandbox,
- runtime,
- budget,
- available models,
- dış sistemlerin gerçek durumu.

Çünkü:

> Actor'ın bir işi yapmayı bilmesi, onu yapabilecek ortamın mevcut olduğu anlamına gelmiyor.

---

# İlk beş alan bize dünyanın parçalarını veriyor

Kabaca:

```text
Purpose      → Neyi gerçekleştirmeliyiz?
Work         → Bunun için ne yapılmalı?
Actors       → Kim/ne yapacak?
Information  → Neyi bilmeleri gerekiyor?
Environment  → Gerçekte neyle/ne şartlarda çalışabiliyorlar?
```

Ama bunların yan yana durması henüz çalışan sistem oluşturmuyor.

Bu nedenle ikinci grup geliyor.

---

# 6. Composition / Control

Bence büyük sistemlerde en kritik alanlardan biri.

Parçaları birbirine bağlıyor.

Örneğin:

> Hangi Actor, hangi Work item'ını, hangi Information ile, hangi Environment içinde, hangi authority altında, hangi şart gerçekleşince yapabilir?

Burada şunlar yaşayabilir:

- orchestration,
- routing,
- dispatch,
- assignment,
- admission,
- permissions,
- authority,
- sequencing,
- coordination,
- synchronization,
- handoff,
- gating,
- state transitions,
- escalation.

Bir anlamda sistemin **trafik ve kontrol düzeni**.

---

# 7. Execution

Planın ve kontrol yapısının gerçek aksiyona dönüştüğü yer.

Burada:

```text
Actor seçildi
→ context hazırlandı
→ tools verildi
→ work başlatıldı
→ aksiyonlar gerçekleşti
→ sonuç/artifact oluştu
```

gibi gerçek yürütme var.

Bunu Work'ten ayırıyorum çünkü:

> İşin plan üzerinde var olması başka, fiilen çalıştırılıyor olması başka.

Aynı şekilde:

```text
work state
≠
execution/session state
```

---

# 8. Verification / Acceptance

Büyük işte zorunlu görüyorum.

Actor:

> “Bitti.”

dediğinde sistemin bunu gerçek kabul etmemesi gerekiyor.

Ayrımlar:

```text
Actor tamamladığını söyledi
≠
çıktı mevcut
≠
çıktı doğru
≠
diğer parçalarla entegre
≠
hedef durumu gerçekleşti
≠
yetkili taraf kabul etti
```

Burada:

- tests,
- reviews,
- critics,
- independent verifiers,
- quality gates,
- acceptance criteria,
- evidence,
- authoritative readback

gibi mekanizmalar olabilir.

---

# 9. Continuity / Recovery

Senin ilk söylediğin memory ihtiyacının önemli bölümü burada.

Büyük iş:

- tek session'da bitmeyecek,
- Actor değişecek,
- context kaybolacak,
- model değişecek,
- crash olacak,
- yanlış bir dala gidilecek,
- iş yeniden açılacak,
- plan değişecek.

Sistem buna dayanabilmeli.

Yeni Actor geldiğinde:

> “Ne konuşulmuştu?”

diye chat geçmişini tahmin etmemeli.

Şunları recover edebilmeli:

```text
amacımız ne?
şu anda nerede kaldık?
ne tamamlandı?
ne doğrulandı?
ne başarısız oldu?
hangi işler açık?
hangi işler bloke?
hangi kararlar geçerli?
kim neye sahip?
sonraki actionable work ne?
```

Burada **durable work state** özellikle kritik.

---

# 10. Learning / Adaptation

Sistem yalnız işi yürütmemeli; büyük ve uzun işte kendi çalışma biçiminden de öğrenebilmeli.

Örneğin:

```text
aynı failure tekrarlandı
        ↓
failure pattern bulundu
        ↓
neden araştırıldı
        ↓
yeni yöntem / kontrol önerildi
        ↓
test edildi
        ↓
kabul edilirse çalışma sistemi değiştirildi
```

Ama bu:

> “Agent kendi kendini istediği gibi günceller.”

demek değil.

Learning'in de kendi Work, authority ve verification süreci olması gerekir.

---

# Memory nerede kaldı?

Bu modelde memory ortadan kalkmıyor. Tam tersine daha doğru yere dağılıyor.

### Actor Memory
Bir Actor'ın öğrendiği/hatırladığı şeyler.

### Shared / System Memory
Sistemin uzun vadeli bilgi birikimi.

### Work State
İşin nesnel durumu.

### Execution State
Devam eden çalıştırmanın durumu.

### Historical Record
Ne oldu, neden oldu, hangi karar verildi.

### Learned Knowledge
Gelecekte davranışı etkileyebilecek çıkarımlar.

Bunların hepsine “memory” deyip tek kutuya koyarsak önemli ayrımları kaybedebiliriz.

# Senin ilk listenle eşleştirirsek

| Senin başlangıcın | Şu anki karşılığı |
|---|---|
| Agent'lar | **Actors** |
| Rol tanımları | **Actors içindeki role/capability/authority/responsibility** |
| Ortada iş olacak | **Purpose + Work** |
| İş planı/workflow | **Work System + Composition/Control** |
| Memory | **Information + Continuity/Recovery + bazı Actor/Learning mekanizmaları** |

Ve repository'nin bize eklettiği önemli parçalar:

| Eklenen alan | Neden |
|---|---|
| **Purpose/Target** | İş yapmak ile hedefe ulaşmayı ayırmak için |
| **Environment** | Gerçek capability ve koşulları temsil etmek için |
| **Composition/Control** | Bütün parçaları çalışan sisteme dönüştürmek için |
| **Execution** | Plan ile gerçek yürütmeyi ayırmak için |
| **Verification/Acceptance** | “yapıldı” ile “doğru/başarılı”yı ayırmak için |
| **Continuity/Recovery** | Uzun soluklu işi session/Actor değişiminden bağımsızlaştırmak için |
| **Learning/Adaptation** | Uzun çalışma boyunca sistemin yöntemini kontrollü geliştirebilmek için |

## En kısa haliyle

Ben şu anda SOUL'un büyük bir iş için kurduğu sistemi şöyle düşünüyorum:

> **Bir hedefi temsil eden; işi keşfedip örgütleyen; gerekli Actor'ları, bilgi ve çalışma ortamını sağlayan; bunları yetki ve kontrol ilişkileriyle birbirine bağlayan; işi gerçekten yürüten; sonuçları doğrulayan; uzun zaman boyunca durumunu koruyup hatalardan geri dönebilen ve gerektiğinde kendi çalışma biçimini kontrollü olarak geliştirebilen bir sistem.**

Bence bundan sonraki konuşmada asıl ilginç soru şu olacak: **Bu on alan gerçekten aynı seviyede mi?** Muhtemelen değil. Bazıları sistemin temel “varlıkları”, bazıları bunların üzerinde çalışan “mekanizmalar”, bazıları ise yaşam döngüsü fonksiyonları. Orayı ayırdığımızda yapı belirgin biçimde temizlenebilir.
