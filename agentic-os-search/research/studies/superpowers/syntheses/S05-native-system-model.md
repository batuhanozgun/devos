## 2. What kind of system this is

The best-supported source-level description is:

**A portable development methodology, expressed through composable skill and role contracts, interpreted by host-provided agents and tools, supported by concrete adapters, file/Git helpers and an optional visual runtime, with a separately operated method-development/evaluation process.**

This formulation avoids three reductions:

- **Only prompts:** omits executable adapters, artifact helpers, companion access/process logic and distribution tooling.
- **A complete autonomous operating runtime:** assigns the package host/model capabilities and enforcement it does not itself implement at the inspected surfaces.
- **One linear SDLC:** erases the three request paths, diagnosis/review entries, alternate execution, correction/adjudication and human integration choices.

The source distributes responsibility rather than eliminating judgment. Some conditions are checked by code; many are instructions to an agent; some require a human or host. An emphatic rule is not automatically a capability restriction, and a code-level check is not automatically semantic validation. [S02–S04]

## 3. Two connected loops

### The development-work loop

An actor receives available guidance and determines what kind of request is being handled. Building may use brainstorming's spike, bounded or architectural route. Bug investigation can enter through debugging; a review request need not instantiate the architectural build flow. [S03 §1]

For architectural work, the source connects human-reviewed intent/specification to a plan, actual execution workspace, task briefs, implementer reports, scoped reviews and controller decisions. SDD keeps ordinary implementation workers serial, with permitted batching of same-shape micro-work. The separate parallel-dispatch skill is for independent domains; a task number does not prove safe parallel execution. [S03 §§2–5; S04 §§1–3; U03 F24]

Tests and diagnosis operate inside this loop, not only at its end. A review gap can return to context selection; a blocker can trigger decomposition or a plan ruling; a repeated failure changes the actor/model or ends in qualified adjudication. Finishing then introduces a new human decision and new objects—merged state, remote ref, PR and retained records. [S04]

### The method-change loop

Observed work can motivate a skill change, but not every problem calls for more prose. Authoring distinguishes intervention types and compares behavior under defined conditions. A separate lab can prepare sources, collect evidence, run checks, obtain an assessor report and compose pass/fail/indeterminate. Human/maintainer admission and actual distribution remain separate from a valid evaluation result. [S01; S02 §3]

These loops meet at two places: observations from doing work can inform method development, and an admitted distributed revision can change later work. The study has not found or demonstrated a universal automatic self-improvement loop that captures every run, revises skills and safely deploys them. The linkage is a combination of instructions, tools and human operation, not an autonomous background service inferred from the diagram.

## 4. The controller does more than schedule

In SDD, the controller selects the route, reads plan/spec/globals, constructs task context, retains BASE, routes worker results, supplies reviewer constraints, resolves what the reviewer cannot verify, records decisions, carries parked findings forward and discloses them at the end. [S30; S03 §§2–4; S04 §§2–3/7]

That allocation explains both a strength and a dependency. File-backed handoffs and narrow contexts can avoid repeatedly transmitting the whole session. But the necessary cross-task meaning must still be selected and preserved. A task extractor cannot decide every applicable global requirement; a reviewer cannot assess evidence it was never given; a completion line cannot establish that a changed plan is the same obligation.

This is not a proven root cause of every observed limit or a claim that controllers inevitably fail. It is a source-supported account of where semantic integration remains necessary. Alternatives remain possible: a defect may arise in a helper, a host lifetime, an input, a model decision or a consumer's interpretation. Earlier experiments localize particular behaviors; synthesis must not combine them into an unmeasured universal failure theory.

## 5. Authority is stage- and action-dependent

The source explicitly gives user instructions priority over skills. Within SDD it treats the spec as binding and the plan as its argument. Ordinary execution ambiguity can be settled by a recorded controller ruling, while named stop classes return to the human. The alternate executing-plans skill stops on a broader set of blockers. Integration and discard require separate human choices. Contributor admission concerns another change object: the method itself. [S04/S10/S30/S31/S55 source IDs; S01/S03/S04]

Consequently, these are not interchangeable:

`approved intent`, `a controller ruling`, `task review approval`, `permission to publish`, and `maintainer acceptance of a skill change`.

Neither shared-key access to the companion nor a browser click establishes those authorities. A file path or directory convention similarly cannot identify every ownership/consent fact. [U07-A F65–F70; U05 F38–F41]

The package has real priorities, but not a fully specified universal arbiter for every overlap. The next section records what can and cannot be resolved from the inspected texts.

## 7. Four dimensions should not be compressed into one success fact

The combined explanation distinguishes:

- **What is present or observable:** installed files, a displayed screen, a report or a test result.
- **What it means for this work:** applicable requirements, selected state, defect resolution and residual risk.
- **Who can authorize the next action:** human, controller under its contract, host policy or maintainer.
- **What actually happened afterward:** files changed, merge completed, artifact published, records retained or the active session refreshed.

This is an analytical lens, not a proposed four-field database schema. The source examples demonstrate why the distinctions matter: a successful output envelope can lack a usable body; a valid diff can be the wrong range; a clicked option can be deselected; an audit can be advisory; an assessor can emit a valid but disputed judgment. Different examples exclude different overstrong inferences, not every use of those mechanisms. [S01–S04]

The recurring problem is preserving qualification at handoff. A producer can supply a useful but limited result; a consumer can mistakenly interpret it as broader. That pattern is a synthesis across bounded observations and attributed reports, not an independently measured prevalence estimate or a single established root cause.

## 8. Light process is not automatically light coordination

The bounded route supplies a useful counterweight to an SDD-centered account. It deliberately avoids the full plan ceremony. SDD's plan-backed brief/ledger/delegation chain therefore cannot be assumed to apply unchanged to every bounded task. Shorter preparation, lower controller-context consumption and better task quality are distinct objectives. [S03 §6]

The separately fetched issue #2203 describes main-session context pressure under a reported v6.3.0 setup, without a transcript. Its comments explicitly distinguish that concern from bad work; the reporter does not claim the latter. A host-policy explanation is suggested but not independently validated. The report is a source for a user's observation and a useful rival hypothesis, not a benchmark or authenticated primary-commit run. [I01/I02]

This challenge refines the model without importing an untested fix: ceremony, context isolation, verification effort and decision authority can vary independently. Choosing fewer artifacts is not proof of lower total cost, and choosing more subagents is not proof of better outcomes. A future comparison must state which objective it is measuring.

## 9. Positive explanatory content and countermodel checks

The study supports concrete positive mechanisms: scalable design preparation; testable task boundaries and interfaces; file-backed context handoffs; reviewer anti-anchoring instructions; coverage escalation; hypothesis-led diagnosis; recorded disagreement rather than silent discard; integrated-state retesting; human integration choice; method-change comparisons; structured evaluation reports; and channel-specific assembly controls. [S01–S04]

A first reverse check compared the model to previously less-central families. Native-discovery hosts prevent an injection-only account. Bounded/spike paths prevent an all-SDD account. Optional visual support prevents a terminal-only account but does not become approval authority. Packaging prevents a source-SHA-only identity model. Separate evaluation prevents treating a valid report as proof of end-user effectiveness. Existing helpers prevent reducing everything to unenforced prose.

These are source-directed countermodel checks by the same research agent, not independent replication or the final freshness/omission closure. The model deliberately does not explain every historical issue or assert the latest upstream state. Any stronger claim can reopen its relevant source family.
