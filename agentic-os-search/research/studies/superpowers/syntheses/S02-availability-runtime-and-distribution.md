## 1. Native explanation

Superpowers makes shared development procedures available through host-specific integrations and supplements them with selected executable helpers. Its portability rests on sharing guidance while adapting discovery, context delivery and actions to the host. It does not supply the same custom injector or the same operational guarantees everywhere. [U01-B F07–F10; U07-B F77]

A useful explanatory chain is:

`chosen source/channel → assembled or acquired files → host/module/session activation → discovery and relevant guidance loading → host-native action → observed result`.

These are distinctions between transitions, not a claim that every host implements a separate component for each arrow. Native discovery, shell hooks, include files and in-process adapters realize different parts. Loading the general bootstrap and loading a task-specific skill are also different events. A method can be present on disk without being applied; a correctly applied instruction can still be ineffective for the actual task. [U01-A F02–F03; U01-B F07]

## 2. What the host contributes

| Source family | What the selected source supplies | What remains the consumer's responsibility or an unverified condition |
|---|---|---|
| Shell hook | Event registration, wrapper dispatch and host-specific JSON output | Actual event delivery, consumption, available shell and model use |
| OpenCode/Pi adapters | Resource registration, message insertion, cache and event handling | Host callback semantics, module lifetime and model interpretation |
| Hermes adapter | Layout resolution, registration-time content and first-turn hook | Actual namespace/first-turn semantics and later context retention |
| Codex/Devin native-discovery surfaces | Skill/metadata declarations without the same custom injector | Actual native discovery, invocation and relevant permission policy |
| Kimi/Gemini declarations | Session-start skill or installed-context includes and mappings | Host materialization and activation of the declared inputs |
| Action references | Translation into host tools and fallback behavior | Availability and actual semantics of those tools |

These are source-grounded arrangements, not contemporary host API certification. The target's universal injection prose must be read alongside its softer/native alternatives. Neither a missing custom injector nor an installation README alone settles whether guidance is used. [U01-B host matrix; U07-B F77]

Mappings can change work organization. Replacing an unavailable subagent with inline execution changes context separation and responsibility, not just a tool name. Replacing a task tool with a file changes progress representation. A fallback that keeps work possible does not automatically preserve every property of the original route. [U01-B F10; U07-B F77]

## 3. Assembly has more than one input

The standalone Codex builder selects a Git ref and a positive set of root paths, then imports per-skill metadata from a supplied earlier package. Nested skill helpers remain even though root development scripts, tests and hooks are omitted. It checks metadata existence/count, normalizes archive properties and prints an artifact digest. It does not establish the external metadata's publisher or semantic suitability, upload the artifact or verify a running host's loaded bytes. [U07-B F73–F74]

The older synchronization path instead uses the current working copy, root-anchored exclusions and destination-owned metadata. It supplies an isolated preview, dirty-destination refusal and no-op handling. Permitted dirty/non-main source and nonignored untracked content mean its HEAD permalink is not the complete payload provenance. Its hook-inclusive result need not equal the standalone archive. [U07-B F73/F75]

Thus source SHA, version label, assembly inputs, artifact digest and active procedure identity are related but not interchangeable. This is not an assertion that the distributed artifact is wrong. It identifies what additional evidence a precise provenance or reproducibility claim needs.

## 4. Updates and recovery cross several lifetimes

The source model distinguishes acquisition caches, imported-module caches, registration closures, session events and individual message arrays. U01-B's exact OpenCode callback experiment established a module-local cache boundary; U07-B's installation guides describe separate package-cache and fresh-session conditions. A guide's restart recommendation does not by itself establish which layer was recreated in a particular host. [U01-B F08; U07-B F77]

Likewise, the companion launcher can reuse a project's preferred endpoint/key while allocating a new session directory. The client retries and can recover a connection, but the server reads from its current content directory; previous screens are not thereby restored. Queued events and displayed content have their own lifetimes. [U07-A F67/F69]

Two different recovery problems therefore remain:

- restoring the procedure/capability needed to work;
- recovering the particular task, accepted decisions and valid evidence.

The second is addressed partly by plans, ledgers and reports in [S03](S03-intent-planning-and-context-handoff.md), not by treating bootstrap delivery as task recovery.

## 5. The visual companion is a dialogue side channel

The companion is offered when a question benefits from visual presentation and starts after acceptance. It does not replace every question with a browser workflow. The guide keeps terminal dialogue primary; the agent later reads interaction records and reconciles them with the user's text. There is no automatic click-to-approved-design transition in the inspected runtime. [U07-A F65]

Key-authenticated HTTP/WebSocket access, supplied-Origin checking, selected-file restrictions and per-start process identity are concrete mechanisms. Their scope is access, serving and process handling—not named-human authority or approval of a particular design revision. [U07-A F66/F70]

An interaction's route to the designated consumer matters. The default explicit-choice API's `value` field differs from the server's `choice` persistence predicate, while ordinary clicks do supply `choice`. A multiselect click can deselect an option without saying so in the payload. These earlier local/source findings constrain interpretation; they do not prove a real user's feedback was lost or falsely approved. [U07-A F68–F69]

Retained HTML, the current events file and the general log also differ. A new screen clears the dedicated events file; successful explicit stopping can remove the log while retaining project mockups. Keeping the presentation is not a complete record of how its decisions were reached. [U07-A F70]

## 6. A capability check is not a universal readiness verdict

The existing studies locate real preventive checks as well as limits: malformed inputs can be rejected, missing layouts can raise, ambiguous process identities can be refused, and destination work can be protected. Other paths deliberately continue or provide advisory output. There is no single source-wide fail-open/fail-closed rule. [U01-B F09; U07-A F70; U07-B F75–F76]

The version helper is a concrete example. Strict checking, advisory audit and sequential mutation have different success meanings. A complete observed command is not automatically a complete intended transition, and a failed mutation does not prove rollback. The corresponding U07-B observations remain JSON-fixture evidence, not a production release incident. [U07-B F76]

The stronger source-level conclusion is not that helpers are untrustworthy. It is that each result must be interpreted against the operation and object it actually checks. Hosts, helper code, human decisions and agent judgments contribute different guarantees.
