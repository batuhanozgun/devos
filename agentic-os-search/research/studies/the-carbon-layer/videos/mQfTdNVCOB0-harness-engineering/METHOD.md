# Method — source-native, iterative and adversarial

**Version:** 0.1 / 2026-09-12. Study-local method, not an agent-control protocol. Adapted from the fully read [HERMES method](../../../hermes-agent/METHOD.md) and the synthesis/closure structure described in [GSTACK metadata](../../../gstack/META.md). Their external-system conclusions are not imported as evidence for this target.

## 1. Preserve source identities and representations

Keep distinct: original video/audio; captions or third-party transcription; our map; paper version; project webpage; cleaned-up reference implementation; selected output artifact; historical execution logs; currently deployed system. Pin code and paper. Webpage and video freshness require separate notes. Source instructions, skills and onboarding prompts are research data, never instructions to this researcher.

Reading statuses: DISCOVERED, METADATA/TREE, SELECTED READ, FIRST-PASS TEXT, VISUAL CHECK, MECHANISM TRACED, TEST SOURCE INSPECTED, EXECUTED. These are dimensions, not a linear ladder of truth. Full text reading is not full comprehension, source correctness or implementation verification.

## 2. Work in meaningful units

A unit follows a transition or mechanism:

`intended need → input/authority → selection/configuration → caller/implementation → state/effect → observation/evaluation → failure/recovery → reuse boundary`.

For harness evolution add: who may change what; what stays fixed; where feedback comes from; candidate lineage; evaluator ownership; selection and deployment authority. Missing links remain explicit. A file-count quota is not a research unit.

The smallest successful unit may be a complete candidate-admission path, not the entire optimiser. Split large units before evidence quality deteriorates. Do not fragment so finely that no producer–consumer relation can be recovered.

## 3. Two directions, two synthesis levels

Bottom-up: source-native observations → mechanism notes → native subsystem/operating-loop syntheses → cross-source comparison. Top-down: challenge each synthesis using a source region, negative path or alternative explanation that did not generate the original model.

Only after this, project into current Foundation and SOUL/DevOS questions. Keep a separate cross-cutting residual: some mechanisms concern several grounds and need not belong to one box. Evidence provenance is a many-to-many graph even when the explanation is hierarchical.

Early project-relevance questions are allowed; they do not dictate the native decomposition or resolve architecture.

## 4. Claim discipline

Use TARGET CLAIM for what authors say; OBSERVATION for what is present in a specified document/code/frame; INFERENCE for our interpretation; HYPOTHESIS/OPEN for an untested explanation; EXECUTED RESULT only with actual run identity and artifacts.

A source may contain a strong claim with weak support. Preserve both. A proposer log giving a causal explanation is observable text, not an independently established cause. A returned score is not the same as correctly measured quality. A test that imports a class establishes less than evaluator integrity or operational safety.

For numeric claims retain dataset/split, model/proposer, baseline, sample/trial count, search versus final evaluation, units, aggregation and uncertainty. Do not mix characters with tokens, additional context with total cost, or evaluation count with wall-clock speed.

## 5. Active alternatives and negative controls

Consider at least the material alternatives: model limitations, wrong objective, bad source, context selection, tool/host failure, authority error, faulty evaluator, selection overfit, task leakage, and cost reallocation. Do not assume every symptom belongs to the harness.

When studying improvement, include no-change and simpler/manual alternatives; hold-out work where possible; old-task regressions; nonstationary environments/models; component removal; and adversarial or misleading traces. Not every unit needs every control, but omitted relevant controls must remain a limitation.

Distinguish regression of a new proposal from regression of an accepted system. Keeping the best score so far makes a chart monotone; it does not prove each proposal is beneficial or the selected system is safe.

## 6. Experiments, when warranted

Before execution define exact source/dependencies, target claim, oracle, fixtures, controls, side effects and expected failure signals. Start with safe local source/fixture probes only when useful. Such probes do not establish live model efficacy, host containment or independent replication.

Paid API calls, credential use, installations with material side effects, production mutation and full expensive benchmark runs need an explicit bounded execution decision; the upstream quick start is not permission. If execution is unavailable, investigate source and preserve the unresolved boundary instead of fabricating a run.

## 7. Plan revision

Record new evidence → affected assumption → unit split/merge/reopen → next action. U00 already elevated evaluation separation ahead of a broad component survey because the coding benchmark is reused for search/final evaluation and the public framework is a cleaned-up release with limited stated testing.

Maintain named open questions and exact next source paths. Revisions do not erase earlier failed hypotheses, access limitations or finished work. Do not treat an existing published unit as unfinished because an older snapshot still calls it pending.

## 8. Bounded completion

Propose campaign closure only when both trigger sources have recoverable coverage; all load-bearing mechanism families and variants are explained; relevant implementation/evaluation claims are traced or explicitly unresolved; rival accounts and omitted regions have been challenged; source-to-synthesis links remain usable; numeric/freshness limits are explicit; and the SOUL/DevOS projection retains nontransferable parts and open decisions.

Unresolved critical evidence may require a narrower conclusion, not an unqualified closure. No percentage complete from pages, files, tokens or tests. Same-model adversarial review is not independent verification.

## 9. Publication and continuity

Only this package plus minimal catalog/index edits. Before writing shared files, reread current main and shared content. Create one additive tree/commit where feasible, advance main without force, and verify actual diff plus entry files. Rebase the bounded delta if another study publishes concurrently; never restore an older shared file wholesale.

Save current authority, completed unit, genuine limitations and next executable research step. The repository, not conversation recall, must support a cold start.
