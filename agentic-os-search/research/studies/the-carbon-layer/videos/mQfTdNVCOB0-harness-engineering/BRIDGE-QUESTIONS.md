# Candidate bridge to SOUL and Development OS

**Standing:** provisional research questions, not architecture. **Date:** 2026-09-12. Inputs: source-native U00 notes, current project orientation and selectively read existing study material. Deep cross-study and Foundation projection is still pending.

## 1. What might be consumed from the research library?

Not necessarily every document, and not necessarily as prompt text. Candidate consumption roles include explanatory background, a selectable mechanism, an applicability condition, a failure counterexample, an evaluation case, an authority constraint or a reason not to make a change.

A research summary can be useful without becoming executable policy. A mechanism can be applicable without its source's whole architecture being adopted. A trace can supply evidence without becoming authoritative memory. These distinctions connect the source pair to questions already present in the older context–memory–harness synthesis; they are not new Foundation decisions.

**Working hypothesis:** the bridge is better studied as a qualification process than as a technology list:

`work need and constraints → relevant research/source recovery → candidate mechanism and its limits → bounded target-specific evaluation → authorised acceptance/rejection → operating feedback`.

This is an analytical scaffold to challenge, not a proposed storage schema or mandatory SOUL runtime pipeline.

## 3. Separate SOUL and Development OS questions

**For SOUL:** How is an appropriate work system formed for an intended outcome? What does the specific work require from context, state, tools, roles, environment and verification? Which features are unnecessary? How does a system recognise when it should adapt, escalate, change model, revise its assumptions or stop? Who may accept a change and what evidence must travel with it?

A model harness is one possible operational object within that inquiry. It is not automatically the whole SOUL product or an adequate model of every human/organisational work system.

**For Development OS:** How should research-derived changes be proposed, traced, evaluated and handed to the authorised developer without turning literature into an unreviewed requirement? How can code identity, configuration, test evidence and real effects remain bound through handoff and continuation? Which controls are instructions and which are enforced at the effect boundary?

The existing DevOS implementation grant and Codex ownership are not expanded here. This package produces research inputs and pressure tests, not an implementation message.

## 4. A concrete hypothetical use case

Suppose a future SOUL work system must prepare an internal technical assessment. It has prior research, repository state, several tools and a human acceptance point. A failed run omits a critical constraint.

Possible explanations differ: the authoritative constraint was wrong; retrieval missed it; a summary lost its qualification; the worker ignored it; delegation dropped it; a tool ran under a different scope; or the final checker could not detect the omission. Adding a memory entry or another agent before separating those explanations may reinforce the wrong process.

The video's responsibility map suggests places to inspect. Meta-Harness suggests a way to generate and test candidate policy changes. Existing Foundation/studies may supply source-fidelity distinctions, continuity cases and falsifiers. None alone establishes which correction is justified. This scenario is illustrative and was not executed.

## 5. Candidate decision questions before any later adoption

What work distribution and risks does a change target? What remains immutable? Which evidence is eligible and current? What does the evaluator actually distinguish? Was the test set repeatedly used for search? What degraded? What is the total cost? What can be rolled back and what external effect cannot? Who accepts the change, and what invalidates that acceptance later?

A later bridge synthesis should answer these with source-grounded mechanisms, not merely rename them as boxes. The strongest useful result may be a bounded mechanism, a negative result or a missing prerequisite rather than a grand unified architecture.
