## Joined mechanisms and contrasts

1. **Rule source versus source-link report.** S-SCAN uses in-code maps/sets; it neither imports S-ADVISORY nor reads its emitted JSON. S-ADVISORY checks metadata and optionally URL status; requestUrl drains responses rather than parsing advisory content. The watch runs them sequentially without changing scanner indicators. No automatic content-to-rule update follows from a fresh report.
2. **Finite coverage.** Scanner selection uses explicit names, special config paths and ignored directory names. node_modules walking checks immediate package roots, not arbitrary payload subdirectories or nested installations; hidden entries and directory-entry symlinks are skipped. Home and fixed system temp targets are opt-in. A matching lockfile entry can still detect a known version independently; omitted installed bytes do not imply universal package invisibility.
3. **Missingness.** A nonexistent root returns zero selected files and no findings, satisfying the CLI zero-finding exit condition. readText/sha256File swallow their own errors into empty strings, while traversal errors can propagate to CLI exit2. A selected ordinary manifest failing both reads can leave no finding; known payload names can still be detected independently. scannedFiles counts the pre-dedup selected list, not a verified successful-read count.
4. **Exception scope.** claudePermissionDenyRanges parses deny strings but finds all textual occurrences of each string/JSON encoding across the complete file; it does not bind ranges to the deny AST locations. Identical text in another field can fall inside an exemption. Existing mixed deny/hook test uses different full strings and therefore does not test this identical-value contrast. This is source scope, not proof of a live host accepting a bypass or a malicious execution.
5. **Refresh status versus readiness.** Valid source metadata with all fetches returning ordinary failure objects yields warning refresh and refresh.ok=false but ready=true. Offline ready and warning ready both feed the Linear summary 'Advisory sources current'. The CLI's optional strict-refresh can exit1 despite ready=true; the actual watch uses --refresh, not strict. Detailed warnings remain visible, and returned failures differ from a custom fetchSource promise that rejects outright.
6. **URL status versus content/time.** Five redirects, timeout, HEAD and GET fallback are implemented. A final 3xx when no redirect remains can be considered ok without reaching terminal content. GET fallback returns requestUrl directly, losing the separately supplied checkedAt in the returned result; per-source checkedAt can then be null despite success. No advisory publication/content date, hash, diff or maximum age is inspected. generatedAt is report time and can be overridden.
7. **Consumer and independent controls.** Watch/CI include separate registry signature and advisory commands; release includes direct IOC prerequisites. These are real different controls. In watch, an earlier audit/fixture/scan failure can skip later report producers; always-upload only tries available files. No complete artifact pair is guaranteed merely by that upload condition. No live workflow or registry audit was run.
