## Joined findings and countercases

1. O-GATE is an explicit repository-surface rubric, not a runtime sensor. Ten checks total21 points and ready requires all points; weights prioritize selected remediation, not confidence or task-completion percentage. Existence, includesAll and a small JSON-key check can succeed for placeholder/comment-only representations. Missing expected material can fail. T-GATE's seeded files demonstrate the intended literal test surface; no execution is credited.
2. O-GATE normal CLI does not translate ready=false into nonzero exit. Its catch does fail actual errors. T-GATE separately asserts ready=true for the current repository, C-SUITE discovers that test and fails on a failing subprocess/assertion, and the previously read CI invokes the suite. Thus there is a real indirect check; no claim that failed readiness can never block CI.
3. O-DASH imports/runs O-PLATFORM, but its observability-for-self-use row checks the package mapping and doc marker instead of calling O-GATE. That row can be complete when the named gate file is absent, or when its ten-check report would be false. Preview/video/supply-chain/Linear rows likewise use selected in-tree markers or historical recorded claims, with distinct requirements/gaps; they do not consume all underlying fresh reports.
4. O-PLATFORM preserves genuine GitHub command errors as failed checks, while skip-GitHub and unavailable local Git are warnings excluded from ready's fail-only predicate. O-DASH's detailed queue requirements additionally require live/no-error GitHub. Its Markdown Current Status table re-derives queue/discussion labels from counts and skipped status, not githubErrors. All failed repo reads can therefore yield zeros and Current queue labels while dashboardReady=false and detailed requirements remain in_progress. Local worktree rendering similarly uses zero count without availability.
5. Markdown uses hard-coded <20 queue and ==0 dirty thresholds; source requirements/platform use configurable <= thresholds. Exactly20 can be accepted by the default budget but rendered Needs work. A stricter custom budget can fail while the overview says Current. This is projection inconsistency, not a false publication approval.
6. O-PLATFORM counts returned PR/issue list rows; under documented gh defaults it can truncate at30. A custom budget40 and actual50 rows can appear as30, subject to other checks. Default20 still rejects a saturated30-row result, so truncation alone does not hide an over-budget queue under that default. O-DISCUSSIONS explicitly samples100 recent discussions and20 comments; total/sample metadata exists there but is not used as a completeness gate downstream. Older unresolved discussions or later maintainer comments can change the whole-population interpretation.
7. O-DASH ready is objective requirements, dashboardReady is platform.ready, publicationReady is a constantfalse. Several objective rows have no current/complete result branch, so the pinned ordinary builder cannot generate objective ready=true merely by completing external work. The renderer test's handcrafted ready/publicationReady=true report does not show builder reachability. This is an intentionally conservative snapshot with hard-coded historical responsibilities, not a deployed approval service.
8. generatedAt and head do not bind every live/historical input to one atomic snapshot. Local files are read from the working tree; probes and the later HEAD query are sequential; --write occurs afterward with no post-write git recheck. Retained historical success phrases can keep freshness-labelled predicates passing without content/age validation. These are evidence-scope constraints, not observed stale production decisions.
