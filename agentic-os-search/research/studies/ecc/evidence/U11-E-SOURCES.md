## Joined mechanism and discriminators

**Input/resolution:** Template CLI resolves an optional source and parses key=value arguments into a map. Parsing trims and rejects empty key/value or missing delimiter; repeated keys overwrite earlier entries. build_template_variables fills absent task/project/cwd/source fields with or_insert, so explicit variables can override generated text. The resolver checks template existence/nonempty step list, substitutes matching placeholders, validates named profiles and resolves every step before launch effects. Required-string interpolation detects missing recognized keys, not nonempty task meaning or valid arbitrary placeholder syntax. Optional blank strings become None. Inherited project/task_group defaults can undergo a second helper call when a step has no override; direct step values undergo their own one pass.

**Binding:** source-session variables/group labels/anchor are not a repository revision or profile snapshot. Launch uses the invoking process current directory for every new session; an overridden cwd variable changes text, not this path. No-source launches use the first created session as anchor; with a source, all created steps receive handoffs from that source. Step order is sequential admission, not a wait for prior completion or dependency-edge evaluation. New sessions are not selected through the reuse/assignment mechanism.

**Profiles:** launch resolves cfg.default_agent_profile before the loop, then chooses a step profile if present; otherwise a step with an explicit resolved agent gets no default profile; otherwise the global default is cloned. A template-level agent inherited by a step has the same explicit-presence effect. The resolved-profile queue does not reintroduce a default. A profile's own agent overrides the agent argument in that queue. The source session's stored profile is not read by this template path. Profile persistence does not certify host enforcement; U12-A is selected for that distinct consumer.

**Capacity:** existing Pending/Running/Idle/Stale rows are counted and subtracted from max_parallel_sessions before comparing total steps. This is stronger than the scheduler's batch-only limit, but a read/check is not a reservation across callers. The lower queue has no template-wide lock/claim; the separately limited worktree path can return an admitted Pending record without a runner.

**Partial failure:** ordinary missing-variable/profile and insufficient-slot refusals precede the template's new sessions. After admission starts, each queue/handoff returns with ? before the final vector is returned; no template-wide rollback or partial-outcome return occurs. Concrete conditional countercase: enough session/worktree capacity; step1 worktree=false with successful record/runner admission; step2 worktree=true; empty normalized worktree_branch_prefix. Step2 calls branch_name_for_session and fails; step1 survives. This uses an explicit source predicate, not an injected DB failure or an executed incident. If worktree capacity is already full, step2 can queue instead; that condition is retained.

**Discovery/retry:** underlying session/profile/message/log records remain useful. The followed writer does not persist a template execution id, immutable resolved input set or next-step checkpoint. The first standalone anchor has no template-generated inbound handoff. CLI prints the collected result only after the whole function succeeds. Retrying calls resolution/admission afresh and can recreate earlier steps, subject to current capacity/configuration. Individual queue cleanup remains real but does not compensate preceding steps. Wrapper admission also need not expose a later harness error synchronously.
