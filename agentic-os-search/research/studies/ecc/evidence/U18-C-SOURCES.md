## Claim-to-chain bindings

1. **Real catalog search and public consumer:** PACKAGE bin maps ecc-universal→CLI; CLI dispatches consult/plan/install to separate scripts. CONSULT constructs rankings and text/JSON output but does not execute returned commands. T-CONSULT invokes the local script, not a model or the suggested installer.
2. **Matching is not needs acceptance:** CONSULT normalizes/tokenizes and scores IDs/descriptions/module names/aliases. Positive matches and preference bonuses generate ranking; no project inspection, negation-to-exclusion translation, outcome evaluation or accepted requirements record is present in that complete script. Its positive and negative MLE tests demonstrate intended matcher assertions, not universal task adequacy.
3. **Direct target versus prerequisite closure:** MANIFESTS listInstallComponents intersects found direct-module target arrays; resolveInstallPlan separately traverses dependencies and calls adapters. COMPONENTS maps framework:nextjs→framework-language. MODULES explicitly admits codex for framework-language, whose first dependency rules-core omits codex. The recommendation candidate survives direct filtering but the resolver marks the framework module skipped. CODEX supplies no custom supportsModule; TARGET-HELPERS returns true by default, so a different adapter filter does not preempt this causal explanation. This is exact source deduction, not an executed run or all-host claim.
4. **Names versus material granularity:** COMPONENTS maps Next.js/React/Python and others to the same broad module. MODULES supplies that module's paths/dependencies. CONSULT adds PROFILES.minimal to every component install command. MANIFESTS exclusion expands to module IDs, so excluding React can exclude the same module selected by Next.js.
5. **Config enters later:** CONSULT reads no project install config. PLAN-CLI/APPLY-CLI discover CONFIG from cwd; CONFIG-SCHEMA admits version1/exclude:[framework:react]. REQUEST uses explicit CLI profile/target but unions configured and CLI sets. MANIFESTS applies the resulting module exclusions. The stipulated config is not an actual user file and no config was created or changed.
6. **Preview destination versus apply destination:** PLAN-CLI omits projectRoot/homeDir when calling MANIFESTS. MANIFESTS defaults projectRoot to its repoRoot. APPLY-CLI supplies cwd; RUNTIME→PLAN preserves it. CURSOR declares project scope and .cursor segments; TARGET-HELPERS binds root to projectRoot. For distinct source R and caller P, standalone plan targets R/.cursor while install's runtime plan targets P/.cursor. Source case, not an observed write.
7. **Scaffold versus materialized preview versus effect:** PLAN-CLI prints its explicit scaffold caveat. PLAN expands/deduplicates operations and creates source/state metadata. APPLY.previewInstallPlan evaluates migration/ownership/settings and emits a consent warning; APPLY.applyInstallPlan begins with HOOKS.assertHookConsentReady and then applies operations. No previous consult/standalone-plan result is passed into the new invocation as an immutable approval.
8. **Consent and useful downstream controls:** PROFILES.security includes hooks-runtime, CONSULT's strings omit consent, RUNTIME attaches the separate choice, and APPLY invokes the actual assertion before apply. Guard and migration call sites, settings checks, conditional bridge recovery and digest/state writes are real source controls. Their whole dependency closure/race/host efficacy was not revalidated by reading this caller.
9. **Version/environment binding:** CONSULT carries no source/catalog digest or frozen destination; suggested package spec lacks a version. PACKAGE's pinned2.2.1 binary declaration plus NPM-NPX explain the intended command and why a later resolution is a separate identity. No registry/current-release or installed npm verdict follows.
