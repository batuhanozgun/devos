## Joined findings and countercases

1. R-GATE reads local Markdown, recognizes eight decision labels and approval-state words, checks seven URL-surface label strings and absence of blocker phrases, and checks command listings/announcement placeholders. It does not parse/fetch URLs, authenticate an approving actor, rerun the listed commands, read Git HEAD, or hash the candidate. Its digest covers check id/status/evidence tuples, not source/document bytes or even the separately returned release label. Content or version changes preserving those tuples can preserve the digest without a cryptographic collision. Normal complete documents pass their literal contract; explicit deferrals/missing content fail with exit2.
2. R-PREVIEW is fixed to 2.0.0-rc.1 while R-GATE selects the package version (2.2.1 here) and fixed May19 suffixes. The finite 2.2.1 listing lacks the latter required files, so the unchanged pinned checkout cannot meet that gate's source predicates. This is a source-derived result, NOT an executed CLI failure. A completed historical preview is neither final approval nor proof of a 2.2.1 tarball.
3. Actual R-RELEASE/R-REUSABLE form a different execution gate: origin/main equality at verification, version/tag and metadata checks, build/IOC, one packed archive and SHA-256, lifecycle jobs on three platforms, digest recheck, publish that archive, registry SHA-512 comparison and dist-tag promotion. Neither workflow directly calls R-GATE/R-PREVIEW or consumes their reports; R-PACKAGE's prepack invokes OpenCode build, not those document gates. No claim about all possible external policy/CI callers is made.
4. R-RUNBOOK requires signed tag and green CI/CodeQL on the exact commit. The two release YAML bodies do not themselves verify a tag signature, fetch the recorded CI verdict, or declare a protected environment reviewer. Repository/ruleset, credential and human controls can exist externally; none was inspected. R-BUMP explicitly calls git tag without an explicit -s request (Git configuration may still sign), pushes, then prints Released; it does not wait for publication. Its local multi-file changes have no transaction/compensation wrapper.
5. R-LIFECYCLE really hashes the archive, creates isolated home/project paths, installs the file and invokes packed public CLI, including induced managed-file drift and repair. Fake Claude responses and selected install scenarios limit the oracle. It does not instantiate OpenCode and test Note25 callbacks or perform live model work. The normal default-root OpenCode case is not Note26's explicit same-root migration case. All tests remain inspected, not run.
6. Registry lookup treats only E404 as missing; other errors block. Already published candidate bytes must match. Post-publish lookup is retried six times, then failure blocks promotion/release, without undoing already published bytes. Stable versions initially use staged and later latest; prereleases publish to next immediately before readback. The dist-tag is a pointer, not confidentiality or distributed rollback.
7. Conditional concurrency: old stable job A can pass main equality, remain active while newer job B verifies a later main and promotes, then A can overwrite latest afterward. These YAMLs have no shared concurrency key or expected-current-tag/monotonic-version predicate. Each archive can be correctly hashed. External serialization would change this outcome; no overlapping release was run. Conversely, a fresh retry of old A after main advances fails the exact-main precheck: attempt timing and retry policy differ.
8. The generic SLSA workflow builds a fresh archive and hashes that subject, rather than consuming the exact release archive/digest. It is a useful separately identified provenance path, not proof the rebuilt bytes equal those published by the main pipeline. Actual triggering/attestation validation and external action implementations are unexamined.
