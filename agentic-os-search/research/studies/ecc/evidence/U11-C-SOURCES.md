## Joined producer/consumer explanation

**Intake:** main's separate Serve branch runs a synchronous TCP accept/handle loop. GET /health returns a constant ok without checking worker/queue health. POST /dispatch and /computer-use compare a supplied Authorization value with one configured bearer string, then deserialize and validate nonempty task/goal and resolve the target before request creation. A successful request is persisted before202. The full body is read before route-specific authentication; neither a body-byte limit nor accepted-stream deadline is configured in the examined functions. Header-size handling exists but is not a complete resource policy. A proxy or network boundary is outside the inspected application.

**Target and authority:** HTTP/CLI normalize a session reference to a stored id, but get_session accepts the first exact/prefix match, not a unique-prefix proof. The request's target is used as a lead for delegate assignment, not necessarily as the final worker. The creator records its local current directory, task/group/profile name and peer IP/source label. The token is not a per-request actor/grant record. No live authorization bypass or unauthenticated job execution was demonstrated.

**Target deletion counterpart:** the native schema uses target_session_id REFERENCES sessions(id) ON DELETE SET NULL, and StateStore enables foreign keys. Successful parent deletion leaves a pending request with no target; mapping returns None; the dispatcher treats None as top-level admission. This joins the real delete method, schema action, mapper and consumer branch. It is conditional on successful deletion and the declared schema/FK behavior, not an observed incident or every migrated database. Deletion after an already-read Some-target snapshot instead leads to target-resolution failure on that snapshot. These different timings are not collapsed.

**Selection and binding:** pending SQL sorts priority descending, then creation/id, with a batch limit. Targeted assignment searches prior handoff children of the requested harness and appropriate state/backlog. Reusing idle/active delegates only sends a handoff; requested profile, worktree and directory are not compared/applied in those branches. New-session branches do resolve/store a profile through the known queue path. send_task_handoff assigns Normal priority and carries lead/task context, not the remote request id or requester; the remote priority therefore governs request selection but is not propagated as handoff priority.

**Outcome/retry:** successful routing writes Dispatched with result_session_id/result_action/time. Queue admission can still mean Pending worktree, not a ready process. DeferredSaturated remains Pending without a new durable deferral outcome; recorded failures become Failed and are excluded from subsequent pending reads. Unlike the schedule loop, an ordinary per-item route failure can be recorded and the next request attempted. A failure writing that result aborts the pass; earlier effects remain. Id-only result updates do not claim work or reject competing snapshots. No exactly-once, automatic same-id retry or completed-task acceptance is established.

**Actual consumers:** CLI List --all/--json and Run output expose stored/outcome data; default List sees only pending records. The complete HTTP handler has health and two intake routes, not a status-result API. Comms persists a handoff and invokes graph/board projection; it does not wait for worker acknowledgement. The selected message reader/mark-read and inbox/backlog paths give operator/control consumers, not proof of model uptake. Request result linkage is a real improvement over timestamp-only scheduling, but session-level linkage is not per-request accepted output, especially with reused sessions.
