## Joined chains and discriminators

**Frontier and normal routing:** unread task_handoff rows are sorted by parsed message priority/id; target aggregation ranks highest priority, unread count, oldest id and session id. It groups recipients, not a separately declared lead-role list. drain_inbox resolves a recipient as lead, extracts task text, assigns onward and marks the source read only for a routing action. Saturated outcomes keep the source unread. New child admission and a new unread handoff are separate from the old marker. The caller uses current/default agent and lead directory, not a complete immutable original request envelope.

**Consumption distinction:** a new child receives task text in its launch arguments; the additional handoff participates in history and another unread frontier. Reuse persists a message without restarting/configuring an existing recipient. The complete native runtime manages stdout/stderr, heartbeat and exit state, not an inbox-input pump or completion-to-message acknowledgement. The actual CLI inbox reader selects a limited recent bidirectional view and marks all recipient-unread rows before printing. A host can explicitly consume that command; automatic custom-host uptake is not established. The metrics session-bridge is a rejected discovery lead, not a general absence proof.

**Repeated delegation condition:** with automatic distribution enabled, successful child admission and no intervening consumer marking the child handoff read, a later pass can treat that child as a lead and forward the same extracted task again. A child without eligible children can create another child; the creation path admits Pending worktree requests too. The examined frontier has no leaf-role or task-lineage termination condition. This is a conditional source trace, not measured infinite growth, all-installation behavior or proof that an external consumer never acknowledges work. Default automation is off.

**Rebalancing:** the rebalancer selects backed-up delegates using all unread-message counts, checks clear idle alternatives/current team capacity, rereads those conditions for each candidate, and moves only messages from the selected lead. Assignment itself considers unread handoffs, a narrower population. After assignment, rebalancer checks whether the destination equals the old delegate, but unlike drain_inbox does not test assignment_action_routes_work before marking the old message read and counting a reroute. A competing change between precheck and assignment can yield DeferredSaturated with the lead id and still enter that marker branch. This is a conditional concurrency boundary, not a reproduced loss incident. Normal idle-transfer tests cover the successful path.

**Durability:** forwarding, new message insertion, projection, source read marker and daemon summary are separate operations. Failure before mark-read can leave an onward effect and a retryable source. A projection failure after mark-read can leave a consumed source while the caller returns error. A competing reader can route before learning its read-marker update affected zero rows; that count is discarded. First propagated errors abort remaining manager batches and can prevent recorder updates while earlier effects remain. SQLite's implicit-transaction contract supports the statement boundary, not a native concurrency test.

**Cooloff:** stored last_dispatch_deferred and relative recovery/dispatch timestamps choose rebalance-first. Cooloff is active for at least two deferred items or a streak of at least three; it contains no elapsed-time test. With zero reroutes the daemon skips dispatch. Rebalance recording updates only rebalance fields; neither deferred count nor streak is refreshed in that skipped branch. Without another relevant state change, the same condition recurs after restart or another cycle, even when a fresh dispatch could use capacity. The escalation predicate requires streak>=5, so a state frozen at1 or3 need not progress to that flag. Positive rebalancing allows another dispatch and successful recovery is recorded. No live hang or recovery was run.

**Observers and manual contrast:** pressure counts concern selected inboxes and candidate delegates, not unfinished deliverables. Health combines fresh inbox pressure with historical daemon activity; escalation has precedence. Explicit CLI coordinate/auto-dispatch call manager directly, not the daemon cooloff wrappers or recorder callbacks. They can perform routing despite automatic mode being off, but do not thereby refresh daemon history. The bounded until-healthy loop also stops on Saturated/EscalationRequired; a requested agent override is not passed into get_coordination_status, which uses cfg.default_agent. These are source-level scope distinctions.
