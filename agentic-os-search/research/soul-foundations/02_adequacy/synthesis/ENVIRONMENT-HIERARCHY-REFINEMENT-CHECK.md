# Environment Hierarchy Refinement — COMPLETENESS / OMISSION CHECK

**Status:** current same-model adversarial refinement review  
**Verification class:** NOT independent verification  
**Date:** 2026-09-02

## Question

Has the narrow reopened adequacy inquiry gathered enough evidence to decide whether Operating World / Work Domain and Technical Work Environment should remain peer top-level grounds or become explicit branches/roles under one broader Environment-like problem ground?

## Prior result being challenged

The first adequacy closure preferred five peers:

```text
Operating World
Information / Representation
Work
Actors
Technical Work Environment
```

Its completeness audit had rejected a broad Environment merge because the tested broad framing recreated residual/scope collision.

The user then raised a direct falsifier:

> perhaps World and Technical Work Environment are not the same thing, but belong under one higher leg and should be separated below that level.

That is a materially different hierarchy hypothesis from `collapse them into one undifferentiated Environment`.

## Challenge A — internal two-corpus comparison

Compared:
- archived operating-world synthesis and focused runtime/tool finding;
- current Technical Work Environment synthesis.

Result:
- both share a higher grammar of boundary/reference point, realized current state, independently changing conditions, interfaces/resources, constraints, observability and situated feasibility/outcome effects;
- they retain different lower questions: target/domain reality versus support capability/condition.

Information gain: **HIGH**.

## Challenge B — ISO/NIST enabling-system counterexample

NIST/ISO 15288 distinguishes enabling systems from systems in the system-of-interest's operational environment. An enabling/development/test system need not be part of the product operational environment.

Result:
- falsifies `Technical Work Environment is always a subtype of Operating World`;
- supports sibling operational/support roles at a wider analytical level.

Information gain: **HIGH**.

## Challenge C — NASA physical versus support environment

NASA ConOps guidance explicitly separates physical environment and support environment within the wider system description.

Result:
- supports explicit lower branch separation;
- does not require them to be peer top-level research grounds.

Information gain: **MEDIUM/HIGH**.

## Challenge D — systems/work-context traditions

Cognitive Work Analysis, Work System Theory, SEIPS and HFE were used as cross-lineage tests.

Results:
- CWA supports a broad work-domain/environmental constraint layer distinct from activity/actor analysis;
- WST and SEIPS preserve environment/infrastructure/tools/tasks/people/organization distinctions, warning against one residual bucket;
- lower distinctions survive, but they can coexist within a broader top-level problem map.

Information gain: **MEDIUM/HIGH**.

## Challenge E — Activity Theory object versus tool

Activity Theory separates:
- subject;
- object/focus transformed by activity;
- mediating tools;
- social/organizational mediation.

Result:
- independently supports target/object versus support/tool distinction;
- also supports retaining Actors/Work/social relations outside an Environment bucket.

Information gain: **MEDIUM**.

## Challenge F — agent/control counterframe

PEAS/POMDP and STAMP/control traditions distinguish world/controlled process from sensors, actuators, controllers, observations/process models.

Result:
- strongly rejects `technical mechanisms = environment objects`;
- does **not** reject a higher problem-ground synthesis if the project ground is explicitly not an architecture-component taxonomy;
- forces the parent to be role-/problem-based rather than inside/outside component classification.

Information gain: **HIGH** because it narrows the valid meaning of the merge.

## Challenge G — boundary-leak cases

Explicitly tested:
- other Actors/organizations;
- policies/laws/rules;
- physical workplace conditions;
- tools/technologies;
- Records/information used as tools;
- organization/coordination;
- other Work streams;
- support system becoming the Work target;
- nested system-of-interest changes.

Result:
- no case required Environment to own Actor, Work or Information semantics;
- all required multi-ground participation / typed relations;
- same concrete thing can change target/support/information/actor roles with the analytical question.

Information gain: **MEDIUM/HIGH**.

## Rival comparison

### R1 — five peer grounds

Strengths:
- strongest top-level anti-collapse visibility.

Weaknesses:
- level asymmetry: TWE is a specialized support problem while Operating World is a broader target/domain problem;
- duplicates a common environment grammar at the top level;
- less aligned with the Information correction where Records was moved under a broader parent.

### R2 — four broad grounds with Environment parent and explicit branches

Strengths:
- better level alignment;
- preserves all substantive distinctions;
- produces a stable recurring two-sided research question: target/domain side versus support side;
- fits both Development OS and general-purpose SOUL;
- survives cross-lineage challenge if treated as problem/role hierarchy.

Risk:
- parent can become residual/vacuous if defined as `everything relevant/external`.

Mitigation:
- strict exclusion and multi-ground role rules documented in Findings 08–10.

### R3 — Technical Work Environment dissolved entirely

Rejected because its independent state/identity/readiness/reproducibility/lifecycle/support-closure semantics remain productive first-order lower research.

### R4 — Context as parent

Rejected as preferred label because context is frequently defined through information/relevance and can absorb Actors, Work and Information.

### R5 — Operating World as parent of Technical Work Environment

Rejected as universal because enabling systems need not be in the system-of-interest's operational environment.

## Minimum current parent semantics

The parent can survive only with a definition close to:

> **the boundary-relative realized situational substrate in which focal Work is situated: the actual domain/conditions it must understand, accommodate or affect, plus the support conditions/capabilities/interfaces on which execution materially depends.**

This is a problem-ground formulation, not an entity containment rule.

## Productive lower split

At minimum:

```text
Environment-like ground
    ├─ Operating World / Work Domain
    │    what actual reality is being understood/changed/maintained/accommodated?
    └─ Work-Support Environment
         what realized conditions/capabilities/resources/interfaces make Work possible/constrained?
              └─ Technical Work Environment
```

The support branch may later require nontechnical profiles, but current evidence does not require another peer top-level ground.

## Development OS check

The split maps naturally:
- product/system/repository behavior being changed or evaluated → target/domain role;
- GitHub/ChatGPT/Codex/CI/runtimes/test services/credentials → support role.

Same concrete resource may occupy both roles under different Work.

Verdict: four broad grounds improve level alignment without losing operational detail.

## General-purpose SOUL check

Clinical, robotics, industrial, market/scientific and other cases preserve:
- actual domain reality;
- support environment/tooling;
- representations;
- Work;
- Actors.

Verdict: one environmental parent remains viable across materially different domains.

## Verification limit

- same-model synthesis/adversarial review;
- no external source independently validates the exact four-ground hierarchy;
- source traditions use different scopes/terminology;
- `Environment` remains an overloaded working label;
- deeper independent Operating World / Information research may alter boundaries.

## Reopen conditions

Reopen this parent/peer result if:
- a materially different domain forces target-world and support-environment semantics to diverge at the top problem level;
- the parent repeatedly absorbs Actors/Work/Information to explain cases;
- nontechnical work support reveals a first-order family that the parent plus current grounds cannot represent;
- deeper research shows Technical Work Environment is not productively nested;
- independent review finds a materially stronger rival decomposition.

## Stop rationale

The trajectory has shifted from new structural falsifiers to terminology/boundary refinements. The latest independent counterframe (agent/control separation) narrowed the permitted meaning of the parent but did not restore five peers.

Further broad searching without a new falsifier is therefore expected to have lower value than user evaluation or deeper branch-specific research.
