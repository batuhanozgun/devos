# Domain State Finding 01 — Evidence Inventory and Starting Falsifiers

**Status:** active-node evidence inventory; not final child result  
**Date:** 2026-09-02

## Question

What is already supported before deeper Domain State search, and which inherited assumptions must be attacked rather than silently preserved?

## Established parent evidence

Current Domain Reality research supports:
- `Domain State / Configuration` as distinct from `Domain Dynamics / Processes` at the immediate-child level;
- realized state/configuration is not identical to observation, model, specification or Record;
- structure/composition was not yet required as a third Domain-Reality child, but deeper State research was explicitly allowed to reopen it;
- identity/continuity, constraints/invariants and state sufficiency/granularity remain unresolved;
- no architecture, state vector or storage representation is implied.

## External starting evidence recovered

### Systems / systems-engineering state
Current SEBoK distinguishes:
- state as values of key qualities/properties at a time;
- structure as elements and their relationships;
- behavior/dynamics as change/evolution.

This is useful discrimination evidence, not authority for the project hierarchy.

### Systems modeling
OMG SysML explicitly separates structure and behavior model families. Structure concerns parts/interconnections; state-machine behavior concerns states/transitions. This supports the reality of a structure concern but is a modeling-language taxonomy, not a Domain-State ontology.

### Configuration management
NIST configuration-management material separately manages:
- system components/inventory;
- network topology/placement/connectivity in baseline configurations;
- configuration settings/parameters.

However baseline configurations and inventories are documented representations/specifications. They are evidence that practitioners need distinct structural/settings views, not proof that those views are identical to actual Domain Reality.

### Live software control
Current Kubernetes documentation separates desired `spec`, reported/current `status`, and control-loop attempts to move actual/current cluster behavior toward desired state. Kubelet documentation also notes that API-visible status can lag instant runtime reality.

This is strong evidence for the project boundary:

```text
actual realized condition ≠ desired specification ≠ reported/observed status
```

### State sufficiency / Markov counterframe
Poole & Mackworth and university MDP materials define a modeled state as containing the information needed for prediction/action under a Markov framing. This makes `state sufficiency` visibly purpose/model-relative rather than a simple intrinsic partition of reality.

### Identity / persistence
Current Stanford Encyclopedia treatment of identity over time frames persistence through change as a distinct philosophical problem. This supports taking identity/continuity seriously but does not yet show it should be a State child rather than a cross-cutting prerequisite across State and Dynamics.

### Formal ontology counterframe
BFO/DOLCE and related upper ontologies distinguish objects/continuants, qualities and relations/processes in different ways. Their disagreement is useful evidence against importing one ontology taxonomy as the project hierarchy.

## Frozen falsifiers

The active pass retains the plan's falsifiers:
- F1 State/Configuration is an arbitrary bundle.
- F2 Structure/Composition deserves child promotion.
- F3 Identity/Continuity deserves child promotion.
- F4 Properties/Status and Relations/Topology deserve separate children.
- F5 Constraints/Invariants deserve child promotion.
- F6 state granularity/sufficiency prevents stable child structure.
- F7 `State` is too model-centric and needs realized-condition/situation reframe.
- F8 social/institutional state breaks the reality/representation boundary.
- F9 a materially different domain exposes a missing State-local family.
- F10 the node is a bounded leaf and deeper hierarchy would be artificial.

## Current evidence asymmetry

Evidence is strongest for three distinctions:

1. **realized structure/configuration** versus **realized condition/status** may be materially different;
2. **actual reality** versus specification/report/model is definitely a boundary, not a child by itself;
3. identity, granularity and constraints are important but currently look cross-cutting rather than State-local children.

These are starting hypotheses under test, not closure conclusions.
