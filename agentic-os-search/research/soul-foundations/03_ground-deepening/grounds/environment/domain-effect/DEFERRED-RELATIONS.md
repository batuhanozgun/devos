# Domain Reality — DEFERRED RELATIONS

**Status:** cross-node/cross-ground observations captured during Domain Reality research; not solved here

## Domain Reality ↔ Work

- How should a Work target/subject relation distinguish Work that changes Domain Reality from Work that targets Information, Actors or another Work?
- How should intended outcome be related to actual resulting Domain State/trajectory?
- How should Work action/closure be related to actual domain transitions without assuming successful effect?
- When does one Work's result become another Work's Domain State or Work Condition?

Local rule:

> **Work action/closure ≠ actual Domain transition/result.**

## Domain Reality ↔ Information

- How should observations, measurements, state estimates, forecasts and models refer to Domain State/Dynamics?
- How should uncertainty/conflict/freshness be preserved when the actual state/process is partially known?
- How should represented laws/rules/specifications be separated from realized physical/institutional constraints?
- How should evidence support claims about past domain state/trajectory?

Local rule:

> **actual Domain State/Dynamics ≠ any particular representation of them.**

## Domain Reality ↔ Actors

- When an Actor's action changes Domain Reality, how are capability, authority and responsibility related to the resulting transition?
- How should socially/institutionally constituted domain facts depend on Actors/collective acceptance without collapsing those facts into Actor state?
- How should other Actors' actions appear as domain dynamics while their identity/authority remains Actors semantics?

## Domain Reality ↔ Work Conditions

- When does the same realized condition act as a Work Condition and as Domain Reality simultaneously?
- How does a support system become Domain Reality when maintenance/debugging Work targets it?
- Can a Domain State change make previously available Work Conditions unavailable, and vice versa?

Sibling remains inactive in this pass.
