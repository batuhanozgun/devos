# B. External / cross-lineage sources

## B1 — SEBoK Environment glossary

URL:
- https://sebokwiki.org/wiki/Environment_(glossary)

Observed content:
- one cited engineered-system definition describes environment as surroundings in which the system-of-interest is utilized and supported, or in which it is developed, produced or retired;
- discussion distinguishes environments across system life cycle.

Carries:
- strong support for a broad Environment concept that can include operating and lifecycle/support surroundings without asserting they are one object class.

Limitation:
- terminology relay drawing on older IEEE/INCOSE definitions; not project taxonomy.

## B2 — SEBoK Introduction to Systems Engineering Fundamentals / System Context

URLs:
- https://sebokwiki.org/wiki/Introduction_to_System_Fundamentals
- https://sebokwiki.org/wiki/System_Context_(glossary)
- https://sebokwiki.org/wiki/Engineered_System_Context

Observed content:
- system context is resolved around a selected system-of-interest;
- external elements interact across a boundary;
- wider natural/social/engineered systems and environment matter;
- system boundaries are analytical and systems can be nested;
- wider/open-system relationships are needed to understand behavior.

Carries:
- boundary/reference dependence;
- nested systems;
- role switching across analytical levels;
- wider environment/context discipline.

Limitation:
- system-centric; project Environment sometimes uses focal Work as the immediate reference.

## B3 — NIST Enabling System glossary / SP 800-160

URLs:
- https://csrc.nist.gov/glossary/term/enabling_system
- https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-160.pdf

Observed content:
- enabling systems support system-of-interest life-cycle activities;
- they need not exist in the system-of-interest's operational environment;
- examples include modeling/design tools, test harnesses, training systems, compilers and fabrication systems;
- distinguishes system-of-interest, enabling system and other systems in operational environment.

Carries:
- rejection of `Technical Work Environment ⊂ product operational world` as a universal rule;
- support/lifecycle role distinction;
- selected-system reference.

## B4 — NASA Systems Engineering Handbook / ConOps Appendix S

URLs:
- https://www.nasa.gov/reference/appendix-s-concept-of-operations-annotated-outline/
- https://www.nasa.gov/reference/system-engineering-handbook-appendix/

Observed content:
- ConOps separately covers system scope/external interfaces/enabling systems;
- Physical Environment;
- Support Environment;
- nominal and off-nominal operational scenarios;
- environmental, organizational and scientific/technical impacts.

Carries:
- physical/operating conditions and support conditions as separable lower concerns;
- lifecycle/off-nominal conditions;
- actual effects/impacts as system/environment concerns.

Limitation:
- mission/product lifecycle framing; support after fielding is narrower than the project's general execution-condition branch.

## B5 — ISO 34503:2023 Operational Design Domain

URL:
- https://www.iso.org/standard/78952.html

Observed content:
- ODD specifies static and dynamic operating conditions within which an automated driving system is designed to function.

Carries:
- specified/assumed operating envelope as distinct from actual realized environment conditions;
- static/dynamic operating-condition vocabulary.

Limitation:
- automated-driving specific; used as a counterexample/generalization prompt, not universal ontology.

## B6 — SEIPS 2.0

URL:
- https://pmc.ncbi.nlm.nih.gov/articles/PMC3835697/

Observed content:
- six interacting work-system components: persons, tasks, tools/technologies, organization, internal environment and external environment;
- internal environment includes physical factors such as lighting/noise/temperature/layout/air;
- external environment includes broader macro conditions;
- components interact dynamically/hierarchically.

Carries:
- nontechnical physical/environmental conditions matter to Work;
- lower tool/person/task/organization distinctions should not be swallowed by Environment;
- `support` is too narrow if read only positively/technically.

Limitation:
- healthcare/human-factors framework, not project-level decomposition evidence by itself.

## B7 — ILO Human Factors and Ergonomics

URL:
- https://www.ilo.org/ergonomics

Observed content:
- work systems comprise humans, tasks, tools/technologies, organization and work environment;
- physical, cognitive and psychosocial factors interact.

Carries:
- work environment/conditions are broader than technical tool support;
- simultaneously warns against collapsing humans/tasks/tools/organization into one environment object bucket.

## B8 — O*NET Work Context

URLs:
- https://www.onetcenter.org/dictionary/31.0/json/work_context.html
- https://www.onetonline.org/find/descriptor/browse/4.C

Observed content:
- Work Context defined as physical and social factors influencing the nature of work.

Carries:
- independent support that execution conditions include physical/social dimensions.

Limitation:
- occupational descriptor model; social context categories may overlap project Actors/Work/relations and therefore cannot be imported as semantic ownership.

## B9 — Cognitive Work Analysis / Work Domain Analysis

Source examples:
- https://www.sciencedirect.com/topics/computer-science/work-domain-analysis
- applied CWA/WDA literature inspected during adequacy and current pass.

Observed content:
- work domain described through physical and purposive constraints within which activity takes place;
- Work Domain Analysis does not itself describe activity;
- wider CWA phases separately address activity, organization and worker competencies.

Carries:
- Domain/Effect reality as distinct from Work/activity and Actors;
- constraints/capabilities can be analyzed independently of particular task sequences;
- supports non-collapse of Work/Actors into Environment.

Limitation:
- `work domain` terminology is framework-specific and can include engineered/social constructs.

## B10 — operational-context research (Disdier et al., Systems Engineering 2024)

URL:
- https://incose.onlinelibrary.wiley.com/doi/10.1002/sys.21775

Observed content:
- no universal consensus on operational context;
- context is focus-relative and dynamic;
- situation/context values influence/explain system behavior over time.

Carries:
- focus/reference dependence;
- dynamic contextual conditions;
- naming caution.

Limitation:
- their `context` is broader than the project's Environment and can include representation/situation-history semantics; used as challenge, not direct definition.

## B11 — affordance / ecological psychology literature

Representative open source inspected:
- https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2013.01003/full

Observed content:
- affordances/action possibilities are relationally specified through environmental features and perceiver/actor capacities.

Carries:
- Actor capability ≠ situated actionability;
- Environment contributes condition-side structure without owning full actionability semantics.

Limitation:
- affordance theories are contested and vary; used only for relational actionability claim.

## B12 — Work System Theory (Alter)

Source:
- Steven Alter, `Work System Theory: Overview of Core Concepts, Extensions, and Challenges for the Future`, JAIS 2013 (AIS eLibrary and related open material inspected during adequacy).

Observed structure:
- distinguishes processes/activities, participants, information and technologies; environment, infrastructure and strategies appear around the work system.

Carries:
- support/environment/infrastructure concerns can be separate from Work, participants and Information;
- argues against one residual Environment bucket.

Limitation:
- exact WST element structure is not the project's hierarchy.

# C. Evidence synthesis limits

The strongest Environment conclusion arises from convergence and falsification:
- project operating-world and TWE corpora independently exposed realized-condition semantics;
- systems engineering supports boundary relativity and distinct operational/enabling/support roles;
- HFE/SEIPS/O*NET expose nontechnical execution conditions;
- CWA distinguishes work-domain constraints from activity/actor analysis;
- ODD and project evidence preserve specification/observation versus actual-state distinctions;
- affordance literature supports relational actionability;
- cross-domain holdouts found no forced third Environment branch.

Limitations:
- no independent source publishes the exact `Domain/Effect Reality + Work Conditions` two-role project synthesis;
- several external traditions use `environment`, `context`, `work domain`, `infrastructure` and `support` at different abstraction levels;
- scenario tests are analytical counterexamples, not deployment validation;
- final completion review is same-model self-review, not independent verification.
