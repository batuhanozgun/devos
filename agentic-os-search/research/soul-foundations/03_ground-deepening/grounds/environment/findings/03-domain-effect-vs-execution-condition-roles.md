# Environment Finding 03 — Domain/Effect Reality vs Execution-Condition Roles

**Status:** current Environment-ground finding  
**Question:** are two first-order Environment roles sufficient, and is `Work-Support Environment` the right second-branch framing?

## Current finding

The **two-role structure survives**, but the second branch needs a semantic correction.

Stronger working decomposition:

```text
Environment / Operating Reality
    ├─ Domain / Effect Reality
    └─ Work Conditions / Enabling–Constraining Environment
         └─ Technical Work Environment as a deep technical specialization
```

Labels remain provisional.

## Role A — Domain / Effect Reality

Primary question:

> What actual reality is the Work about, trying to understand, accommodate, navigate, maintain, transform, or judge outcomes against?

Examples:
- patient's physiological state in treatment;
- physical terrain/traffic in autonomous navigation;
- market/customer state in business decision Work;
- specimen/phenomenon in scientific Work;
- actual behavior/properties of software under development;
- damaged infrastructure in repair Work.

The role includes actual state, processes/dynamics, disturbances and effect space. It is not the representation/model of those facts.

## Role B — Work Conditions / Enabling–Constraining Environment

Primary question:

> What realized conditions, capabilities, resources, interfaces and surrounding circumstances materially shape whether and how the focal Work can be performed?

This includes positive support and negative/limiting conditions:
- technical tools/services/runtimes;
- physical workspace, temperature, noise, lighting and access;
- available equipment/material/capacity;
- communication or logistics infrastructure;
- network/service/resource availability;
- hazards/interference/contention;
- realized institutional or regulatory conditions insofar as they constrain feasible execution;
- support personnel/services only in their situated support-condition role, without absorbing Actor semantics.

## Why `support` alone is too narrow

Human-factors and occupational frameworks repeatedly include physical and social conditions that influence work but are not naturally described as support. SEIPS includes internal physical environment and external macro conditions; O*NET defines work context through physical/social factors influencing work; ILO HFE treats work environment as one interacting part of a work system.

The existing TWE research already contained negative semantics such as constraints, isolation, degradation, unavailability and capacity limits. Therefore the *content* of the old branch was broader than the positive connotation of its name.

Current correction:

> **Use a neutral enabling–constraining/execution-condition concept at the parent branch; preserve Technical Work Environment as the technical specialization.**

## Branch membership is role-relative, not exclusive

A condition is classified by **why it matters to the focal Work**, not by intrinsic type.

Examples:

### Temperature
- target variable in climate-control Work → Domain/Effect role;
- occupational heat constraint during unrelated maintenance → Execution-condition role;
- both roles when Work must repair a system while heat is both the failure state and a safety constraint.

### Repository
- product/codebase being changed → Domain/Effect role;
- service/interface necessary to carry out development → execution-support role;
- stored meaning/provenance remains Information semantics under another ground.

### Regulation
- regulatory state can be part of the domain/effect space of compliance or policy-analysis Work;
- its current applicability may constrain another Work's feasible execution;
- rule text/interpretation is Information and issuing/enforcement authority retains Actor/control semantics.

## Third-branch challenge

Candidates such as `ambient context`, `external disturbance`, `physical environment`, `institutional environment`, `resource environment` and `social environment` were tested conceptually.

No third peer branch is currently forced if roles are non-exclusive:
- if a condition matters because Work is about or affects it → Domain/Effect;
- if it matters because it enables, constrains, degrades or shapes execution → Work Conditions;
- if both, assign both analytical roles;
- if neither, it is not load-bearing Environment for that focal analysis merely because it exists.

## Result

The current best Environment decomposition remains **two first-order roles**, but the old `Work-Support Environment` label is weakened.

Preferred working phrase for the second role:

> **Work Conditions / Enabling–Constraining Environment**

This is a research-language correction, not an architecture rename.
