# Hierarchical Ground Deepening Method

**Status:** user-authorised planning method; substantive branch research requires separate activation
**Date:** 2026-09-02
**Scope:** recursive research sequencing inside an accepted top-level ground

## Purpose

Deepen a top-level research ground hierarchically without turning one research turn into a mixed multi-level ontology exercise.

The method separates three activities that must not silently collapse into one another:

1. research one currently selected node/branch;
2. identify its immediate child problem regions, if any;
3. later research those children one at a time.

Finding a child does not authorize researching that child in the same pass.

## Core rule — one active node at a time

During substantive research, **at most one hierarchical node is active**. When a node pass is running, exactly one node is active; between passes or while a closed result awaits user evaluation, zero nodes may be active.

Examples:
- `Environment` may be the active node;
- after Environment closure, `Domain Reality` may become the active node;
- if that node yields three immediate children, only one child may later be active at a time.

Sibling nodes remain inactive. They may be referenced only for boundary tests, counterexamples or relation capture.

## One-level discovery rule

A node-level research pass should aim to determine:
- whether the node is coherent at its claimed level;
- its boundary and non-collapse rules;
- its immediate first-order child problem regions, if any;
- cross-cutting dimensions that should **not** be mistaken for children;
- residual uncertainty and falsifiers.

Do not recursively deep-research grandchildren during the same pass merely because they become visible.

A deeper child may be probed enough to validate that the split is real, but not enough to silently convert the current pass into a second active node.

## Child-promotion test

Promote a candidate as a distinct child branch only when separating it is materially useful. At least one of the following should hold:
- it has a distinct first-order question or protected outcome;
- it exposes failure modes not adequately explained by siblings;
- materially different external traditions or mechanisms converge on the distinction;
- collapsing it into a sibling repeatedly loses decision-critical information;
- it has a distinct boundary/reduction behavior relevant to later SOUL/Development OS reasoning.

Do **not** create a child branch merely because:
- terminology permits finer categorization;
- examples can be grouped by type;
- a cross-cutting dimension such as state, time, observability or boundary applies broadly;
- a domain-specific taxonomy exists but does not generalize to the project level;
- symmetry would make the tree visually cleaner.

## Cross-cutting-dimension test

Before promoting a candidate child, ask whether it instead behaves like a dimension that recurs across several children.

Typical examples may include:
- realized state;
- dynamics/history;
- observability;
- uncertainty boundary;
- identity/equivalence;
- boundary/reference frame;
- causal/effect timing.

Cross-cutting dimensions remain explicit research dimensions but are not automatically hierarchical children.

## Node research sequence

### N0 — Canonical recovery
Recover the parent result, relevant sibling boundary, historical evidence and current open questions before new search.

### N1 — Node coherence attack
Treat the selected node label and level as hypotheses. Test split, merge, reduction and rename rivals before building deeper taxonomy.

### N2 — First-principles problem inventory
Derive the problems that genuinely belong to the selected node without importing a ready-made external taxonomy as the answer.

### N3 — Immediate-child discovery
Cluster only those problems that appear to form stable first-order subregions. Keep rival decompositions alive until tested.

### N4 — Boundary and anti-collapse tests
Stress-test each candidate child against:
- siblings;
- parent;
- neighbouring top-level grounds;
- role switching;
- nested/reference-relative cases;
- actual-vs-representation distinctions where material.

### N5 — External and cross-domain falsifiers
Use materially different source traditions and domain holdouts to challenge the split. Repeated same-style examples are insufficient evidence of completeness.

### N6 — Omission / reduction / rival-decomposition audit
Try to produce:
- a missing first-order child;
- a forced-fit case;
- a reason to merge or split the selected node differently;
- evidence that a supposed child is only a cross-cutting dimension.

Label same-model audit as non-independent verification.

### N7 — Node closure and user evaluation
Close only when the immediate-child map is boundedly sufficient for the current level and additional broad probes show declining structural information gain.

Return to the user before activating a child or sibling.

## Stop-descending rule

Do not descend forever.

A node may be treated as a leaf for the current foundation research when:
- no stable immediate child split survives adversarial testing;
- candidate splits are merely dimensions, mechanisms or domain-specific profiles;
- further decomposition would not change later problem framing, failure analysis, relation structure or design reasoning materially;
- additional search mostly refines vocabulary/examples rather than exposing a new first-order region.

Leaf status is bounded and reopenable; it is not a universal claim that no finer taxonomy exists.

## Continuity rule

For every node pass persist:
- node state;
- immediate-child candidates/result;
- focused findings;
- source/view ledger;
- deferred cross-node/cross-ground relations;
- completion/omission audit;
- exact current surfaces when closed.

A fresh session must be able to tell which node is active, closed, awaiting evaluation or merely planned.

### Pass-artifact provenance

Focused findings, source ledgers, plans and audits may preserve the labels, candidate status and wording that were current **during the pass that produced them**. Once a node closes or is refined by a deeper child pass:
- current hierarchy, authorization and epistemic status come from the current `STATE.md`, `KEY.md`, `FINDINGS-MAP.md` and `CURRENT-SURFACES.md` route;
- pass-time metadata must not be interpreted as present authorization;
- if a preserved pass artifact can reasonably be mistaken for current state, its package router or the artifact itself should carry an explicit executed/preserved/subsequent-refinement notice;
- historical reasoning should not be retroactively rewritten merely to make it look as though later refinements were already known.

## Phase guardrail

Hierarchical deepening is still research.

Do not infer from a stable tree:
- ontology classes;
- architecture modules;
- database schemas;
- final relation/control model;
- implementation components.

Research hierarchy and architecture decomposition remain separate decisions.
