# Returned Influence — G1 Return Boundary and Semantic Core

**Status:** COMPLETE / PARENT WORDING REFINEMENT REQUIRED  
**Date:** 2026-09-11

## 1. A return must be relative to something

`Information I influenced later action A` is not enough to identify feedback. It establishes, at most, an informational causal relation. The inquiry must identify the bounded process, system or continuing pursuit whose realized condition/performance is being brought back into a relevant response path.

Contrast these constructed cases:

| Case | Interpretation |
|---|---|
| A new client request specifies a new product | Usually a forward instruction/input, not feedback merely because it changes a plan |
| A test of the current product returns a failure that informs its correction | Returned performance information in the product-development pursuit |
| A customer evaluates a delivered product and the team changes a later version | Feedback can span actors and versions within an explicit continuing pursuit |
| A team reads an unrelated organization's study | External evidence/transfer input; do not label it this system's feedback without establishing the relevant return relation |
| A current sensor reading informs a system's response | It need not have been caused by the controller's own previous command; disturbances and initial conditions can also be observed |

Choosing a sufficiently enormous boundary after the fact must not make every information flow feedback. The boundary must be relevant to the inquiry and preserve what operation/outcome is being informed. Boundary changes must be disclosed because the same message can play different roles in different loops.

S1 in `SOURCE-LEDGER.md` supplies the coupled-system/closed-loop pressure. S2 supplies an implemented distributed response pattern. Our cross-ground interpretation does not claim either source publishes this Foundation region.

## 2. Feedback versus feedforward is not simply past versus future

An output-derived prediction can remain part of a feedback response. Conversely, information about an external input can feed a prospective adjustment without measuring the controlled process's output. Classify by the signal's functional relation to the relevant process, not merely its timestamp or whether the message uses future tense.

This pass does not impose one engineering feedforward formalism on every domain. It preserves the narrower diagnostic rule: a future-oriented response is not automatically feedback, and a forecast is not automatically outside feedback.

## 3. Same actor and continuous recurrence are not required

A producer can be different from the observer, evaluator, decision-maker and implementer. The return path may cross a tool, human team, queue, record or later session. Exact role and scope binding matters more than a requirement that one agent both act and critique itself.

A single returned episode can inform later response in a continuing pursuit. A repeatedly operating loop is a stronger temporal/topological claim than one such episode. Do not infer indefinite recurrence from one observed response or require infinitely recurring operation to recognize one return.

## 4. Ground-local dynamics remain protected

Multiple components do not automatically imply multiple Foundation grounds. A physical feedback example may be used to challenge a definition while its own domain-level dynamics remain Environment research.

Route here when the question irreducibly concerns how realized condition/performance, its representation, and a relevant Work/Actor/Control response are semantically composed across accepted grounds. Merely measuring an otherwise ground-local dynamic for research does not create cross-ground feedback.

The distinction is about the protected inquiry, not assigning every device or process permanently to one node.

## 5. Minimum returned-influence grammar

Preserve the following when necessary to state the claim without material ambiguity:

```text
Returned-influence inquiry
├─ bounded system/process/continuing pursuit and inquiry scope
├─ realized source condition/performance/event/artifact
├─ signal or assessment about that source
│  └─ provenance, derivation and claimed referent kept distinguishable
├─ exact return relation and relevant consumer/response process
├─ applicability: target, role, stage, time/version/context
├─ claim level: topology / active use / episode contribution / outcome effect
├─ operative response locus
│  └─ evaluation, choice, timing, inhibition, continuation, action, etc.
├─ downstream realization boundary when an effect is claimed
└─ evidence, competing explanations and uncertainty
```

A numerical setpoint, scalar error, explicit reward, named controller, two-node edge, continuously recurring loop or persistent rule change is not universal. Some may be crucial in a particular inquiry.

This is a semantic checklist, not a storage schema. It does not require all optional details for every harmless everyday use of the word feedback.

## 6. Signal truth and actual influence are different

A false report can affect a decision. That establishes neither the reality of the reported condition nor valid source binding. Keep at least three claims separate:

1. a message was generated and returned;
2. it accurately represented the claimed source condition;
3. it operatively influenced a specified response.

An active loop can be driven by corrupt input. Label the corruption rather than treating influence as evidence of truth or treating false content as proof that no influence occurred.

Likewise, synthetic test feedback can be genuine feedback about a synthetic execution; it does not become production feedback by changing the label.

## 7. Narrow parent delta

The parent supplied the important phrase 'returned causal influence' but sometimes abbreviated it as any earlier observation changing later behavior. Current refinement adds an explicit return reference and separates claim levels. G2 tests the visible-change part. The two parent questions remain useful; their wording is not exempt from correction.

A bounded, reference-relative returned-influence core survives. Neither arbitrary information flow nor a universal single-controller pipeline is sufficient. No separate child is justified merely for return topology, consumer identity or feedback/feedforward comparison.
