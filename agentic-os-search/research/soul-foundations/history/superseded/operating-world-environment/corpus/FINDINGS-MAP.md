# Environment — FINDINGS MAP

**Document role:** current topic router  
**Vertical revision:** `environment-foundation-2026-09-01-r1`  
**Status:** bounded research result; not architecture truth

## Current result at a glance

The research supports a distinct **foundation problem region** around boundary-relative operating-world state/dynamics, but does **not** validate Environment as a mutually exclusive fourth object class or required fourth architecture module.

`Environment` remains a working research label. `Operating world` / `operating situation` are candidate alternative framings, not accepted terminology.

## Findings

### F1 — Environment membership is boundary-relative

Read: `findings/01-boundary-relative-environment.md`

Keep:
- system-of-interest and analytical purpose/level are load-bearing;
- inside/outside membership can change with boundary/coupling;
- do not classify entities intrinsically as `Environment`.

### F2 — Context is not Environment

Read: `findings/02-context-is-not-environment.md`

Keep:
- context is selective/relevance-bearing and may emerge through activity/interaction;
- live world state, contextual relevance and persistent context representation are not the same thing.

### F3 — Situated actionability is relational

Read: `findings/03-actionability-is-relational.md`

Keep:
- Actor capability/competence alone does not determine what is currently possible;
- environmental conditions/resources/interfaces can change actionability while Actor facts remain stable;
- affordance/actionability is safer as a relation/derived condition than an intrinsic Environment property.

### F4 — World state ≠ observation ≠ belief ≠ Record

Read: `findings/04-world-state-observation-and-record.md`

Keep:
- actual/current world state may be hidden, noisy, delayed or changed independently;
- observation and belief are representations/epistemic states about the world;
- Records preserve assertions/knowledge/history, not the underlying world by identity.

### F5 — Tool/runtime/infrastructure are boundary-dependent roles

Read: `findings/05-tools-runtime-infrastructure-are-boundary-roles.md`

Keep:
- a concrete tool/system/resource can be internal element, external system, enabling system, infrastructure, mediator or resource depending on boundary/activity;
- runtime conditions are a real operating-world case but do not require a separate first-order technical-environment family.

### F6 — Null reduction fails at the problem-region level, not the module level

Read: `findings/06-reduction-and-null-hypothesis-test.md`

Keep:
- Records + Work + Actors alone cannot preserve cases where those facts stay fixed but external/current world state changes and alters feasibility/outcomes;
- typed relations may avoid a fourth object bucket/module;
- if those relations require external states/conditions/resources/interfaces as relata, the underlying problem region has been represented relationally rather than eliminated.

## Strongest non-collapse rules

- Environment/world state ≠ Context.
- Environment/world state ≠ Observation.
- Observation/belief ≠ persistent Record.
- Actor capability ≠ situated actionability.
- Work readiness/failure/effect ≠ underlying external condition.
- Tool/resource/infrastructure ≠ intrinsic Environment object type.
- Other Actor ≠ only Environment; one entity can retain Actor semantics while its behavior contributes to another system's environment.
- Boundary choice ≠ harmless presentation detail.
