## Current bounded result

The vertical does not support one permanent universal Records checklist.

The stronger method is:

> recurrent context-bound appraisal → a dated, evidence-backed Records requirement profile/contract.

The profile is a current checkpoint under explicit assumptions, not a timeless taxonomy or metadata template.

## Derivation inputs

Material inputs can include:

- exact resource/population and identity granularity;
- protected future use/outcome;
- retrieval/reconstruction needs;
- horizon and expected environmental change;
- consequence/risk dimensions that actually change requirements;
- applicable legal/policy/security/privacy/archival constraints;
- change/standing behavior;
- transformation/migration/transfer exposure;
- dependencies/aggregation;
- target users / assumed knowledge / interoperability boundary.

## Baseline first

Contextual derivation cannot waive a valid inherited obligation.

Begin with any applicable external baseline/mandate floor; then derive applicability, additional obligations, permitted satisfaction modes and stronger assurance where needed.

`NOT REQUIRED` is valid only when no applicable mandate or protected-use dependency requires it.

## Keep four decisions separate

For each obligation ask independently:

1. Is it required?
2. How strong/deep must it be?
3. Where/how can it be satisfied?
4. How will sufficiency remain observable/verified?

`Required` does not mean `must be an object-local field`.

## Requirement states

Use at least:

- `REQUIRED`;
- `NOT REQUIRED FOR CURRENT PROFILE`;
- `UNKNOWN / NEEDS EVIDENCE`.

For a material `NOT REQUIRED` decision, test a credible counter-scenario that would activate the omitted obligation and confirm that its activating condition is actually outside the current profile.

## Counter-check corrections retained

- protected use must include evidenced legal/accountability/archival/future-use interests in scope, not only current business convenience;
- do not promise support for all imaginable future uses;
- use the broadest profile scope that does not hide a requirement-changing discriminator; bounded overlays are preferable to one profile per object;
- risk dimensions are prompts, not a mandatory universal risk matrix;
- external/inherited satisfaction requires dependency assurance and exact binding; `external` is not a quality level;
- a one-time acceptance test does not prove ongoing satisfaction where dependencies/currentness can change;
- profile applicability itself can have history and must be re-appraised when material assumptions/context change.
