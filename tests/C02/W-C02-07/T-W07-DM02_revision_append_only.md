## Cases (one set per revision table, from the catalogue)
- **DM02-<table>-ins** (positive control): a new revision row is appended at the owner level.
- **DM02-<table>-upd**: `UPDATE ... SET revision = revision + 1000` on that row. The row is unchanged afterwards (refused, raising or not).
- **DM02-<table>-del**: `DELETE` of that row. The row is still there.
- **DM02-<table>-trunc**: `TRUNCATE ... CASCADE`, twice, each attempt undone: (1) as deployed, every trigger in place; (2) the table's own rule alone: inside the attempt, every other table the cascade reaches (the tables whose foreign keys reference this one, recursively) has its user triggers disabled, so that only this table's own rule can refuse. The row is still there after both; the case is `ok` only then (revision under ledger rule 3, 2026-10-14, below).
- **DM02-list** records the tables found; **DM02-pre** is `could_not_check` when one of the five is absent.

Every attempt runs as `postgres`, the migration role and owner level, which is the strongest role a test reaches. The application roles' direct writes are T-W07-5A's.

## Could not check
The test gives COULD NOT CHECK when one of the five revision tables, or its `revision` column, is absent. A table's cases give `could_not_check` when no revision row can be planted in it. A table's `-trunc` case gives `could_not_check` when the user triggers of a table its cascade reaches cannot be disabled for the second attempt (for example where `postgres` does not own that table), naming the error; the first attempt's outcome is in its detail. Before the build exists the test gives COULD NOT CHECK.

## Revision under ledger rule 3 (2026-10-14; written by: test-designer, agent `a033d27a36478231f`)
- **What was seen.** W-C02-08's producer ran the merged break B-DM02-1 on a throwaway PostgreSQL 16 copy of the build, as an offline supporting run (the executor's account to the test designer, 2026-10-14; the test designer read no file of that build or run). DM02-work_revision-upd and -del turned red; DM02-work_revision-trunc stayed green. Cause: the case's `TRUNCATE devos_private.work_revision CASCADE` also truncates the tables whose foreign keys reach `work_revision`, among them `assignment`, then `operation`, then `observation`, and observation's own append-only trigger refuses the whole statement. The row survives, so DM-02's rule holds on that build, but the refusal came from another table's rule, so B-DM02-1 (which removes only `work_revision`'s) could not show the case. The failure class is wider than that one table: on any revision table, a case whose refusal another table's rule can give stays green under a break of its own table's rule.
- **What changed.** The case, not the break, and only by adding: `-trunc` keeps its first attempt as it was (as deployed) and adds a second, in which `pg_temp.w07_dm02_cascade` lists every other table the cascade reaches and each has its user triggers disabled inside the attempt, undone with it, so only the table's own rule can refuse. The case is `ok` only when the row survives both, so a pass now asks more than before (the second attempt's refusal implies the first's, since the table's own trigger fires in both). B-DM02-1 is unchanged, with the same three red cases. No case ID changed; no case was removed.
- **Cases changed.** DM02-<table>-trunc, for every revision table the catalogue lists (`mission_revision`, `work_revision`, `finding_revision`, `artifact_revision`, `decision_revision`, and any other `*_revision` table). DM02-<table>-ins, -upd and -del, DM02-list and DM02-pre are unchanged.
- **Earlier results.** Every earlier result of this test is void. The only earlier runs are the producer's offline supporting runs named above; none was counted. The self-checks above are the test designer's and were never results.
