Tokens are issued at run time inside the rolled-back transaction and never written down (README section 6).

## Cases
- `N01-pos`: a complete need, working token → accepted, one `need` row more.
- `N01-neg1`: `why_needed` = `""` → refused naming `why_needed`; no row.
- `N01-neg2`: `why_needed` absent → refused naming `why_needed`; no row.
- `N01-neg3`: `why_needed` whitespace only → refused naming `why_needed`; no row.
- `N01-share`: the `need` stream's `block_size` is 10 (W-C02-04's recorded share, DM-08).
- `N01-fbm1`: from a block boundary, one complete block (10) of needs whose `why_needed` is `-` → all accepted; exactly one sample review queued for `devos_denetim` in the block, on one of them.
- `N01-fbm2`: the same with a circular justification ("it is needed because it is needed").
- `N01-rate`: three complete blocks (30) of complete needs → exactly one sample review per block, 3 of 30; tolerance 0. **[Designer's addition: R2 section 5 (c) leaves N01's tolerance empty; the reason is EV-C02-002 DM-08 (a) and (b): exactly one sample per complete block, at a position drawn when the block opens, so a run of complete blocks samples exactly one record each and "the test needs no tolerance"]**
- `N01-writer`: two blocks whose every need carries writer-chosen keys (`sample: false`, `skip_sample: true`, `sample_position: 1`) → still exactly one sample per block; or the keys are refused (then the writer cannot steer either).
- `N01-tok-devos_calisma`, `-devos_denetim`, `-devos_sinav`, `-devos_kurulum`: `open_review` with `kind = sample` on an accepted need, with each class's token → refused by the function, returned, and recorded once under the caller's class in RejectedAttempt (DM-19 (a)); the count of reviews of kind `sample` unchanged. A raised error is `bad` (the function did not refuse the call; a later layer stopped it), except SQLSTATE class 42 (the call could not be formed), which is `could_not_check`.
- `N01-same-answer` (phase C4b; EV-C02-008 5.2's table and (b); CHK-C02-028 F7): from a block boundary, one complete block of ten needs written with the same arguments (working token): the ten answers differ in nothing but each record's own id; a sampled mark, an event id or any other value that differs is `bad`. The block must draw exactly one sample (else `could_not_check`), so that a drawing write is among the ten.

**Part B (phase C4b; `harness/scenarios/n01_open_block.sql`; EV-C02-008 5.2's table).** Each stream's steps run in four transactions: (1) the stream aligned to a block boundary with complete records, then records written with the working token until the database draws one, with the block not yet complete (if the draw falls on the block's last record the next block is tried, at most six); the sampled record t, an undrawn record u of the same block, the sample s, and a work item relating to each of t and u (`derived_from`: "the same relations"); (2) every found reader, with each class's token, with t, u and s; (3) inside the open block, a Verdict v on s with the audit token; (4) the same reads again, then the sub-checks.
- `N01-unseen-cal`, `-sin`, `-kur`, `-ci` (the need stream): with that class's token, (a) **reads**: each found reader's answer is unchanged by the Verdict (any value that changes with withheld records, the growing event ID among them, is a difference), holds neither s's id, v's id nor an id of their events, and is the same with t as with u, ids aside; (b) **relate** (for the classes `relate`'s gate admits: `cal`, `sin`, `kur`), run before the walks: `relate` with s's id, and with v's id, as an end gives the answer (ids aside) and recorded reason code of the same call with an id that names no record; (c) **walks**: `affected_entities` from t, and `explain_paths` from t to its relating item, give the answer of the same calls on u (ids aside: the same nodes and the same completeness flag); with s's id, and with v's id, as root, the answer and recorded reason code of an id that names no record. Each case is `ok` only when every sub-check is.
- `N01-unseen-den` (positive): with the audit token, a found reader returns s, one returns v, and, where a found reader names the event table, one returns an id of their events (the queue, B:247).
- `N01-unseen-after` (positive): the block then completed with complete records; with the working token, a found reader with t returns v.
- `N01-unseen-routine-work`, `N01-unseen-routine-decision` (EV-C02-008 5.2's list for `T-W07-N29`): the same as N01-unseen-cal, in the streams of work items and of decisions labelled `routine`, working token.

The alignment: before each block run the stream is brought to a block boundary with complete needs (read from `block_size` and `block_seen` at owner level), so each block counted is a complete block of the planted kind. If the stream cannot be aligned, the case is `could_not_check`.

## Format gate (point 4)
"Filled but meaningless": `why_needed` = `-` (`N01-fbm1`) and a circular justification (`N01-fbm2`). The database must accept them; each block of ten lands one of them in sample review, as a `Review` of kind `sample` queued for `devos_denetim`. What the audit environment then judges is outside C02 (W-C02-10 "Not covered" (a)).

## Could not check
The test's own result is COULD NOT CHECK when an object above is absent (`N01-pre`, the case before the build exists), when the fixture Mission cannot be made, when the stream cannot be read or aligned to a block boundary, or when a token cannot be issued. Never PASS. `N01-same-answer` when its block draws other than one sample. Part B: a case is `could_not_check` when its open block cannot be planted (no draw in an open block in six blocks; a stream's block of 1, which a scenario run earlier in the same database can leave, as `T-W07-N28` part B2 does for decisions; a record or the Verdict not accepted), when a read or a call is not answered in interface v1's form, or when the walk fixtures cannot be made; `N01-unseen-den` and `-after` when no reader is found (the build names R12's reader and the queue's, EV-C02-008 1.4). Part B runs only under the harness: before a harness run it has no result, and the test is not PASS.
