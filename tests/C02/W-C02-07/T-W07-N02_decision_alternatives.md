## Cases
For each class `high_impact` (`-hi`) and `batu` (`-batu`), with the working token:
- `N02-pos-compared-*`: compared options and every gated field → accepted.
- `N02-neg-none-*`: no options, no `alternatives_considered`, no `single_viable_path_reason`, no `alternatives_state` → refused, naming the alternatives; no row.
- `N02-neg-compared-empty-*`: `alternatives_state = compared` with an empty `options` list → refused.
- `N02-neg-single-blank-*`: `alternatives_state = single_viable_path` with a whitespace reason → refused.
- `N02-neg-premises-empty-*`, `N02-neg-premises-absent-*`: `premises` empty or absent (the "major design decision without premises", DM-27) → refused naming `premises`.
- `N02-pos-single-*`: a single feasible path with its justification, no options → accepted.
- `N02-pos-single-one-option-*`: the same with exactly one option → accepted (no invented second option needed).
- `N02-pos-open-exploration-*`: `alternatives_state = open_exploration`, no options → accepted at `open`.
- `N02-oe-answer-*`, `N02-oe-accept-*`: a decision opened in `open_exploration` with no options and no reason, then answered (to its current revision) or accepted at owner level → refused; status stays `open`.
- `N02-oe-pos-reason-*`: after a new revision that enters `single_viable_path_reason`, the answer → accepted. `N02-oe-pos-options`: after a revision that enters compared options, the acceptance → accepted.
- **The ledger transfer's two transitions** (phase C5, CHK-C02-030 C6; replacing the placeholder `N02-oe-transfer`). W-C02-06's design is accepted (CHK-C02-024, PC-44): `transfer_decision` writes a decision directly in its recorded status, never passing through `open` (EV-C02-005 2.2; B:308), and `transfer_acceptance` sets a Decision's status to accepted (EV-C02-005 2.4). Both are called with the `devos_kurulum` token after `begin_transfer_run` opens a run. Their payload keys are **chosen** by README 8.1's rule (no source names them, EV-C02-005 section 12): B 3.17's fields as for `open_decision`, with `status`; `run_id` and `transfer_source` {`kind`, `source_id`, `path`, `input_commit`, `last_commit`, `sha256`} (EV-C02-005 section 15 S1's keys); for an acceptance, `target_ref`, `review_ref`, `accepted_use` `installation_acceptance`, `scope` `installation`, `current_evidence`. If W-C02-09 names other keys, the cases are revised before the first result (README section 8).
  - `N02-oe-transfer-decision`: `transfer_decision` of a `high_impact` decision in status `answered`, `alternatives_state = open_exploration`, no options and no `single_viable_path_reason` → refused, no decision row written. Its pair `N02-oe-transfer-decision-pos`: the same with `single_viable_path_reason` entered → accepted, one decision written, status `answered`.
  - `N02-oe-transfer-accept`: `transfer_acceptance` of a decision opened in `open_exploration` with no options and no reason → refused, the decision's state unchanged. Its pair `N02-oe-transfer-accept-pos`: the same for a decision whose revision entered `single_viable_path_reason` → accepted, status `accepted`. The Review copy and its `pass` Verdict that each names are planted at owner level, with the tables' triggers off for that insert only (README 5.1 (a): the rule under test is the decision's; DM-41 (a) would otherwise refuse a Review of a decision revised in the file's one transaction).
  - If a pair is not accepted, its refusal shows nothing about the rule, and both give `could_not_check` with the reason; so does the whole group when a transfer function is absent or `begin_transfer_run` is not accepted.
  - **No `transfer_decision` case with status `accepted` is tried** (CHK-C02-046 C6; CHK-C02-030 C6 (a)'s "in an answered or accepted status"). EV-C02-005 2.4 gives the accepted status to `transfer_acceptance` alone: it "sets the target's acceptance: ... `status` to `accepted` for a Decision whose record shows that state", and "Until C03 this is the only path that sets an installation record accepted". So a conforming `transfer_decision` writes no decision `accepted`. A negative case with status `accepted` would be refused for that reason alone, whatever the open-exploration rule, so its refusal would show nothing about the rule. Its positive pair would not be accepted, so it would be `could_not_check` on every conforming build, the defect CHK-C02-030 C2 forbids. The accepted transition on the transfer's path is covered by `N02-oe-transfer-accept` with `N02-oe-transfer-accept-pos`.
- `N02-oe-answer-decision`: present only if the build has `devos_api.answer_decision`; then COULD NOT CHECK until the case is written for it.
- `N02-fbm1`, `N02-fbm2`: one complete block each of `high_impact` decisions filled but meaningless → all accepted; one sample per block.

## Format gate (point 4)
Kind 1 (`N02-fbm1`): every gated list filled with `x` and `reversibility` = `x`. Kind 2 (`N02-fbm2`): a single path whose reason is circular. The database accepts both; each complete block of ten lands one of them as a `sample` Review queued for `devos_denetim`.

## Could not check
Since phase C5 the transfer cases are written against W-C02-06's accepted design (above), so no case is `could_not_check` on every build by design. They give `could_not_check` only while the transfer's functions are absent, `begin_transfer_run` or a positive pair is not accepted with the chosen keys (revised before the first result when W-C02-09 names them), or a fixture cannot be made. Also COULD NOT CHECK when an object is absent (`N02-pre`), a fixture cannot be made, or a revision cannot be planted.
