Otherwise (iii) > 0 gives `could_not_check`: a token issued during the run, which the program did not record, is unrevoked; it may be one of its own whose ID was lost, or another issuer's. Otherwise `ok`. No time window or clock is used. Only row IDs are read and kept, never a token or a hash.
- **Ledger rule 3: the claim is kept, not narrowed or loosened.** The claim is that the program leaves none of its own synthetic tokens unrevoked (the Cases table: "no synthetic token of this run left unrevoked"). Taking each kind of unrevoked token the old window could count:
  - *A token the program recorded.* Before: `could_not_check`. Now: `bad`. This is stricter: an own token that stays live after the run is the very state the case forbids, and with the ID the program can say it is its own. The change is also what lets a break show the case (the harness counts only `bad` as red, README 5.2).
  - *A token of this run whose ID was lost, or another issuer's token issued during the run.* `could_not_check` before and now, through count (iii).
  - *A token already unrevoked before the program's first statement.* Counted before only through the 5-second margin; no longer counted. It cannot be a token of this run: the baseline is read in its own committed statement before the fixtures' first issue, and a row's ID is fixed when it is written. No function of the build clears `revoked_at`: the only update of the column in the 25 migrations, in `revoke_env_token`, sets it to `now()`. An owner's direct write could clear it, and that is listed under "Not covered" (4). So a row outside the baseline that is unrevoked at the end was issued after the baseline. The only change on this side is that the job's own tokens are no longer counted as the program's, which is the fault. So it narrows what is counted to what the claim names, and the claim itself does not narrow.
  - The baseline grows with any token left unrevoked by an earlier run. Those are counted by the run that left them (as `bad` or `could_not_check`), not by later runs. That is what the job's repeated runs need (run 4 below), and an earlier run's red stays red in its own job.
