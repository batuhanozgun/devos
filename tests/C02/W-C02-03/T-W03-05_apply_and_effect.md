# T-W03-05 · A migration merged into `main` is applied to both projects, and its effect is seen

Synthetic test data (plan Section 8 item 13): the fixture migration `supabase/migrations/20261012231841_w03_fixture_apply.sql` is made up for this test. It carries the README's first-line label and creates only synthetic objects. It merges in H1-prime (the campaign's first class-high change, H1, as revised under FR-07), with its read in `devos-test`, `supabase/migrations/tests/w03_fixture_apply_read.sql`; the read in `devos` is `T-W03-05_devos_read.sql` in this directory. All three were written by the test designer before any run of this test.

**Serves.** W-C02-03 point 5, and C02's Acceptance line "✔ A migration merged into `main` is applied by the CI job, and its effect is seen in the database." Point 5 is quoted in full in the item file. This test also serves EV-C02-001 section 10, "Point 5".

## The fixture

- **What it is.** One migration file at the top level of `supabase/migrations/`, merged through the merge gate with a fresh-context class-high verdict, after W-C02-19 is accepted. It may merge with, or after, the first migration (W-C02-08's, which creates `deployment_drift`). It cannot come before it: `deployment_drift` must exist to report "no difference" after the apply.
- **What it creates.** Objects whose definition can be read from the catalog and compared with the file: a schema `w03_fixture` with one table `w03_fixture.apply_check (id int primary key, note text not null default 'synthetic')` and one comment on that table. A second, differently named object (a view `w03_fixture.apply_check_view`, `security_invoker = true`, selecting `id` and `note` from the table) gives the second example below.
- **What it touches.** Nothing outside its schema; it removes any grant on its own objects to PUBLIC and to Supabase's API roles where they exist. It does not call `issue_env_token` or `revoke_env_token` (M24).
- **Its version.** `20261012231841`, later than the first migration's `20261012184638`: the pinned tool refuses a version below the latest recorded one (T-W03-14, "P2, settled offline"). If another migration merges before H1-prime, the file is renamed to a later version first, and the read files' version literal with it.
- **Its end.** It stays on `main`. Migrations are append-only, and M16 blocks a change once it is applied. Its schema is accounted for in point 10's listing as made by this migration (`schema w03_fixture`, `table w03_fixture.apply_check`, `view w03_fixture.apply_check_view`), and it is removed later by a forward migration if the executor decides to; that change removes the read file too, which otherwise fails every later push in `devos-test` and holds `devos`.

## What is observed (raw, each labelled with its source)

1. **GitHub's run record of the push run at the merge commit**
   - The `devos-test` job: steps apply, compare and database tests, each concluded success; the step times; the line "credential present: yes".
   - Then the `devos` job: decide gives `apply = yes`, then the dry run lists the fixture's version, then apply concludes success, then the comparison after the apply runs.
   - The `devos` job's apply starts after the `devos-test` job ends (also T-W03-14's positive control).
2. **In `devos-test`, by the job's own read after the apply** (labelled the job's own): `w03_fixture_apply_read.sql`, run by step `dbtests` of job `devos-test`, which prints each of its lines with the file's name. The definition of `w03_fixture.apply_check` from `pg_catalog` (columns in order with their types, not-null flags and defaults; the primary key; other constraints; the comment), the view's definition as fields (its kind, its columns and types, its options, the relations it reads; its `pg_get_viewdef` text is printed, not compared, because its layout is the server's), and the rows of `supabase_migrations.schema_migrations` with the fixture's version (count and name). Twelve fields, each compared with the file's text. The read runs only after a clean comparison (`dbtests`' condition); if it does not run, `devos-test`'s part is "could not check".
3. **In `devos`, by the builder's read-only connection** (EV-C00-002 item 8): `T-W03-05_devos_read.sql`, one plain SELECT with the same field expressions, whose row gives the UTC time, the server version, the two positive controls, the fields read, the fields that differ, and the two breaks' results. That connection reaches `devos` only; it is never used as evidence for `devos-test`.
4. **`deployment_drift`'s result after each apply, from the run report.** "no difference", complete, at the merge commit, for each project.
5. **Each merge's versions appear as applied in a run's report.** If the merge's run ended "superseded", the head's run lists them.
