# T-W03-09 · The credential is not found where an agent session can read it

**Synthetic test data** (plan Section 8 item 13). The planted value is a non-secret constant made up for this test. It has the form `w03-fixture/plant+value@<plant tag>=x`, so that its percent-encoded form differs from its plain form. `<plant tag>` is not a run's ID: the plants and the workflow's encoded copy are made before the search run, so no run's ID is known then. It is a tag the executor chooses when making the plants, the UTC time of planting written `YYYYMMDDTHHMMZ`. It is recorded in `inputs_ref`, so that a plant from an earlier round is not counted as this round's. This round's tag is called "the H1-prime tag" until the record names it; the tag `20261012T2338Z` is retired (CHK-C02-045 C2) and is never this round's. The executor makes the value last, after the revision's other parts (FR-07 item 3). It goes into no place but its planted ones below, of which p1 and p2 are the only files: never into another file, a file name, a commit message, a tag, a pull-request text, a verdict or a record, which name the tag only. The workflow holds it only in a form the search does not match: base64 (`W03_PLANT_B64`), decoded at run time. Its only plain occurrences are therefore the planted ones. It is never any credential.

**Serves.**
- W-C02-03 point 9, quoted: "✘ The credential is looked for where an agent session can read it, by a method that never shows it (for example a step of the job that holds it and reports only a count of matches): the repository on `main` and on every branch, and issue #6. The result is "none found by that method", with a positive control that the method finds a synthetic value planted for the purpose. That a session has no other route to it is taken from the documentation (R5 G1, G2), quoted with URL and date and labelled documented, not independently tested. The record names the layers … states D-003's residual, and claims this ✘ at that level only."
- The session half of C02's Acceptance line "✘ The migration credential cannot be read by an agent session …".
- EV-C02-001 section 10, "Point 9", and CHK-C02-008 C4 (both credentials).

## The method

This is the build's step; the test fixes what it must do and print. In each scheduled job, `check-devos-test` and `check-devos`, a step holds that job's own project's value. For each place in the table below, it counts fixed-string matches of the value and of its percent-encoded form. It treats every text it reads as data only: never run, evaluated or put into a command. It prints, per place and per form, only the count.

| Place | How read |
|---|---|
| every ref's tree and history of `devos` | every object of a full clone (all branches, tags and pull-request refs the token can fetch) |
| issue #6's body and comments | the issues API, read with the same code used for the fixture issue below |
| the logs of earlier runs of `migrate.yml` | the runs API |

**Planted positive control.** The synthetic value is planted once in each kind of place. The places were fixed by the executor for revision H1-prime (FR-07 item 2; EV-C02-007 15.13 and 15.14). The executor makes p1 to p3 last, after this revision's other parts, before H1-prime's pull request is judged, so they exist before S1 and S2 (below). The plants:
- (p1) a new file holding the plain form, in the current tree of the existing branch `claude/w03-search-fixture`;
- (p2, which is also p5) a new file holding the percent-encoded form. One commit on that branch adds it and the next removes it, so only the history holds it. Its content differs from p1's, so the two are not one blob;
- (p3) a new comment labelled synthetic, holding the plain form, on the fixture issue #308 (`W03_FIXTURE_ISSUE`);
- (p4) the line printed by step `plant` of job `check-devos-test`. H1-prime's class-high change carries that step, sets `W03_PLANT_B64` to the plant's base64, and sets `W03_FIXTURE_ISSUE` to `308`. The same change also gates `tokens_revoke` on the head check. The step is in `check-devos-test` only, the scheduled comparison job. It prints the plain plant exactly once in every scheduled run whose commit holds `W03_PLANT_B64` set, and in no push run, because a push run skips that job. Its script and the job's environment hold only the base64 form, so in a run's logs the plain form occurs only in that line.
  - **S1 prints; S2 searches.** S1 is the first scheduled run of `migrate.yml` created after H1-prime's merge (the merge that sets `W03_PLANT_B64`), and S2 is the second. Each one's commit (`head_sha`) holds `W03_PLANT_B64` set. A scheduled run created before the merge keeps its older commit, which holds no plant, even if it starts later; it is neither S1 nor S2. Each search drops its own run, so neither S1's search nor S2's counts its own run's line. S1's line is therefore the only one S2's search can count: push runs never print, and no run is re-run (the windows, under "Stage and environment").
  - **The expected count** is 1 per job of S2's search, plain, and 0 percent-encoded. That 1 is the one line S1 printed, read from S1's log archive by the search's own rule: the archive's top-level files, or its files in folders if it has no top-level file. S2's per-run line for S1, `logs: run <S1's id>: … (<n> top-level, <m> in folders)`, names the layout the rule used. "(0 top-level, 0 in folders)" is a run not read (CHK-C02-045 F-7 (c)). An archive that holds `check-devos-test`'s log only in folders while another job's log is top-level gives 0 by that rule. That 0 is "could not check" for the logs, never "none found".
  - **S1 is read before S2's count is judged.** S1's `check-devos-test` log must hold the printed line exactly once, shown by a fixed-string count that prints a count only. Otherwise S2's logs place is "could not check".
  - **S1 is not the search run.** S1's own logs place reads "could not check" by design, since no earlier run holds the plant. Its other counts are recorded with the result, never as the result.
  - **The expected values hold for S2 only.** A later run would count S1's, S2's and later lines, so no other run with this tag is this test's run. If S2 cannot serve, the round is made again with a new tag, new plants and its own S1 and S2 (EV-C02-007 15.3).

The branch's older files and #308's older comment hold only the retired tag `20261012T2338Z`, which this round's search does not count.

**Expected plant counts in S2, in each of its two jobs** (CHK-C02-045 C2's numbers, and FR-07 item 2's fact for the logs, fixed before any result):

| The search's place | Planted there | plain | percent |
|---|---|---|---|
| `repository: current trees` | p1 | 1 | 0 |
| `repository: history` | p2 (p5) | 0 | 1 |
| `issue #308` (the fixture issue) | p3 | 1 | 0 |
| `issue #6` | nothing; backed by `issue #308`, read by the same code | 0 | 0 |
| `logs of migrate.yml's earlier runs` | p4, S1's line | 1 | 0 |

Any other plant count, in any place, form or job, makes that place "could not check", never "none found". A 0 means a plant is missing or a place was not read. A count above the table's means a copy of the plant outside its planted place, which also reopens FR-07. The credential's expected count is 0 in every place and form (the negative control). The percent-encoded form is planted in history only. That the issues and the logs are searched in that form too is therefore not shown by a plant there; it rests on the step counting both forms with one code path in every place.

The plants are removed after S2's search:
- the fixture issue #308 is closed;
- the branch is deleted by whoever can (the guard refuses a session's branch deletion; otherwise Batu does it, batched with another step of his);
- `W03_PLANT_B64` and `W03_FIXTURE_ISSUE` are emptied by the next class-high change after S2's search (until then every scheduled run prints p4 again, and no search after S2 is this test's run);
- the record keeps the run IDs.

No pull request is opened from the plant branch (`refs/pull/*` are searched as tips and stay). S1's and S2's `check-devos-test` logs hold the printed plant. By FR-07 item 3, no copy of those logs that holds that line goes into a file, in the repository or outside it. They are read where GitHub keeps them, for its retention (90 days by default, EV-C02-007 15.6), and the line is recorded as a count. The executor states in the record how those logs are otherwise kept.

## Could not check

- A place the step cannot read.
- A plant count in S2 other than the table's (above), in any place, form or job.
- S1's `check-devos-test` log not holding the printed line exactly once. S2's line for S1 reading "(0 top-level, 0 in folders)", or giving a layout by which the rule counts 0.
- S1's own logs place, by design. S1 is not the search run, and its counts are never this test's result.
- A scheduled run of `migrate.yml` before H1-prime's merge. It is a run of this test's stage as merged before this revision ("at the first scheduled runs after the workflow merges"), with no plant set. Its result is recorded as "could not check", never a pass. If one runs before this revision merges, this revision falls under the test designer's rule for a test after a result: the executor decides, that result is void, and the test is run at S2 with new plants (FR-07, "A scheduled run before the revised T-W03-09 is fixed").
- S2 superseded at its head check, or S2's logs place reporting earlier runs not read. A merge or a re-run inside the windows causes either, and so does a run list past the search's 400-run bound (N-266).
- A window of "Stage and environment" broken.
- A scheduled run that did not receive the secret (P7). Its "credential present" line is `no`, and the search found nothing because it had nothing to look for.

None of these is a pass. A credential match in any run's search is not "could not check": the claim fails, and the credential is treated as exposed (EV-C02-001 M30). That holds for S1's search and the runs above too.
